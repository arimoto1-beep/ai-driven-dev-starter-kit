# 初回利用で分かったこと

## AGENTS.md薄型化の作業を最初の実例にした

作業メモ機能がGOになった後、本来やりたかった確認として、AGENTS.md薄型化とrule体系分離の作業をwork noteにしてみた。

この作業はかなり長かった。

設計、分離、prompt修正、Opusレビュー、採否判断、実タスクでの確認など、多くの判断があった。

そのため、work notesが本当に価値ある情報を残せるかを見るにはちょうどよかった。

## 最初の出力は「正しいけれど、こじんまりしている」と感じた

最初に作ったwork noteは、

- 背景
- 設計判断
- レビュー
- 実タスクでの確認

という構成で、文章としてはかなり読みやすかった。

ただ、作業にかかった時間や迷った量に比べると、小さくまとまりすぎていた。

読めば概要は分かる。

でも、

> こんなにいろいろ悩んだ作業だったっけ？

という感覚が薄い。

ここで、単に「履歴が大きすぎたから全部入らなかった」のではなく、まとめ方そのものが報告書寄りだったと気づいた。

## 具体的な変更内容はGitで見られる

話していく中で、何を残したいかがさらに明確になった。

たとえば、

- 23本のpromptからAGENTS.md参照を外した
- 7本の番号飛びを直した
- project/50を修正した

といった内容はGit差分から確認できる。

もちろん経緯説明に必要ならwork noteへ書いてよい。

ただ、それ自体を詳細に文章化する価値は相対的に低い。

## 本当に残したいのは完成物から消える情報

AGENTS.md作業で本当に残したいのは、むしろ次だった。

- AGENTS.mdを単純分割するだけでは足りないと思った理由
- 全promptからAGENTS.mdを読ませる案をなぜやめたか
- 「念のためruleを増やす」方向へ戻りたくなかったこと
- Opusの指摘を全部採用しなかった理由
- `review_context` にproject/50を足す案を見送った理由
- 正本関係を決めた直後でも、実装で簡単に逆転したこと
- 実タスクを通して「使えそう」と思えたこと
- それでも判断経緯が正式文書から消えると気づいたこと

こういうものはGitからはほとんど復元できない。

## 「きれいな文章を残す意味は少ない」という基準

この初回利用で、work notesの価値基準がかなり固まった。

文章をきれいにすることは目的ではない。

読めることは必要だが、整った報告書になった結果、

- 迷い
- 不採用案
- 途中の違和感
- 考え直した理由

が消えるなら失敗に近い。

多少生々しくても、

> 後から同じ判断をする人が「なぜこうなったのか」を理解できる

方が価値がある。

## prepare_work_note.mdへ戻した

この気づきを、実例だけで終わらせず `prepare_work_note.md` に反映した。

追加した中心方針は、

> 実装内容や変更ファイルなどGitや正式文書から後で確認できる情報を詳細に列挙することを主目的にしない

こと。

代わりに、

- 何に違和感があったか
- どこで迷ったか
- 何を比較したか
- 採用理由
- 不採用理由
- 前提や判断が変わった経緯
- レビューや実験で考え直したこと

を優先するようにした。

情報量が多い場合も、要約を強くして判断経緯を消すのではなく、付随ファイルを増やして整理する。

## 初回利用そのものが設計の一部になった

結果として、work notes機能は、ルールとpromptがGOになった時点で完全に固まったわけではなかった。

実際に1件作ってみて、

> 何を残せば価値があるのか

を確認したことで、目的が一段明確になった。

このフィードバックまで含めて、今回の作業メモ方式の設計作業だったと考えている。
