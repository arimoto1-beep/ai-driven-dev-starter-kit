# 作業メモ: 作業メモ方式の設計・実装・初回利用

## 目的

AIや人間が行った作業について、Git差分や完成した正式文書だけでは消えてしまう判断経緯を、人間とAIの両方が後から追える形で残す方法を作る。

特に残したいのは、次のような情報。

- 何に違和感があったか
- どこで迷ったか
- 何を比較したか
- 何を採用したか、その理由
- 何を採用しなかったか、その理由
- 途中で前提や判断が変わった経緯
- ミス、見落とし、手戻り
- レビューを受けて考え直したこと
- 当時どこまで確信していたか

変更ファイル一覧や最終結果をきれいに報告すること自体は主目的にしない。

## 状態

完了

## 現在地

- `docs/context/work_notes/` を作業メモ置き場とする仕組みを実装した。
- READMEは比較的固定した入口・現在地・索引とし、詳細は自由形式の付随ファイルへ残す構造にした。
- 作業チャットをそのまま残す案も試したが、AIが後から読む用途では機能しても、人間が読むにはかなり厳しかった。そのため、生ログときれいな要約の中間として「判断経緯を落とさず再構成する」方針にした。
- 作業メモの対象範囲と粒度は人間が最終判断する。
- AIを指示側と作業側へ分けることは必須ではない。分けている場合は、通常、全体経緯を把握しているAIが作業メモを構成する。
- リポジトリを参照できるAIは実ファイルやGitも確認する。参照できないAIでも、提供された会話・作業報告・資料から作業メモを作れる。
- 作業メモpromptは `prompts/prepare_work_note.md` に一本化した。別の保存専用promptは設けない。
- リポジトリを更新できるAIは、人間確認後の保存指示を受けてそのまま保存できる。更新できないAIは、別AIへそのまま渡せる自己完結した反映指示を作る。
- 「反映担当AI」という正式な第三の役割は設けない。
- Opus 5の整合性レビューでは一度 `STOP` となったが、周辺ルール・索引・人向け文書を修正し、独立再レビューで `GO` となった。
- 最初の実運用例としてAGENTS.md薄型化の作業をwork note化したところ、最初の出力が「きれいだが、作業量の割に判断の手触りが薄い」ことに気づいた。
- その結果、`prepare_work_note.md` も「Gitから復元できる変更内容より、迷い・判断・不採用理由など完成物から復元しにくい情報を優先する」方向へ補強した。

## 決定事項

- 作業メモは作業テーマ単位で `docs/context/work_notes/` 配下に置く。
- READMEは入口・現在地・索引とし、詳細をREADMEだけへ押し込まない。
- 付随ファイルの種類・数・見出しは固定しない。
- Git差分や正式文書から復元しやすい変更内容より、判断過程、迷い、不採用理由、前提変更などを優先して残す。
- 作業チャット全文の保存を標準方式にはしない。
- ただし、読みやすくするために「成功結果だけのきれいな報告」へ圧縮もしない。
- ミスや見落としは、責任追及ではなく、事象・影響・対応・現在状態として残す。
- 作業メモの対象範囲と粒度の最終判断は人間が行う。
- AIは記録対象・粒度の候補を提案できる。
- AIを指示側と作業側へ分けることは任意。
- 複数AIを使う場合、作業者AIの完了報告は入力資料として扱い、通常は全体経緯を把握するAIが作業メモを構成する。
- リポジトリを参照できないAIでも利用可能とする。その場合は未確認事項を明示する。
- 作業メモpromptは `prompts/prepare_work_note.md` に一本化する。
- 作業メモの構成と保存は別の行為とし、保存には人間の明示指示を必要とする。
- 人間が反映指示を別AIへ渡して実行を依頼した場合、その行為を人間の明示指示とみなす。
- 「反映担当AI」という独立した権限主体は作らない。
- 過去の設計や不採用案は、現在の結論に合わせて消さない。
- 完了後は原則追記。ただし人間の明示指示があれば、訂正内容と理由を残して明白な誤記を訂正できる。

## 未決事項

作業メモ機能の利用開始を妨げる未決事項はない。

今後の通常改訂候補として、独立再レビューでは次の軽微事項が残った。

- `docs/how_to_use_prompts.md` の「通常のpromptはcore 2〜3本＋project 2〜3本」という説明と、7本を読む `prepare_work_note.md` の関係を、将来必要なら補足する。
- `docs/templates/work_note_readme_template.md` の「付随ファイル」とproject/60の「付随ファイル一覧」の語を、将来必要なら揃える。

これらは現在の利用可否には影響しない。

## 次に行うこと

1. 実際の作業でwork notesを使い、残した情報に価値があるかを見る。
2. 「きれいだが役に立たないまとめ」になった場合は、変更一覧ではなく判断経緯が落ちていないかを確認する。
3. 情報量が多い場合は、要約を強くするのではなく、付随ファイルを増やして整理する。
4. 実運用で見つかった不足だけを、必要な範囲で `prepare_work_note.md` やルールへ戻す。
5. 現在の未コミット差分のコミット単位は別作業として整理する。

## 完了後の追記

### 2026-08-08

当初は `write_work_note.md` と構成側promptを分ける案も考えたが、利用者から見ると使い分けが分かりにくく、保存のためだけに別promptを必須にする意味も薄いと判断した。

最終的に `prepare_work_note.md` へ、構成、人間確認、保存、または反映指示生成までをまとめた。ただし保存には人間の明示指示を必要とする。

その後、AGENTS.md薄型化の作業を最初の実例としてwork note化した。最初の出力は読みやすかったが、作業量の割にこじんまりしており、「何を変更したか」の説明に比べて、何で悩み、何を選び、なぜ別案を捨てたかが薄かった。

ここで、work notesの価値は「きれいな文章を残すこと」ではなく、Gitや正式文書からは消える判断の跡を救うことだと再確認した。

この気づきを `prepare_work_note.md` に戻し、Gitから復元しやすい変更内容の列挙より、違和感、迷い、比較した選択肢、採用・不採用理由、前提変更、レビューで考え直したことを優先するよう補強した。
