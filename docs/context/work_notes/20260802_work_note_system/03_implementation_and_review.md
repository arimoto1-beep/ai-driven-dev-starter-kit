# 実装後に起きたことと、レビューで考え直したこと

## 最初の実装は「だいたいできた」に見えた

採用方針を決めた後、Sonnetへ実装を依頼した。

rule、template、context、promptが追加され、pytestも21件通った。

報告だけを見るとかなり完成に近く見えた。

しかし、実ファイルを独立に見ると6つの問題が見つかった。

この時点で、「作業者AIの完了報告だけを作業メモの材料にしてはいけない」という感覚が強くなった。

## 旧ログを守る指示が強すぎて、現在状態のREADMEまで古くなった

旧 `ai_work_logs` を壊したくなかったので、かなり強く変更禁止にした。

その結果、既存ログ本文だけでなく、置き場のREADMEまで変更対象外になり、新しいwork notes方式が導入された後も「まだ未実装」という説明が残った。

保護したい対象を広く指定しすぎたことによる副作用だった。

ここから、

> 保護対象は「ディレクトリ全部」ではなく、何を守りたいのかまで具体化した方がよい

という学びが出た。

## ルールでは許可した訂正が、templateでは禁止されていた

人間側では、

> 完了後は原則追記。ただし明白な誤記は人間指示で訂正してよい

と決めていた。

ところがtemplateには「既存記述は書き換えない」という強い表現が残った。

ruleだけ見れば合っているが、templateまで横断すると矛盾していた。

これは今回の仕組みそのものを象徴する問題だった。

正本を決めても、周辺ファイルに強い表現が残ればAIは迷う。

## project ruleよりtask promptが正本になってしまった

作業メモの参照条件について、`project/60` より `review_context.md` を正本とするような記述が入り込んだ。

AGENTS.md整理で「ruleが正本、promptは実行手順」と決めた直後なのに、実装で逆転していた。

設計思想を決めることと、すべての参照文言がそれに従うことは別問題だった。

## 最初の限定修正で終わらず、prompt再設計が続いた

6論点を限定修正したあと、作業メモを実際に使う段階で新しい疑問が出た。

> AIを指示側と作業者に分けた場合、誰が全体をまとめるのか

最初は「指示側AIがまとめ、別の反映担当AIが保存する」と整理した。

ただ、さらに話すと、反映担当を別役割として固定する必要はないと分かった。

さらに、

> 指示側AIがリポジトリを見られない人もいる

という利用形態も考慮する必要が出た。

その結果、promptはかなり変わった。

## `write_work_note.md` をやめたことで周辺文書が一斉に古くなった

`prepare_work_note.md` 一本へ集約した後、Opus 5へ全体整合性レビューを依頼した。

ここで `STOP` になった。

原因は設計の本体ではなく、

- project/50が存在しない `write_work_note.md` を権限授与先として参照
- project/60にも旧prompt名が残る
- READMEやoverview、人向け導線が古い
- project/00の索引に60がない
- prompt数の説明が23/24/25で揺れている
- `prepare_work_note.md` の変更可能範囲節がない
- templateを必須参照ルールへ入れてしまっている

といった追随漏れだった。

「promptを一本化した」という小さな見た目の変更が、権限境界、索引、完全性チェック、人向け案内まで波及していた。

## STOPは妥当だった

最初は「名前を変えただけに近いのにSTOPか」と感じる余地もあった。

ただ、project/50が存在しないpromptを保存権限の根拠にしていたため、AIが実際に保存しようとすると止まる。

つまり、機能の中心がルール上は動かない。

ここはSTOPで正しかった。

## 人間判断を入れてからSonnetへ限定修正した

Opusが未決として挙げた中で、AIに決めさせず人間側で決めたのは主に次。

- 反映担当AIを正式役割にはしない
- 人間が反映指示を別AIへ渡した行為を明示指示とみなす
- 記録対象と粒度の最終判断は人間
- その原則はtask promptではなくproject/60へ置く
- 人向けREADME等も今回まとめて直す
- 過去の `write_work_note.md` 記述は履歴なので消さない

この方針を固定してからSonnetへ修正を依頼した。

## 再レビューでGO

修正後、再びOpus 5へ読み取り専用レビューを依頼した。

結果は `GO`。

前回STOPだった、

- 権限境界
- 反映指示
- 記録対象・粒度の正本
- prompt導線
- 旧prompt参照
- prompt構造

は解消されていた。

pytestも21件成功。

ここでようやく「仕組みとして使い始めてよい」状態になった。

## この一連で残したいこと

変更ファイル一覧そのものより、今回価値があるのは次の経緯だと思う。

- 「だいたい完成」に見えた後で実ファイルを見ると問題が出た
- 保護指示が強すぎて別の不整合を生んだ
- ルール体系を整えた直後でも正本関係は簡単に逆転した
- prompt一本化は小さな変更に見えて、権限や索引へ広く波及した
- OpusのSTOPをそのまま修正指示にせず、人間判断が必要なところだけ先に決めた
- 最終的にGOになったのは、設計を大きく変えたからではなく、周辺を現在の設計へ追随させたからだった
