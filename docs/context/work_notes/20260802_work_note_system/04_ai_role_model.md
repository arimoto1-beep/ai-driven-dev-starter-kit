# AIの役割分担をどう考えたか

## 最初は「作業者AIにまとめさせる」でよいと思っていた

作業メモ用promptを作れば、そのpromptを作業者AIへ渡してまとめてもらえばよいようにも見えた。

しかし、今回のように、

- 人間と指示側AIで方針を決める
- Opusへレビューを出す
- Sonnetへ実装させる
- 返ってきた報告を別途確認する
- 再度限定修正させる

という流れでは、各作業者AIが見ているのは自分の一部分だけだった。

作業者AIに全体要約を求めても、そのAIが知らない部分は埋められない。

## 指示側AIの方が全体を持っている

指示側AIは、

- 人間が最初に何を気にしていたか
- どの案を比較したか
- 作業者へ何を頼んだか
- 何が返ってきたか
- 人間がどの提案を採用したか
- 何を見送ったか
- どこで方針が変わったか

を一連で見ている。

そのため、AIを分けて使う場合は、通常、指示側AIが作業メモを構成した方が情報価値が高いと考えた。

作業者AIの役割は、全体を語ることではなく、担当範囲を正確に報告すること。

## 一度は「反映担当AI」も正式に分けようとした

指示側AIが作った本文を、リポジトリを操作できる別AIへ保存させる場合を考え、

- 指示側AI
- 作業者AI
- 反映担当AI

という3役に整理した。

その時点ではきれいに見えた。

ただ、実際の使い方を考えると少し過剰だった。

## 利用形態は人によって違う

考えていくと、少なくとも次の使い方がある。

### 1つのAIだけ使う

そのAIが会話もリポジトリも見られる。

この場合、役割分担自体いらない。

### 指示側AIと作業側AIを分ける

指示側が全体を見て、作業側がリポジトリで実装する。

この場合は指示側がまとめるのが自然。

### 指示側AIがリポジトリを見られない

指示側は会話や作業報告から本文を作れる。

保存だけ別AIへ依頼すればよい。

この差を吸収するために、正式な3役モデルはやめた。

## 最終的な考え方

役割名ではなく、できることと人間の指示で整理する。

- 作業全体を把握しているAIが、通常は作業メモを構成する
- AIを分離していない場合は、そのAIがそのまま構成する
- 作業者AIの報告は入力資料
- リポジトリを見られるなら実ファイルやGitも確認する
- 見られないなら、提供された情報だけで作り、未確認を明示する
- 保存できるAIなら、人間確認後の明示指示で保存する
- 保存できないAIなら、自己完結した反映指示を生成する
- 人間がその反映指示を別AIへ渡して依頼した時点で、人間の明示指示になる

「反映担当AI」という特別な権限主体は作らない。

## 作業メモの粒度までAIに決めさせない

AI役割の話をしている途中で、もう一つ気になった。

指示側AIが全体を知っているからといって、

> 何を1つのwork noteにするか

までAIに決めさせる必要はない。

作業者単位で残したい人もいれば、全体だけでよい人もいる。

そこで、

- 記録対象
- 粒度

の最終決定は人間とした。

AIは候補を出すだけ。

これはprompt固有の手順ではなく、work notes運用そのものの原則としてproject/60へ置いた。

## 最終的には「指示側AI」という言葉すら必須ではない

「指示側AIがまとめる」は、複数AIを使っているときの分かりやすい説明としては残る。

ただし、スターターキットの必須構成にはしない。

重要なのは役割名ではなく、

> 作業全体の目的と判断経緯を一番持っているAIがまとめる

という考え方。

この方が、単一AIでも、複数AIでも、リポジトリ非参照AIでも使える。
