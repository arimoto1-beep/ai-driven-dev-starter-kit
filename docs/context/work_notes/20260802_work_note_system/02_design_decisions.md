# 設計判断と採用しなかった案

## いきなり実装せずOpusへ設計レビューを出した

作業メモは単なるフォルダ追加ではなく、

- 記録
- context
- AI権限
- 正本
- prompt
- template

にまたがると感じた。

そこで、最初からSonnetに作らせるのではなく、Opusへ読み取り専用の設計レビューを依頼した。

ここで欲しかったのは「正解を決めてもらうこと」ではなく、見落としている論点を広く出してもらうことだった。

## Opus案は有用だったが、そのままは採用しなかった

Opusからはかなり整った案が出た。

その中には、

- `core/60` を作る
- `docs/work_notes/` をcontext外へ置く
- project固有ルールは既存文書へ分散する
- 専用の `write_work_note.md` を作る
- Gitから復元できる情報は書かない
- 同じ事実は1ファイルだけ
- 完了後は追記のみ

といった提案があった。

骨格はかなり参考になった。

ただ、全部採用すると「情報を落とさない」より「厳密な運用ルールを守る」方へ寄りすぎる感じがした。

そこは人間側でかなり変更した。

## `docs/work_notes/` ではなく `docs/context/work_notes/`

Opusは通常のcontextレビューへ混ざることを避けるため、context外を推奨した。

ただ、意味として考えると、work notesは正式仕様ではなく「必要なときに参照する補助的な経緯情報」なので、個人的にはcontextの方がしっくりきた。

そのため置き場は `docs/context/work_notes/` にした。

通常のcontext横断レビューへ混ぜない問題は、置き場を変えるのではなく、通常探索から除外するルールで解決した。

## project固有ルールを分散しすぎない

Opus案では、保存場所、テンプレート、権限、タイミングなどを既存projectルールへ分散する方向だった。

正本境界としてはきれいだが、作業メモの運用だけ知りたい人が複数ruleを横断しないと全体像が分からない。

そこで `project/60_work_notes.md` を運用正本として置き、他のproject ruleは自分の責務に関係する登録だけ持つ形にした。

## Gitから復元できる情報を「書いてはいけない」にはしなかった

最初のOpus案にあった「Gitや完成物から復元できる情報は書かない」は、かなり迷った。

重複を減らすという意味では正しい。

ただ、経緯を説明するために、

- 何を変更したか
- 何を確認したか
- testがどうだったか

を少し書く必要はある。

そのため「全面禁止」ではなく、

> Git差分やログの全文を理由なく複製しない。経緯の理解に必要なら書く

へ緩めた。

その後、初回利用でさらに考えが進み、

> Gitから復元しやすい情報を中心にしない。復元しにくい判断過程を優先する

という表現の方が目的に合うと分かった。

## 同じ事実は1ファイルだけ、も採用しなかった

READMEに現在地を書き、別ファイルに詳しい経緯を書くと、同じ出来事が二度出ることはある。

これは重複ではあるが、役割が違う。

READMEは入口、付随ファイルは詳細。

そのため「同じ事実は1回だけ」という強い制約は入れなかった。

## 完了後は絶対書換禁止、にも しなかった

履歴を守りたいので原則追記にはした。

ただ、明白な誤字や事実誤認まで直せないのは扱いにくい。

そこで、

- 原則追記
- 過去の経緯を現在の結論に合わせて消さない
- 人間の明示指示がある場合は明白な誤記を訂正可能
- 何を直したかと理由を残す

という形にした。

## `write_work_note.md` と `prepare_work_note.md` を分ける案は後で捨てた

途中では、

- 指示側AIが内容を構成する
- 反映側AIが保存する

という流れを意識し、構成用と保存用のpromptを分ける案を考えた。

しかし、利用者から見ると、

> どっちを使えばいいのか

が分かりにくい。

さらに、リポジトリを操作できるAIなら人間確認後にそのまま保存できるので、保存専用promptを必須にする意味が薄い。

最終的に `prepare_work_note.md` 一本へ集約した。

リポジトリを操作できないAIの場合だけ、自己完結した反映指示を生成する。

## 「反映担当AI」という第三の役割も正式化しなかった

一時期は、

- 指示側AI
- 作業者AI
- 反映担当AI

と3役に整理した。

ただ、これも運用形態を固定しすぎる。

実際には、

- 1つのAIだけで全部やる人
- 指示側と作業側を分ける人
- 指示側AIがリポジトリを見られない人

がいる。

そのため「反映担当AI」という権限主体は作らず、人間が別AIへ反映指示を渡した時点で、その依頼を人間の明示指示とみなす形にした。

## 記録対象と粒度はAIではなく人間が決める

どこまで残すかをpromptへ細かく固定する案もあった。

しかし、作業によって価値のある粒度はかなり違う。

作業者AI単位で残したい場合もあれば、指示側の全体メモだけで十分な場合もある。

そのため、

> 何を1つのwork noteにするか、どこまで詳しく残すかは人間が決める

をprojectルール側へ格上げした。
