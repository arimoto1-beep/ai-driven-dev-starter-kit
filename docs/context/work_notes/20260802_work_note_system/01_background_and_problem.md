# 背景と問題意識

## 会社でやっていた方法が出発点

もともと会社では、まとまりのある作業ごとにフォルダを作り、README.mdを置き、AIにかなり率直な作業経緯を書かせていた。

うまくいったことだけでなく、

- 判断を間違えた
- 見落とした
- やり直した
- 最初の案を捨てた

といったことも残る。

後で読むと少し恥ずかしい内容もあるが、事実として残っている方が役に立つ。

スターターキットでも、同じように「後から作業の経緯が分かる場所」を作りたかった。

## 短い固定フォーマットでは足りないと思った

最初に考えやすかったのは、

- 目的
- 実施内容
- 判断
- 結果
- 未解決事項
- 次にやること

のような小さな固定フォーマットだった。

ただ、AIにこういう枠を渡すと、かなりきれいにまとめてくれる。

それ自体は悪くないが、今回欲しかったのは報告書ではなかった。

たとえば、

- 途中でなぜ止まったのか
- 最初は何を正しいと思っていたのか
- どこで違和感を持ったのか
- 誰かの提案をなぜ採用しなかったのか
- 一度GOになった後で何が見つかったのか

といったことが、短い形式では消えやすい。

そのため、READMEだけは比較的固定し、詳しい部分は自由形式の付随ファイルへ逃がす方向にした。

## 作業者AIのチャットログをそのまま残す案も試した

もう一つ試したのが、作業者AIのチャットログをそのまま残す方法だった。

これはAIが後から読むという意味ではかなり機能する。

作業中の発言が全部残っているので、情報そのものは失われにくい。

ただ、人間が後から読むにはかなり厳しかった。

長い会話の中から、

- どれが単なる途中案か
- どれが最終判断か
- どこで前提が変わったか
- どの発言が重要だったか

を拾い直す必要がある。

「情報を失わない」ことだけを考えるなら生ログは強いが、再利用しにくい。

そこで落としどころとして、

> チャットをそのまま保存するのではなく、人間が読める形へ再構成する。ただし、判断や迷いまできれいに削らない

という方向を選んだ。

## きれいな文章を残したいわけではなかった

この点は途中でさらに明確になった。

欲しいのは、読み物として完成度の高い文章ではない。

変更内容はGit差分を見ればかなり分かる。

正式な仕様やルールは正式文書を見れば分かる。

それよりwork notesで救いたいのは、

- 何で悩んだか
- 何を比較したか
- なぜこの案にしたか
- なぜ別案を捨てたか
- どこで考えが変わったか

のような、完成物から復元しにくい部分だった。

後のAGENTS.md作業メモの初稿が「読みやすいけれど、作業量の割にこじんまりしている」と感じたことで、この目的がかなりはっきりした。

## 前提整理が想定以上に大きくなった

作業メモを追加しようとしただけなのに、その前にAGENTS.md、rule、prompt、人向け文書の正本関係が気になり始めた。

結局、作業メモ機能の前に大きなルール体系整理を行うことになった。

本来の目的から見るとかなり大きな寄り道だった。

ただ、後から見ると、この寄り道があったから、

- 作業メモは正本ではない
- どのルールが作業メモの権限を決めるか
- promptはどのルールに従うか
- context内でどう参照するか

を曖昧にせず決められた。

一方で、前提整理そのものが大きくなり、本来何を作りたかったのか見失いかけたのも事実だった。
