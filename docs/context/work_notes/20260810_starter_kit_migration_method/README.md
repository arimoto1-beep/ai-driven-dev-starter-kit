# スターターキット既存環境の新版移行方法

## 目的

AI駆動開発スターターキットのルール構造・context運用を大きく変更したあと、
すでに利用・カスタマイズされている既存環境を新版へどう移行するかを検討・実験した記録。

最終的なファイル差分だけではなく、

- なぜ単純上書きでは危ないと考えたか
- 最初の移行実験で何が不足したか
- 一度 OK / GO まで到達したあと、なぜ実験をやり直したか
- Claude Code と Codex で結果が一致しなくても問題ないと判断した理由
- rules と context で移行方式を分けた理由
- 過去contextを新版形式へ変換しないと判断した理由
- 今後のスターターキット更新で再利用したい判断基準

を残す。

このwork noteは移行ルールそのものの正本ではない。
正式なrule・promptがリポジトリに存在する場合は、そちらを正本とする。

## 現在地

既存環境の新版移行は、一律の「新版ファイルで上書き」では扱わない方針になった。

大きく2種類に分けている。

### rules

「今の動き方」を新版へ移す。

既存利用者が加えた変更意図を抽出し、
新版で吸収済みか、残す必要があるか、衝突するかを確認したうえで
新版構造へ意味を移す。

変換型マイグレーションとして扱う。

### context

「これまでの記録」は旧形式のまま保持する。

旧AI作業ログなどを新版形式へ変換せず、
今後の保存方式だけ `work_notes` へ切り替える。

既存保持＋新運用追加型として扱う。

## 決定事項

- rules移行では、旧版・利用者版・新版を A / B / C として明確に分離する。
- A→B から利用者固有の変更意図を抽出する。
- A→C から新版側の構造変更と受け皿を確認する。
- 利用者固有の意図が新版で「吸収済み」「部分吸収」「未吸収」「衝突」「判断不能」のどれかを追跡する。
- 文字列が似ているだけで「吸収済み」と判定しない。意味・拘束力・適用範囲・発動条件まで見る。
- 衝突や判断不能をAIだけで解消しない。人間判断へ戻す。
- 新版参照先は moving な `main` ではなく、特定commit/tagへ固定する。
- 1回正しく移行できたことと、再利用可能な移行promptを検証できたことは別と考える。
- AI環境ごとにpromptを分けてもよい。すべてのAIで同じ分類結果になることは必須としない。
- 最重要なのは、利用者固有の意図をsilent lossしないこと。
- rules移行は「影響調査 → 人間判断 → 移行実行 → 別AIによる独立レビュー」の流れとする。
- contextの過去記録は新版形式へ遡及変換しない。
- 旧 `ai_work_logs` は凍結して保持し、新規作成しない。
- 今後の作業記録は `work_notes` を使用する。
- 新版作者自身のwork noteは利用者プロジェクトの履歴ではないため、利用者環境へコピーしない。
- 履歴系成果物は「新版にあるから」という理由だけで利用者環境へ上書きしない。
