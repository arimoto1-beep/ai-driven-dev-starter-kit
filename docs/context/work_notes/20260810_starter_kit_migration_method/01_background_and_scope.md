# 背景と今回扱った範囲

## AGENTS.mdを分けたことで「既存環境の更新」が問題になった

スターターキットでは、もともとAIに守ってほしいルールを
主に `AGENTS.md` へ集めていた。

運用を続けるうちに内容が増え、

- 共通で守りたい原則
- スターターキット固有の運用
- taskごとの実行手順
- 人間向け説明

が混在するようになった。

そこで `AGENTS.md` を薄い入口にし、

- `docs/rules/core/`
- `docs/rules/project/`
- `prompts/`

へ責務を分けた。

各promptが何を読むかは、そのpromptの `## 必須参照ルール` を正本とする形へ変更した。

この変更自体は整理として成立したが、
その時点で別の問題が出た。

すでに旧スターターキットを使っている人が、
自分のプロジェクト向けに `AGENTS.md` やpromptを変更していた場合、
新版をそのまま上書きすると、その変更が消える。

新版ではファイルの配置そのものが大きく変わっているため、
通常のGit mergeだけを考えても不十分だった。

問題は「どの文字列を残すか」ではなく、

> 利用者が何のために追加したルールなのか

を新版構造へ移すことだった。

## 検証用に利用者カスタマイズを作った

実際の既存利用者環境を模すため、
旧版スターターキットへ意図的にローカル変更を追加した。

主な内容は次のようなものだった。

- 実装コードは原則として標準ライブラリを使うが、理由と影響を示し、人間が承認すれば外部ライブラリを利用可能
- SQLをPythonへ直接埋め込まず、原則として外部SQLファイルで管理
- 単体試験だけで安心せず、可能な限り早く実環境または実環境に近い環境で確認
- 設計へ影響しない軽微なコード修正は、AI判断で事前承認なしに実施可能
- ログへ個人情報・認証情報を出力しない
- 設計内容を人間が確認してから実装へ進む
- 実装中に設計上の問題が見つかったら、AIが勝手に補正せず設計へ戻す
- 障害調査・設計判断の経緯をMarkdownで残す
- 既存コード変更時に呼び出し元・呼び出し先への影響も確認
- unrelatedなリファクタリングを同時に行わない
- レビュー結果へ影響機能・ファイル・外部I/Fを記載
- 確認できない影響を推測で「影響なし」としない

同じ意図が複数箇所に重複しているものも意図的に残った。

これは、実際の長期運用でも十分起こり得る状態として扱った。

## A / B / Cで考える

最終的に、移行調査では次の3点を分けることが重要になった。

### A: 旧版スターターキット基準

`2632a9dd6e1060ebaeb6ca149e73680edc384dab`

まだ利用者固有変更を入れていない旧版。

### B: 利用者カスタマイズ済み環境

`b7342ec19e975c9a4304a0c39648fc64a32a1e39`

Aへ利用者固有の変更を入れたfixture。

### C: 新版スターターキット基準

`1af7dc8643b292e5a158c2bace831d9dfb33bcbb`

AGENTS.md分割・rules体系・work notes等を含む新版。

AはBとCの共通祖先として扱える。

そのため、

- A→B = 利用者が独自に変えたもの
- A→C = スターターキット作者が新版で変えたもの

として分離できる。

この分離なしに B と C を直接比較すると、

「これは利用者固有変更なのか」
「新版側の構造変更なのか」

が混ざりやすい。

## 新版の変更規模

検証時点では、

- A: 111ファイル
- B: 111ファイル
- C: 142ファイル

だった。

A→Cは、

- 31ファイル追加
- 43ファイル変更
- 削除0
- 68ファイル一致

合計74ファイルが差分対象。

A→Bで利用者が変更した4ファイルは、
4ファイルすべてがC側でも変更されていた。

つまり、

> 「利用者が触っていないファイルだけ新版で置き換える」

という単純な方式では処理できなかった。

## 今回の範囲

この作業では、主に次の2種類を扱った。

### rules

現在・今後のAIの振る舞いを決めるもの。

利用者固有の意味を新版へ移す必要がある。

### context

過去に何があったかを残す補助記録。

必ずしも新版形式へ変換する必要はない。

当初はこの2種類を同じ「スターターキット更新」として考えていたが、
実験を通して移行方法を分けることになった。
