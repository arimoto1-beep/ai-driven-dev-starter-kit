# 一度OK / GOになったあと、prompt検証をやり直した

## 正しい結果ができたことと、再利用できる方法は別

rules移行は修正後に独立レビューで OK / GO まで到達した。

最初は、この結果をそのまま完成としてcommitしてもよいと考えた。

しかし途中で、

> 今回のfixtureで正しい移行結果を作れたことと、
> 別の利用者にも使える移行方法・promptを検証できたことは別ではないか

と考え直した。

一度の移行では、

- AIの最初の誤り
- 人間からの追加指示
- 独立レビューの指摘
- その後の修正

が積み重なっている。

最終成果物だけを見れば正しいが、
その途中の人間介入まで含めないと再現できない可能性がある。

「正解のファイルができた」という成功を、
「promptが完成した」と読み替えてはいけないと判断した。

## 完成結果をstashへ退避してfixtureへ戻した

一度完成したrules移行結果は削除せず、

`stash@{0}: migration-v1-final-ok-go`

として退避した。

そのうえで、

`b7342ec19e975c9a4304a0c39648fc64a32a1e39`

の利用者カスタマイズfixtureへ戻した。

ここからは、

> 移行結果を作る

のではなく、

> 再利用できる影響調査promptを検証する

ことを目的に変えた。

このやり直しは今回の作業で重要な判断だった。

## 万能promptを1本作ることをやめた

当初は、どのAI環境でも使える汎用的なmigration promptを作る方向も考えた。

しかし実際には、
Claude CodeとCodexでは調査の仕方や分類の傾向が違う。

そこで、

> 利用者が実際に使うAI開発環境ごとに調整したpromptがあってもよい

と考えた。

最終的に少なくとも、

- Claude Code向け
- Codex向け

のrules移行影響調査promptを分けて検証した。

## Claude Code / Opus 5

検証設定:

- Opus 5
- Effort Max
- Thinking enabled

A / B / Cを固定して読み取り専用調査を実施した。

主な結果:

- A=111、B=111、C=142ファイルを確認
- A→Cは31追加、43変更、68一致
- 利用者固有変更を意味単位へ分解
- 意味・拘束力・適用範囲・発動条件を比較
- 新版作者自身のwork noteと仕組み本体を分離
- A→C 74差分を、移行に必要・関連独立・無関係へ分類
- 衝突・判断事項を人間へ返した
- ファイル変更なし

Opus側では利用者意図を細かく分けたため、
13 U-itemとして扱う場面があった。
重複ルールをまとめれば件数は減る。

A→C差分の分類は、

- 移行に必要: 46
- 関連するが独立: 10
- 無関係: 18

という整理だった。

## Codex / GPT-5.6 Sol

検証設定:

- GPT-5.6 Sol
- reasoning Extra High
- speed Normal

同じA / B / Cを対象に別promptで調査した。

Codexでは、

- 利用者意図: 12 U-item
- 吸収済み: 3
- 部分吸収: 2
- 未解決: 5
- 衝突: 2

という整理になった。

A→C 74差分の分類は、

- 移行に必要: 49
- 関連するが独立: 7
- 無関係: 18

だった。

Opusとは件数も人間確認事項数も一致しなかった。

特に、

- work note関連をどこまで利用者意図の吸収とみなすか
- 呼び出し元・呼び出し先確認を部分吸収とみなすか
- 人間判断事項を何件へ分割するか

などで違いが出た。

## 結果が一致しなくてもよいと判断した

最終的に重要視したのは、

> OpusとCodexが同じ表を作ること

ではなかった。

重要なのは、

- 利用者固有変更を黙って落とさない
- 「それっぽい新版記述がある」だけで吸収済みにしない
- 弱くなったルールを検出する
- 衝突を人間へ返す
- 新版作者の履歴やunrelatedな変更を自動導入しない

ことだった。

両AIとも、この目的は満たした。

AIごとに分類粒度が違うこと自体は問題としなかった。

むしろ、

> 最終判断をAIへ固定的に委譲しない

という今回の設計と整合する結果だった。

## 最終的なrules移行フロー

最終的には次の流れへ整理した。

### 1. 移行影響調査

AIがA / B / Cを比較する。

利用者固有変更を抽出し、
新版での吸収・未吸収・部分吸収・衝突・判断不能を報告する。

この段階ではファイルを変更しない。

STOPになっても失敗とは限らない。

人間判断が必要だと正しく検出できたなら、
影響調査としては成功。

### 2. 人間判断＋移行実行

人間が、

- 衝突をどうするか
- 利用者ルールを残すか
- 新版側へ寄せるか
- どのlayerへ置くか

を決める。

その判断を入力として別promptで移行を実行する。

### 3. 別AIによる独立レビュー

移行担当とは別AIで、

- 利用者意図が追跡できるか
- 拘束力が弱まっていないか
- rule / prompt / template / indexが同期しているか
- unrelatedな変更が混ざっていないか
- 矛盾が残っていないか

を確認する。

作業AIの「完了しました」だけでは終了しない。
