# 今後のmigrationで再利用したい判断基準

## 1. 最初に「何の資産か」を分類する

同じMarkdownでも役割は違う。

少なくとも、

- 現在の振る舞いを決めるrule
- task手順を決めるprompt
- 正式仕様・設計
- template
- 人間向け説明
- 過去のcontext
- review結果
- 作業履歴

を一律の上書き対象にしない。

特に、

> 現在の正本なのか
> 過去履歴なのか

で移行方法は大きく変わる。

## 2. rulesは文字列ではなく意味を移す

利用者が変更した行をそのままコピーするのではない。

その変更が、

- 何を禁止したかったのか
- 何を許可したかったのか
- 誰の承認を必要としていたのか
- どのtaskへ適用したかったのか
- 常時適用なのか条件付きなのか

まで見る。

文章が似ていても、
拘束力が弱まっていれば移行成功ではない。

## 3. A / B / Cを混ぜない

A: 旧版基準

B: 利用者カスタマイズ済み

C: 新版基準

を明示する。

A→Bから利用者意図を取り出し、
A→Cから新版変更を確認する。

B→Cだけを見ると、
利用者変更と新版変更の起源が混ざる。

## 4. 新版参照先は固定する

`main` や作業中worktreeを参照先にしない。

特定commit/tagへ固定する。

今回もCを、

`1af7dc8643b292e5a158c2bace831d9dfb33bcbb`

として固定した。

これによって、
途中で新版側が変わって実験結果が再現できなくなることを防ぐ。

## 5. 「吸収済み」は4軸で考える

最終的に有効だった観点:

- 意味
- 拘束力
- 適用範囲
- 発動条件・頻度

たとえば、

「確認する」

と、

「必要に応じて確認する」

は同じではない。

## 6. ruleだけでなく依存先も見る

ruleを移しただけで終わらない。

そのruleが、

- prompt
- template
- review出力
- index
- README
- 権限rule

などと接続されている場合、
同期が必要になる。

最初の独立レビューで、
「review ruleはあるが出力slotがない」
という状態が見つかった。

これは局所的な文章比較だけでは拾いにくい。

## 7. 衝突をAIにきれいに解かせない

利用者が、

> 外部ライブラリを人間承認後なら使える

とした一方、
新版が、

> stdlib/pytest以外は禁止

としている場合、
AIが勝手に「より厳しい方を採用」などと決めない。

これは利用者の運用方針と新版設計の衝突。

人間へ戻す。

## 8. STOPは失敗とは限らない

影響調査の目的は、
必ずGOを出すことではない。

人間判断が必要な衝突を正しく見つけてSTOPできれば、
影響調査としては成功。

「止まった = prompt失敗」とは限らない。

## 9. 一度成功した結果と、再利用可能なpromptを区別する

今回もっとも大きかった考え直しの一つ。

人間が途中で補正し、
独立レビューで問題を拾い、
修正してOK / GOになったとしても、

> その最終結果を最初のpromptが再現できる

とは限らない。

移行結果と移行方法を分けて検証する。

## 10. AI環境ごとにpromptが違ってもよい

Claude CodeとCodexで、
同じ分類表にならなかった。

それでも、

- silent lossを防ぐ
- 部分吸収を検出する
- 衝突を人間へ返す
- unrelatedを除外する

という目的を満たしていればよいと判断した。

モデル間の完全一致を品質基準にしない。

## 11. 新版作者の履歴と再利用資産を分ける

新版に存在するファイルだからといって、
すべて利用者環境へコピーするわけではない。

今回、

- `docs/rules/core/60_work_notes.md`
- `docs/rules/project/60_work_notes.md`
- `docs/templates/work_note_readme_template.md`
- `prompts/prepare_work_note.md`
- `docs/context/work_notes/README.md`

は仕組み。

一方、

- `20260802_agents_rule_refactor/`
- `20260802_work_note_system/`

は作者自身の作業履歴。

後者は利用者PJのcontextへ入れない。

同じ考え方は、
完了済みreview結果やサンプルPJ固有の履歴にも適用できる。

## 12. 過去履歴は「きれいにする」ことが破壊になる場合がある

context移行では、
旧AI作業ログを新しいwork notes形式へ揃えなかった。

履歴は、

> 今のtemplateに合っていること

より、

> 当時どう残されていたか

が重要な場合がある。

AIによる再構成は、
見た目を整える代わりに履歴を再解釈する危険がある。

## 13. rulesとcontextの最終整理

### rules

現在の振る舞いを守る。

利用者固有の意味を新版へ移す。

**変換型マイグレーション。**

### context

過去の記録を守る。

既存履歴はそのまま残し、
これからの保存方式だけ切り替える。

**既存保持＋新運用追加型。**

この違いは、
今後スターターキットに別種の資産が増えた場合にも
最初の分類軸として使える。
