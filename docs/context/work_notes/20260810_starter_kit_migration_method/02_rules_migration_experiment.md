# rules移行実験

## 最初の考え

最初は、新版の構造を既存環境へ導入しながら、
旧 `AGENTS.md` 等の利用者変更を新しいruleへ振り分ければよいと考えていた。

AIへ既存環境と新版を見せれば、
それなりに移行案を作れるだろうという期待もあった。

## 最初のSonnet調査で分かった不足

最初の読み取り専用調査では、
利用者固有の変更意図そのものはかなり拾えた。

一方で、大きな不足があった。

AIが、

> 旧版のこの記述を、新版のどこへ移すか

という局所的な対応付けへ寄り、
「新版スターターキット本体をどう導入するか」という視点が弱かった。

つまり、

- 利用者変更の救出
- 新版本体への更新

が一つの問題として十分に整理されていなかった。

また、新版参照先について、
固定commitではなく動いているworktreeを前提にしそうな部分もあった。

この結果から、
単純な「旧→新」ではなく A / B / C を明示する必要があると判断した。

## A / B / C方式

以後の影響調査では、

1. A→Bから利用者固有変更を抽出
2. A→Cから新版側の変更を把握
3. 利用者固有変更ごとにCでの吸収状況を調べる

という順序にした。

特に「吸収済み」を単純なキーワード一致で判断しないようにした。

確認する観点は最終的に、

- 意味
- 拘束力
- 適用範囲
- 発動条件・頻度

まで広げた。

たとえば、

旧利用者ルール:

> 呼び出し元・呼び出し先への影響を確認する

に対して新版側が、

> 必要に応じて呼び出し元・呼び出し先を確認する

となっていれば、
文字列は似ていても拘束力が弱くなっている。

これは「吸収済み」ではない。

## 一度、実際にmigrationまで実施した

影響調査だけでなく、
一度フルのrules移行も実施した。

その後、別AIに独立レビューを依頼した。

結果は STOP だった。

主な指摘は次のとおり。

### 1. reviewルールを追加したが出力先がない

影響範囲をレビュー結果へ出すruleを移したが、
templateやprompt側にそれを記録する明確なslotがなかった。

ruleだけ存在し、実際のtask出力へ接続されていない状態だった。

### 2. review ruleの適用範囲と新版共通観点が矛盾

利用者固有のreviewルールを移した結果、
新版側の共通review観点と責務境界が噛み合わない部分ができた。

意味だけ移しても、
新版側のrule / prompt / templateの依存関係まで見なければ不十分だった。

### 3. 呼び出し元・呼び出し先確認が弱まった

利用者側では明確に「確認する」だったものが、
移行後に「必要に応じて確認する」となっていた。

意味の方向は近いが、拘束力が弱くなった。

この指摘によって、

> 文章がそれらしく移っていること

と、

> 利用者が付けた強さまで保持されていること

は別だと分かった。

### 4. 外部依存ルールが矛盾した

利用者側には、

> 原則標準ライブラリ。
> 外部ライブラリは理由と影響を提示し、人間承認後なら使える

というルールがあった。

一方、新版には、

> 標準ライブラリのみ
> 許可依存はpytestのみ

というルールがある。

移行後、一部に両方が残り、
「使ってよいのか、絶対禁止なのか」が矛盾した。

これは人間判断が必要な典型例だった。

### 5. work noteを残すべき作業だったが提案されなかった

移行方法そのものを検討し、
複数の判断・手戻りが発生しているのに、
work noteの対象として拾えていなかった。

この点も、ruleを追加しただけでは運用が成立しない例になった。

## 修正後

STOPされた項目を修正し、
さらに軽微な指摘として、

- `review_feature_source` の出力への影響範囲追加
- rules READMEのindex
- project/00のindex
- project/25の同期対象

なども補正した。

修正後の独立レビューでは、

- 利用者固有意図を追跡可能
- 主要な矛盾解消
- test 21件成功

となり、

**OK / GO**

まで到達した。

ここまで来た時点では、
一度「移行方法はできた」と考えかけた。
