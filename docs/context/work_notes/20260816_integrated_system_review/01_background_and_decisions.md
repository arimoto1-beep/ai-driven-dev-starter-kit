# 背景と判断経緯

## スターターキットの現在の組み立て方

AI駆動開発スターターキットでは、機能仕様IO単位を中心に、人間とAIで個々の機能を考える。

概念的には次の形になる。

```text
機能仕様A + 機能仕様B + 機能仕様C = 全体機能
```

複数の機能仕様を束ねて一つの作業として設計・実装し、それらを積み上げてシステム全体を構成する。

この方式は業務開発として自然であり、次の利点がある。

- 人間が機能単位で内容を理解しやすい
- 関係者と合意を取りやすい
- 作業範囲を定義しやすい
- AIへ渡すコンテキストを限定しやすい
- 個々の機能仕様、設計、実装、テストを段階的に確認しやすい

そのため、機能仕様IO単位で進める現在の方式自体を変更する判断にはならなかった。

## 気になった点

一方で、個々の機能仕様や各作業がそれぞれ妥当でも、それらを統合したシステム全体が、現在の要件を最初からすべて知った状態で選ぶ構造と一致するとは限らないのではないか、という問題意識が出た。

個々の機能を考えている段階では自然だった責務境界や実装方針も、全体が組み上がることで、初めて次のような再考余地が見える可能性がある。

- 別々に扱っていた責務を統合した方が自然
- 一つにまとめていた責務を分けた方が自然
- 同じ判断や変換が複数箇所に現れている
- 機能仕様上の境界が実装境界として残りすぎている
- 局所的な変更に対して理解・変更・試験の範囲が広くなっている
- 現在の全要件からゼロベースで考えた場合には別の構造が考えられる

したがって、次の2つは区別する必要があると整理した。

```text
機能仕様A + 機能仕様B + 機能仕様C = 必要な全体機能
```

と、

```text
実装A + 実装B + 実装C = 現在の全要件に対して最も筋のよいシステム構造
```

は同じことではない。

## 必要だと考えた補完

機能仕様IO単位で安全に進める方式は維持したうえで、複数の機能・作業が組み上がった後に、一度全体へ戻って構造を再評価する機会を設ける方向を検討した。

中心となる問いは次とした。

> 現在までに確定した要件・制約を最初からすべて知っていたとしても、今のシステム構造を選ぶか。

この問いでは、現在の feature 分割、コンポーネント境界、ファイル構造、呼び出し階層、過去の実装順序を、それだけを理由に正解として扱わない。

一方で、正式資料で維持すべき要件として確定している入力、出力、外部動作、制約、エラー契約などは尊重する。

## AI駆動開発としての観点

今回の再評価は、一般的なアーキテクチャレビューだけではなく、AI駆動開発として扱いやすい構造かも見ることにした。

### 全体像の復元容易性

AIがシステムを安全に変更・レビューするには、まず対象システムの全体像を正しく復元できる必要がある。

そのため、次を確認対象とする。

- システムの目的と主要な処理を把握しやすいか
- 処理の入口とデータの流れを追いやすいか
- コンポーネントの責務を構造から推測しやすいか
- 全体像を理解するために不必要に広い資料・コード横断が必要になっていないか

「大量のコンテキストを読めば最終的に理解できる」ことと、「AIが扱いやすい構造である」ことは別として扱う。

### 変更とコンテキストの局所性

一つの機能変更のために、関係の薄い大量のコード・設定・設計まで理解しなければ安全に変更できない構造になっていないかを見る。

AIへ局所的な変更を依頼したときに、変更対象と確認対象を自然に限定できることを重視する。

### 試験と自己確認の局所性

AIが変更を行った後に、その変更の正しさを自分で確認しやすいかを見る。

一つの変更に対して、構造上の理由だけで不必要に広い結合試験や回帰試験が必要になっていないかも評価する。

### レビューと障害解析のしやすさ

AIが変更影響を追い、レビューし、障害発生時に処理経路を復元しやすい構造かを見る。

構造上見える境界と実際の責務が一致していることも、この観点に含める。

## 検討した別方向

### 実装分割そのものをAI主導にする

機能仕様や全要件から、実装単位の分解までAIへ大きく任せる方向も考えた。

この方式なら、人間が定義した業務上の機能境界を、そのまま実装境界として引き継ぐ可能性を下げられる。

一方、業務開発では設計者が段階を作り、関係者と合意し、担当や進捗を管理しながら進める必要がある。

そのため、現在のスターターキットを全面的にAI主導の分解方式へ変更する判断にはならなかった。

### 統合後の再評価を正式ゲートにする

統合後レビューを必須工程や正式な次工程判定へ組み込む案も考えられる。

しかし、今回は採用しなかった。

理由は次のとおり。

- 毎回の開発を重くする可能性がある
- AIが提示した理想構造へ変更する圧力になりやすい
- 既存の正式レビューとの役割が混ざる
- 再評価の目的は、まず改善候補と再考材料を得ることだから

## 採用した方向

現在のスターターキットの開発方式は維持しつつ、統合後に任意で実施できる読み取り専用レビューを追加する。

レビューでは、現在の構造を前提にした改善だけでなく、現在の全要件からゼロベースで見た代替構造も検討する。

ただし、次の2つは明確に分ける。

```text
ゼロからなら別構造がよい
```

と、

```text
今からその構造へ変更すべき
```

は別の判断である。

既存システムには移行コスト、運用実績、納期、変更リスク、周辺資産があるため、理想案がそのまま変更指示になるとは限らない。

## 今回の位置づけ

今回追加した仕組みは、機能仕様IO単位で進める現在のスターターキットの代替ではない。

機能単位で安全に進める長所を維持しながら、

**部分を積み上げた後、一度全体へ戻る**

ための補完的な仕組みとして位置づける。
