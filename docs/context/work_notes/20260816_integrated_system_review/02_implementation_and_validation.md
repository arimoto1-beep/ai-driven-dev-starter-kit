## 実施内容

新しい読み取り専用レビュー prompt を追加した。

### 新規追加

```text
prompts/review_integrated_system.md
```

### 導線更新

```text
prompts/README.md
docs/how_to_use_prompts.md
```

既存の正式レビュー prompt、標準 workflow、ルール文書、実装コード、テストコードは今回の意図した変更対象には含めなかった。

## `review_integrated_system.md` の役割

新規 prompt は、複数の feature・機能仕様・設計・実装が組み上がった後に使う。

既存レビューとの役割は次のように整理した。

| prompt | 主な役割 |
|---|---|
| `review_feature.md` | 1つの feature の仕様・設計・実装・テストの整合確認 |
| `review_command.md` | 現在定義されている overview・feature 分割・entrypoint・結合試験を前提とした command/app 全体レビュー |
| `review_design_code_consistency.md` | 現在の正式資料とコードの意味上の矛盾確認 |
| `review_integrated_system.md` | 現在の構造そのものを正解から外し、現在の全要件から全体構造を再評価 |

`review_integrated_system.md` は `review_command.md` の代替ではない。

## 主な設計内容

### 現在の実装構造を固定しない

以下は、現在そうなっているだけでは正解として固定しない。

- feature 境界
- ファイル・モジュール・クラス・関数の分け方
- コンポーネント分割
- entrypoint と feature の切り方
- ワークフローの処理分割
- 現在の呼び出し階層
- 現在の抽象化
- 過去の実装順序

ただし、正式資料で今後も維持すべき意味として明示されている場合は勝手に無視しない。

### 特定の構造を先に正解にしない

次を機械的な正解にしないよう明示した。

- 分割が細かいほどよい
- まとめるほどよい
- コンポーネント数が少ないほどよい
- マイクロサービスがよい
- モノリスがよい
- 共通化が多いほどよい
- AI向けなら特殊な構造でもよい

人間とAIの双方が、責務・処理フロー・変更範囲・試験範囲を自然に理解できることを重要な基準とした。

### AI駆動開発への適合性を明示

以下を独立した評価対象にした。

- 全体像の復元容易性
- 機能仕様の集合と全体構造の関係
- 判断ロジックの所在
- 変更の局所性
- 試験・自己確認の局所性
- AIが必要とするコンテキスト範囲
- AIによるレビュー容易性
- 障害解析・観測可能性
- 構造の見た目と実態
- 過剰設計と過小設計
- ゼロベースで見た代替構造
- 現実的な変更コスト

### 全体像の復元結果も出力させる

レビュー対象のシステムについて、まず全体像を復元し、

```text
復元確信度: High / Medium / Low
```

を報告させる。

また、全体像の把握に必要だった主な資料・実装範囲や、復元を難しくした要因も出力対象とした。

これは、

「AIが最終的に理解できるか」

だけでなく、

「理解するためにどれだけ広いコンテキストを復元する必要があったか」

自体をシステム構造の評価材料にするためである。

### 正式判定にはしない

この prompt では、

- `GO`
- `条件付きGO`
- `STOP`
- `OK`
- `要修正`

などの正式な次工程判定は行わない。

ファイルも変更しない。

改善案の採用、正式資料変更、リファクタリングは別作業として人間が判断する。

## 変更範囲の確認方法

修正版リポジトリの Git status には、今回以前からの未コミット差分が多数存在した。

そのため、Git の作業ツリー全体を今回作業の差分として扱うことはできなかった。

今回の変更範囲は、

- 人間がアップロードした元ZIP
- 今回生成した修正版ZIP

を直接比較して確認した。

キャッシュディレクトリを除いた論理的な差分は以下だけだった。

```text
新規:
prompts/review_integrated_system.md

更新:
prompts/README.md
docs/how_to_use_prompts.md
```

## テスト

修正版ZIPを展開した状態で次を実行した。

```text
python -m pytest -q
```

確認時の結果:

```text
.....................                                                    [100%]
21 passed
```

21件すべて成功した。

## 後から確認した不要な改行コード差分

作業メモ作成時に元ZIPと修正版ZIPをさらに比較したところ、`docs/how_to_use_prompts.md` に意図しない改行コードの変更があることを確認した。

### 元ZIP

- CRLF主体
- 一部LFが混在

確認値:

```text
CRLF: 322
LF全体: 327
```

### 修正版ZIP

- LFのみ

確認値:

```text
CRLF: 0
LF全体: 344
```

改行コード差分を無視して比較すると、意図した内容変更は17行の追加だけである。

したがって、機能上の変更意図とは無関係なファイル全体の物理差分が発生している。

これは最初の実装完了報告時には把握できていなかった。

現時点では修正していない。

## 作業メモ作成時の訂正

最初の作業メモ案では、同じ会話内にあった今回のスターターキット変更とは直接関係しない別システムの議論を、今回の発端として混在させてしまった。

人間から「今回の対象とは関係がない」と指摘を受けたため、保存前にその記述を削除し、スターターキット自身の開発方式から生じた問題意識だけで背景を再構成した。

## 未実施の確認

以下は今回実施していない。

- 実際の複数 feature システムへ `review_integrated_system.md` を適用した出力評価
- 新規 prompt が期待どおり現在の設計を固定せず、別案を提示できるかの実運用検証
- スターターキット全 prompt に対する「具体的な手順や方法を過度に固定していないか」の棚卸し
- 改行コード差分の修正
- コミット

## 作業中に見つかった別テーマ

既存 prompt には「作業手順」等の節が存在する。

ただし、見出しとして「作業手順」が存在することと、AIの実装方法を不必要に固定していることは同じではない。

今回の作業では、その内容を体系的に評価していない。

そのため、既存スターターキットがAIを手順で縛っているとは結論づけていない。

必要なら別作業として、各 prompt について、

```text
これは守るべき条件なのか。
それとも人間が考えた方法をAIへ固定しているのか。
```

という観点で確認する。

## 現在の評価

統合後レビューを独立 prompt として追加する目的は実現できている。

ただし、実際の資産へ適用した効果はまだ観測していないため、有効性は未検証である。

また、`docs/how_to_use_prompts.md` の不要な改行コード差分については、最終成果物として扱う前に人間判断が必要である。
