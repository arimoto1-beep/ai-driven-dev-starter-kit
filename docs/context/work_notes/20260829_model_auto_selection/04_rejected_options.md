# 検討したが採用しなかった案

設計検討フェーズと実装中に検討し、採用しなかったものを残す。
**「人間が却下した」ものと「AIが提案しなかった／取り下げた」ものを区別して書く。**

## 1. モデル選択のために別のAIを呼ぶ

**却下（AIが第1回検討で非推奨とし、人間も採用しなかった）。**

「作業内容をAIに評価させて `cheap` / `standard` / `strong` を選ばせる」案。

却下理由：

- 成果物を生まないAI呼び出しが stage ごとに増える。削減しようとしているコストに直接ぶつかる
- 非決定的になり、「後からなぜこのモデルを使ったか分かる」という要件と衝突する
- Gate もレビューも通らないAI判断が1つ増える。このキットの構造と整合しない

**採用した CP1 Reviewer 方式は、この却下理由をすべて回避する。**
既存の呼び出しに1語の出力を足すだけで、追加呼び出しがゼロだからである。

## 2. 自動昇格（cheap → standard → strong）を主機構にする

**却下（AIが第1回検討で提案し、人間が「第一段階では実装しない」と決定）。**

AIは当初、「収束しなければ1段昇格」を推奨案としていた。人間の判断で見送った。

見送りが妥当だった理由（実装後の視点）：

昇格を入れると、runner に**失敗理由の分類表**が必要になる。

| 信号 | 昇格してよいか |
|---|---|
| `guard_violation` | ×。境界違反であって能力不足ではない |
| `business_decision` / `tradeoff` / `risk_acceptance` | **×。人間が決める領域。昇格は人間判断の境界をモデル能力で突破する構造になる** |
| `state_error` | ×。環境・設定の問題 |
| `spec_not_approved` | ×。工程状態 |
| test failure | ×。収束ループ途中では正常な状態 |
| 収束しない / 差し戻しの繰り返し | ○ |

今回の方式では、この表そのものが不要になった。**実装量と説明の長さの差が大きい。**

将来追加する場合は、`model_selection` に値を追加し `escalated_from` キーを足す形で拡張できる。
現在の構造はそれを妨げない。

## 3. Reviewer の最低モデルクラスを固定する（下限ルール）

**却下（AIが第2回検討で提案し、人間が「第一段階では設けない」と決定）。**

AIの提案は「Reviewer は `cheap` にしない（下限2）」だった。
理由は「Worker のクラスを下げられるのは Reviewer が最後の砦だから」。

人間の判断は「まず基礎レベル + 難易度の単純な計算だけで成立させ、
必要性が実AI検証で確認された場合に追加する」。

**結果として、`easy` feature では Worker も Reviewer も `cheap` になる。**

実AI検証で見るべき点（AIの提案。判断は人間）：

| 見るもの | 追加を検討すべき兆候 |
|---|---|
| `findings_total` | `easy` feature で恒常的に 0 件 |
| `review_rounds` | 常に 1 ラウンドで即 PASS |
| CP3 の人間確認欄 | 人間が受け入れ時に Reviewer の見逃しを発見している |

追加する場合は、丸め規則に1行足すだけで済む（runner の構造変更は不要）。

## 4. 基礎レベルを role 単位で持つ

**却下（AIが第2回検討で提案し、人間が「当初想定どおりプロンプト単位にする」と決定）。**

AIは `design` / `build` / `review` の3つで十分と提案した。

人間の決定に従いプロンプト単位にした結果の観察：

**現在の既定設定では、両案は同じクラスを出す。**
`create_function_call_flow = 1` は `max` 合成により G1 では吸収されるためである。

それでもプロンプト単位が優れている点：

- 係数が、能力要求を実際に決めているもの（プロンプト）に付く
- `stage_*_prompts` を差し替えればレベルも自動的に追随する
- プロンプトが増えたとき（`implement_entrypoint.md` などをオートモードへ取り込む場合）に1行足すだけで済む
- `role` を経由しないため、モデル選択から role 概念が外れる

## 5. 基礎レベルをプロンプトファイルの front matter に書く

**却下（AIの判断。人間の指示にも「front matter を新設しない」と明記されていた）。**

`70_feature_loop.md` は次を明記している。

> プロンプト自身がモデルを変更しません。モデルの選択は起動側の責務です。

係数をプロンプト側に置くとこの境界が崩れる。加えて `prompts/*.md` に front matter は存在せず、
runner がプロンプトファイルを解析する新しい結合が生じる。

**「プロンプト単位で係数を持つ」ことと「プロンプトファイルの中に書く」ことは別である。**

## 6. `--difficulty hard` のような難易度の直接指定

**却下（人間の指示で第一段階の対象外）。**

`--model-class` で用途を満たせる。両方あると優先順位が4段になる。

## 7. `prompt_base_level` を Gate記録へ残す

**却下（AIが第2回検討で比較し、記録しない案を推奨。人間も追加を指示しなかった）。**

`feature_difficulty` と `worker_model_class` の対で「なぜこのモデルか」に答えられる。
基礎レベルは設定から導出できる。「記録項目を増やしすぎない」という制約を優先した。

唯一の利点は「基礎レベルを変更した後の遡及解釈」だが、
これは基礎レベルを軽々に変更しないことで対処すべき問題である。

## 8. Worker 指示文の `使用モデル区分` 行を削除する

**今回は変更しなかった（AIが未決事項として提示、人間の指示なし）。**

Reviewer 指示文からは削除した（`reviewer_model_class` が役割を引き継ぐため）。
Worker 指示文には残したままである。

削除を検討する理由：`prompts/run_stage.md` はこの値の使い道を定義しておらず、
**Worker が自分のクラスを知って挙動を変えるのは望ましくない。**

残した理由：今回のスコープはモデル選択方式の切り替えであり、
Worker のモデル情報の意味づけは変えていない。`run_stage.md` を触らずに済む。

未決事項として README へ記載した。

## 9. `model_selection` の値を `v1_fixed` / `legacy_fixed` にする

**却下（人間の訂正）。**

AIは第1回検討で `v1_fixed`、第2回訂正で `legacy_fixed` を提案した。

人間の訂正：このキットで V1 はマニュアルモードを指す。`feature_runner.py` を使う方式はすでにオートモードであり、
`role_*` 固定はその**内部の従来方式**である。世代を示す名称は誤解を招く。

採用した値は `role_fixed`。

## 10. 段階的廃止をリリース番号（V2.0 / V2.1 / V3）で表現する

**却下（人間の訂正を受けてAIが取り下げ）。**

`feature_runner.py` を使う方式そのものがオートモード（現行世代）であり、
「V3」はキット全体の次世代を意味してしまう。

`role_*` の廃止時期は未決事項として残し、リリース番号では表現していない。
