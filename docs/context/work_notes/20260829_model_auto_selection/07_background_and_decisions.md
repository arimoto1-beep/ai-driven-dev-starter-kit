# モデル自動選択に至った背景と判断経緯

## この文書の目的

この文書は、モデル自動選択機能の最終仕様そのものではなく、

* なぜモデル自動選択を入れようとしたのか
* 途中でどのような案を検討したのか
* なぜ現在の単純な方式を選んだのか
* 実装途中でどのような認識違いがあったのか
* 実AI検証を通して何が分かったのか

を後から追えるように残すための作業記録である。

現在の正式なルールや設定値は `docs/rules/project/70_feature_loop.md` などを正とする。

この文書は、それらが現在の形になった理由を補足する。

---

# 1. 出発点

今回の検討は、「最適なモデルを自動的に選びたい」という高度な最適化要求から始まったものではない。

最初に欲しかったのは、もっと単純なものだった。

* 明らかに簡単なfeatureにstrongモデルを使わない
* 明らかに難しいfeatureにcheapモデルを使わない
* 普段は利用者がモデルクラスを意識しなくてもよい
* 仕組みそのものが複雑になりすぎない

つまり目標は「最適化」ではなく、**明らかな過剰利用と過小利用を避ける程度の自動選択**だった。

人間側では、モデル選択まで精密な仕組みにすると、モデル選択ロジック自体の保守・説明・検証が必要になり、スターターキット全体の理解しやすさを損なうことを懸念していた。

そのため最初から、

> 完璧なモデル選択より、説明できる単純なモデル選択

を重視した。

---

# 2. 最初に検討された複雑な案

検討初期には、より細かな自動選択案も候補になった。

例として、次のような方向が考えられた。

* stageごとに難易度を判定する
* WorkerとReviewerで個別に難易度を判定する
* REVIEWでRETURNしたらモデルを自動的に1段上げる
* テスト失敗時にモデルを自動的に上げる
* 収束しない場合にstrongへエスカレーションする
* FINDINGの種類によってモデルを変える
* feature難易度を3段階より細かくする
* 0.5刻みなどのスコアリングを使う
* Reviewerには最低standardなどの例外ルールを持たせる
* モデル選択専用のAI判定を追加する

これらは個別には合理性がある。

しかし、人間側では次第に、

> モデルを選ぶための仕組みが、featureを作る仕組みより複雑になり始めている

という違和感が強くなった。

特に、RETURN・BLOCKED・テスト失敗などから「モデル能力不足」を自動推定する案は採用しなかった。

失敗の原因は、

* 仕様不足
* 設計ミス
* テスト設計ミス
* 単純な実装バグ
* ツール実行エラー
* 環境問題

など多様であり、

> 失敗した = モデルが弱かった

とは限らないためである。

モデル不足と原因を誤認すると、strongを多用するだけの仕組みになり得る。

---

# 3. 「足す」のではなく「減らす」方向へ整理した

検討中、人間側では別の問題意識も強くなった。

AIは既存の仕組みを前提として、

> 何を追加すれば要求を満たせるか

を考えやすい。

一方、人間が求めていたのは、

> この仕組みに本当に必要な要素は何か
> そもそも削除できる概念はないか

という整理だった。

モデル選択についても同様で、

* stage別再判定
* 自動エスカレーション
* Reviewer例外
* 詳細スコア
* 失敗理由別分岐

を追加する方向ではなく、一度それらを外し、

**何が最低限あればモデルを選べるか**

を考え直した。

最終的に残ったのが、

1. featureそのものの難しさ
2. 実行するpromptそのものの基礎的な重さ

の2要素だった。

---

# 4. feature難易度とprompt基礎レベルを分離した

最終的な考え方は次のようになった。

## feature_difficulty

featureそのものがどの程度複雑かを表す。

* easy
* normal
* hard

これはfeatureの性質を表す値である。

## base_level

各promptで行う作業そのものが、どの程度強いモデルを必要とするかを表す。

たとえば、

* 設計を作る
* テスト設計を作る
* 実装する
* Reviewerとして確認する

では、同じfeatureでも作業の性質が異なる。

そのため、

> hard featureだから全工程strong

とはせず、

> featureの難しさ + 実際に行う作業の基礎レベル

でモデルを決めることにした。

最終的な計算は、

```text
prompt base level + feature difficulty adjustment
```

を1〜3へ丸め、

```text
1 = cheap
2 = standard
3 = strong
```

へ対応させる単純な方式とした。

---

# 5. feature難易度判定のためのAI呼び出しは増やさなかった

feature難易度をAIに判定させる案を考えたとき、

「モデル選択のためだけにAIを1回呼ぶ」

案も考えられた。

しかし採用しなかった。

モデル選択によってAI利用量を抑えたいのに、その判定のために追加のAI呼び出しが必要になるのは本末転倒に感じたためである。

そこで、すでに存在していたCP1 Spec ReviewのReviewerに難易度判定を追加した。

これにより、

* Spec Review
* feature難易度判定

を1回のAI呼び出しで行える。

**モデル選択機能による追加AI呼び出しは0回**となった。

---

# 6. 難易度判定をstageごとに行わない

feature難易度は、原則としてCP1で1回だけ判定することにした。

G1、G2、CP3で再判定しない。

また、

* FINDINGが出た
* RETURNした
* テストが失敗した
* retryした
* reworkした

といった事象でも難易度を変更しない。

理由は、それらがfeatureそのものの難易度変化を意味するとは限らないためである。

一方、`20_spec.md` が変更された場合は別である。

仕様自体が変わればfeatureの難しさも変わる可能性があるため、

```text
仕様変更
→ CP1を再実行
→ feature_difficultyも再判定
```

とした。

実AI検証でも、hard用featureで一度仕様修正を行った後にCP1を再実行し、再度 `hard` と判定された。

---

# 7. easy / normal / hard の判定基準を増やしすぎなかった

難易度判定は詳細な採点方式にしなかった。

最終的には次の程度に留めた。

## easy

* 要求が少ない
* 入出力やエラー動作が明確
* 設計上の選択余地がほとんどない

## normal

* easyともhardとも明確に言えないもの

## hard

* 要求同士が相互作用する
* エラー・境界条件が多い
* 複数の有力な設計選択肢がある

迷った場合は `normal` とする。

これは精密な難易度分類を目的としていない。

「明らかに簡単」「明らかに難しい」の両端を拾えればよい、という当初目的に合わせた。

---

# 8. Reviewerだけの特別ルールを入れなかった

途中では、

> Reviewerは品質を担保するため最低standardにする

という案も考えられた。

しかし最初の実装では採用しなかった。

例外ルールを増やすと、

```text
基本計算
ただしReviewerは...
ただしCP1は...
ただし...
```

という構造になりやすいためである。

まずは、

```text
base level + feature difficulty
```

だけで全Worker / Reviewerを同じルールに載せることを優先した。

結果としてeasy featureでは、G1・G2・CP3のReviewerもcheapになった。

実AI検証では、そのeasy featureは問題なく最後まで完走した。

ただし、これは1回の検証結果であり、

「easy Reviewerはcheapで常に十分」

と確定したわけではない。

---

# 9. V1 / V2 の認識違い

実装検討中に、重要な用語の認識違いが発生した。

人間側で使っていた意味は、

* V1 = 人間が個別promptを選択して実行する従来方式
* V2 = `feature_runner.py` がWorker / Reviewerを回すオートモード

だった。

しかしAI側では、会話中でモデル選択の話を始めた地点を基準に、

* 従来のrole固定モデル選択 = V1
* 新しいモデル自動選択 = V2

のように解釈しかけた。

これは誤りだった。

`role_design` / `role_build` / `role_review` による固定モデル選択は、すでに `feature_runner.py` のオートモード内部に存在していた。

つまり今回の変更は、

```text
マニュアルモード → オートモード
```

ではない。

```text
オートモード内の従来モデル固定方式
↓
オートモード内のモデル自動選択方式
```

である。

この認識違いにより、一時はモデル選択方式の値として `v1_fixed` のような名前も候補になったが採用しなかった。

最終的には、

```text
auto
manual
role_fixed
```

とした。

この件から、

> 人間同士では過去から共有している用語の意味を自然に補完できても、AIはその単語が会話中で導入された局所的な文脈へ引っ張られることがある

という気づきも得た。

---

# 10. role_* を完全削除しなかった

新しい標準設定では、

```text
role_design
role_build
role_review
```

を削除し、自動選択を標準とした。

一方、既存利用者への後方互換としてrole固定方式そのものは残した。

優先順位は、

```text
1. --model-class
2. role_* が存在する場合
3. 自動選択
```

とした。

既存のローカル設定に `role_*` が残っている場合は、従来どおりrole固定方式で動く。

その場合は、

> 従来のモデル固定設定（role_*）で動作しています。role_* を削除すると、モデル自動選択になります。

という案内を出す。

これにより、既存環境を突然壊さず、新規標準だけをautoへ移行できるようにした。

---

# 11. --model-class は一時overrideとした

モデルを人間が明示的に指定したい場面も残した。

ただし、

> このfeatureは永久にstrong

のようなfeature固有設定は作らなかった。

`--model-class` は、その実行時だけのoverrideとした。

これは、

* 調査
* 比較実験
* 一時的なモデル変更
* 障害時の回避

などには必要だが、featureの正式な性質として保存する必要はないと判断したためである。

---

# 12. Gateへ何を残すか

今回、Gate recordのschemaを `gate_record/v2` とした。

新たに、

```text
feature_difficulty
worker_model_class
reviewer_model_class
model_selection
```

を記録する。

一方、次の情報は最初の実装では記録しなかった。

* 実際のモデル名
* prompt base level
* token使用量
* 金額
* 処理時間

Gateは実行ログをすべて保存する場所ではなく、

> なぜこのstageでこのモデルクラスが使われたのか

を後から追える程度の抽象度に留めることにした。

なお、`gate_record/v2` の `v2` はGate schemaのversionであり、スターターキットのV2やオートモードの世代を表すものではない。

---

# 13. 実AI検証の考え方

自動テストだけでなく、実際のAIを使ってeasy / hardの両端を確認することにした。

`normal` は従来既定値と同じクラス構成になるため、自動テストと既存featureでの互換確認を中心とした。

実AIでは、

* easy
* hard

を重点的に確認した。

---

# 14. easy検証featureの作り方

easy検証では、単に「easyと書かれたfeature」を作るのではなく、実際にeasyと考えられる仕様を用意した。

特徴は、

* 要求数が少ない
* ASCII数字を `*` に変えるだけ
* 入出力が明確
* エラー処理がほぼない
* 設計選択肢がほとんどない
* CLIやファイルIOなどを対象外にする

というものだった。

結果は、

```text
CP1 Reviewer = standard
feature_difficulty = easy

G1 Worker / Reviewer = cheap / cheap
G2 Worker / Reviewer = cheap / cheap
CP3 Worker / Reviewer = cheap / cheap
```

となり、人間の最終受け入れまで通過して `done` となった。

---

# 15. hard検証featureの作り方

hard検証では、単にREQ数を増やして「難しく見せる」方法は採らなかった。

小さいfeatureの中で複数状態が相互作用する仕様を作った。

扱う状態は、

* 通常テキスト
* シングルクォート文字列
* ダブルクォート文字列
* コメント

であり、さらに、

* エスケープ
* 改行
* 未閉じ文字列
* コメント内のクォート
* 文字列内のコメント記号

などが相互作用する。

また、難易度判定を文章に引っ張らせないため、

* 仕様本文に `hard`
* 「難しい」
* 「モデル選択試験」

といった説明は入れなかった。

featureの中身そのものだけを見てReviewerが判定するようにした。

---

# 16. hard CP1で人間側の仕様漏れを発見した

hard featureの最初のCP1レビューでは、

```text
feature_difficulty = hard
```

と判定された一方、仕様上の空白も1件検出された。

引用符付き文字列の中で生の改行が発生した場合、

* 文字列状態を継続するのか
* 改行で文字列を終了するのか

が未定義だった。

これはAIが勝手に補完せず、人間判断として返された。

人間側で、

> 改行を保持し、文字列状態を継続する

と決定して仕様へ追加した。

再度CP1を行ったところ、

* FINDING 0
* PASS / GO
* `feature_difficulty = hard`

となった。

この結果から、

* 難易度判定と仕様品質判定が分離して動くこと
* 仕様変更時には難易度を再判定すること
* hardだから自動的に止まるわけではないこと

を実AIで確認できた。

---

# 17. hard G1 / G2でstrongを使用した

hard featureでは、

```text
G1 Worker = strong
G1 Reviewer = strong

G2 Worker = strong
G2 Reviewer = strong
```

となった。

G1は1ラウンドでPASSした。

G2では、要求カバレッジ・観点カバレッジが、

```text
REQ 13 / 13
TV 19 / 19
```

となっていたにもかかわらず、strong Reviewerが境界ケースの不足を1件検出した。

内容は、

> 文字列内で `\` によってエスケープされる「次の1文字」が `\` 自身であるケースが、具体的なテストとして不足している

というものだった。

これは要求IDや観点IDの件数だけでは見えない穴だった。

同一G2内でWorkerがfixし、Reviewerが再確認して2ラウンドでPASSした。

この結果は、

> カバレッジ数値が100%でも内容に穴はあり得る

という点と、

> hard側でstrong Reviewerを使ったことが、少なくとも今回の実験では実際のレビュー価値につながった

という点を示した。

---

# 18. CP3でprompt base levelの意味を確認した

hard featureだからといって、CP3 Workerまでstrongにはならなかった。

結果は、

```text
CP3 Worker = standard
CP3 Reviewer = strong
```

となった。

これは、

```text
implement_feature の base level = 1
hard adjustment = +1
→ standard
```

に対して、

```text
review_stage の base level = 2
hard adjustment = +1
→ strong
```

となったためである。

CP3 Workerが作ったfeature単体テスト21件はすべてPASSした。

strong ReviewerによるCP3レビューでも新規FINDINGはなく、人間の受け入れ後 `done` となった。

これにより、今回の仕組みが単純な、

```text
easy → cheap
hard → strong
```

ではなく、

```text
featureの難しさ
+
作業そのものの基礎レベル
```

でモデルを変えていることを実AIで確認できた。

---

# 19. 最終回帰試験

easy / hardの検証featureを含めた状態で、

```bash
python -m pytest --basetemp=.pytest_tmp
```

を実行した。

結果は、

```text
294 passed
```

だった。

途中、通常の `python -m pytest` ではWindowsのpytest一時ディレクトリに対する `PermissionError: [WinError 5]` が発生した。

これはfeatureやモデル選択実装の問題ではなく、`--basetemp` を明示することで全件成功した。

---

# 20. 実AI検証後に出たコスト面の気づき

hard featureを実際に流したところ、strong Worker / Reviewerを複数回呼ぶため、セッション消費が大きかった。

実験では利用枠100%を超え、追加で約2ドル分を使用した。

この結果から、人間側では、

> 実際の仕事では、多くのfeatureがhard判定になるのではないか

という懸念が出た。

特に業務システムでは、

* 複数要求の相互作用
* 例外
* 境界条件
* 既存システムとの整合
* 複数の設計選択肢

が普通に存在するため、`hard` が珍しくない可能性がある。

---

# 21. 安いモデルへ寄せる場合にdifficultyを歪めない

コスト問題に対して、

> hardの判定条件を緩めてnormalを増やす

方法も考えられる。

しかし、人間側ではこの方向を採らない方がよいと考えた。

`feature_difficulty` は、

> featureそのものがどの程度難しいか

を表す値として残した方が意味があるためである。

コスト政策のために、本当はhardなfeatureをnormalと判定させると、難易度値の意味が曖昧になる。

そのため会社環境などで安いモデルへ寄せたい場合は、

```text
feature_difficulty
```

ではなく、

```text
base_level_*
```

側を調整する方が自然ではないか、という整理になった。

たとえば、

```text
base_level_create_function_design = 2 → 1
base_level_create_test_design = 2 → 1
```

とすれば、hard featureでも、

```text
G1 Worker = standard
G2 Worker = standard
```

へ下げられる。

一方、

```text
base_level_review_stage = 2
```

を維持すれば、hard Reviewerはstrongのまま残せる。

つまり、

> 作る側は一段安く、レビューは強くする

という運用も可能になる。

今回の実AI検証では、hard G2のstrong Reviewerが実際に境界ケースの不足を検出したため、少なくとも最初にコストを下げる候補としては、ReviewerよりWorker側のbase levelを下げる方が試しやすいと考えられた。

ただし、これは現時点では人間側の運用上の所感であり、スターターキット標準設定を変更する決定ではない。

会社環境では、この方向で調整を試す予定となった。

---

# 22. 実装中に見つかったテストの環境依存

モデル自動選択実装後、ローカル設定から `role_*` を削除した状態で全テストを実行したところ、既存テストが1件失敗した。

原因は、実リポジトリに対して `read_config()` を実行するテストが、

```text
role_build = cheap
```

の存在を前提としていたことだった。

新標準では `role_*` が存在しないため、本来この前提は成立しない。

しかし実装中は、`tools/feature_loop.local` に旧 `role_*` が残っていた。

`read_config()` がルール文書とlocal設定をマージした結果、旧キーが偶然存在し、壊れていたテストが通っていた。

人間がauto方式を使うためlocal設定から `role_*` を削除したことで、初めて問題が表面化した。

これはモデル自動選択本体のバグではなく、

> テストが利用者のlocal設定に依存していた

ことが原因だった。

テストを修正後、

```text
273 passed
```

となり、その後easy / hard実AI検証の30テストが加わって最終的に294件となった。

この出来事から、実AI検証だけでなく、

> 実際に利用者が設定を切り替えた状態でテストする

ことの重要性も確認できた。

別の修正候補として作業メモへ残している。

# 24. 今回採用しなかったもの

後から「なぜ無いのか」が分からなくならないよう、今回意図的に採用しなかったものをまとめる。

* モデル選択専用の追加AI呼び出し
* stageごとのfeature難易度再判定
* RETURN時の自動モデル昇格
* BLOCKED時の自動モデル昇格
* テスト失敗時の自動モデル昇格
* 失敗理由別のモデル分岐
* Reviewer最低standardなどの例外ルール
* 5段階以上の難易度
* 小数・0.5刻みの難易度スコア
* Worker専用 / Reviewer専用の新しいoverride
* featureごとの永続的モデル指定
* actual model名のGate記録
* token使用量のGate記録
* コストのGate記録
* durationのGate記録
* prompt base levelのGate記録

これらが不要であると確定したわけではない。

必要性が実際に発生するまでは追加しない、という判断である。

# 25. 現時点の考え方

今回のモデル自動選択は、モデルを最適化する仕組みではない。

現在の役割は、

```text
明らかに簡単な仕事でstrongを使わない
明らかに難しい仕事でcheapを使わない
```

程度の大きなミスマッチを避けることである。

そのため、

* 難易度分類は3段階
* 判定はCP1に相乗り
* 計算式は単純
* 例外を増やさない
* 実行失敗からモデル能力を推測しない
* コスト政策はbase level側で調整する

という構成になった。

今後、実際の利用で問題が出た場合にだけ追加の仕組みを検討する。

現時点では、

> モデル選択を賢くしすぎない

こと自体を、設計上の重要な方針としている。
