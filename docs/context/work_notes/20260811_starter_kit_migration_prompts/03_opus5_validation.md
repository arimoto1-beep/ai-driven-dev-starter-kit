# Opus 5による移行影響チェックpromptの検証

## 検証対象

過去にmigration方式を検討するために用意していたfixtureを使用した。

```text
A: 2632a9dd6e1060ebaeb6ca149e73680edc384dab
B: b7342ec19e975c9a4304a0c39648fc64a32a1e39
C: 1af7dc8643b292e5a158c2bace831d9dfb33bcbb
```

AはBとCの共通祖先として使用した。

過去のmigration調査結果やwork noteを正解として参照させず、A/B/Cの実資産だけから独立して分析するよう指示した。

検証にはOpus 5を使用した。

## 読み取り専用で実行した

Opus 5の報告では、

* checkout
* switch
* reset
* restore
* stash
* merge
* rebase
* cherry-pick
* commit
* push
* branch作成
* tag作成

は行われていない。

3-way mergeの確認もスクラッチ上のコピーで実施され、リポジトリとworktreeは変更されなかった。

## A/B/Cの機械的確認

報告では次が確認された。

| 項目        |  結果 |
| --------- | --: |
| Aのファイル数   | 111 |
| Bのファイル数   | 111 |
| Cのファイル数   | 142 |
| A→B変更ファイル |   4 |
| A→C追加     |  31 |
| A→C変更     |  43 |
| A→C削除     |   0 |
| A→C一致     |  68 |

利用者が変更した4ファイルは、

```text
AGENTS.md
README.md
prompts/implement_feature.md
prompts/review_feature_source.md
```

だった。

## 利用者意図は13件に分解された

Opus 5はA→Bの変更を13件の利用者固有意図へ分解した。

最終判定は次のとおりだった。

| 判定   | 件数 |
| ---- | -: |
| 吸収済み |  4 |
| 部分吸収 |  3 |
| 未吸収  |  4 |
| 衝突   |  2 |
| 判断不能 |  0 |
| 合計   | 13 |

13件すべてがいずれかの状態へ追跡され、未追跡itemはなかった。

## 総合判定はSTOPだった

総合判定は `STOP` となった。

主な理由は、

* 人間判断が必要な意味上の衝突が2件
* 新版に受け皿が存在しない利用者意図が4件
* 単純mergeでは見つからないsilent lossリスク

が存在したためだった。

これは「migrationできなかった」という意味ではない。

人間判断なしに移行実行へ進めるべきではない状態を1段目で検出できた結果である。

## 衝突として検出されたもの

代表的な衝突は2件だった。

### 外部ライブラリの扱い

利用者側では、

> 原則標準ライブラリだが、理由と影響を示して人間承認を得れば外部ライブラリを追加できる

という運用を追加していた。

新版では、外部ライブラリを追加しない方向のルールとtask手順が存在した。

単純に厳しい新版を採用せず、人間判断が必要な衝突として扱われた。

### 軽微修正のAI裁量

利用者側では、

> 設計へ影響しない軽微な修正ならAIが必要と判断して事前承認なしで変更してよい

という裁量を追加していた。

新版では、

> 「軽微」かどうかをAIが単独判断しない

という方向へ変更されていた。

さらにprojectからcoreを緩和できない構造になっているため、単純な再配置では解決できないことも検出された。

## 最大の発見はGit mergeと意味のmigrationが違うことだった

今回特に重要だったのは、3-way mergeの結果だった。

利用者が変更した4ファイルのうち、

```text
AGENTS.md
```

だけがGit上のmerge conflictになった。

残り、

```text
README.md
prompts/implement_feature.md
prompts/review_feature_source.md
```

は無警告でmergeできた。

Gitだけを見ると3ファイルは正常に移行できたように見える。

しかし新版では各ファイルの責務が変わっていた。

たとえば、

* `README.md` はAIルールの正本ではない
* task promptはcore/projectを再定義する場所ではない
* `AGENTS.md` は詳細ルール本体ではなく薄い入口になった
* 通常taskから `AGENTS.md` を読む導線が外れた

という変化がある。

そのため、

> テキストは残っているが、AIのルールとして機能しない

状態が発生する可能性がある。

promptはこれをsilent lossリスクとして検出した。

## ruleからtaskまでの接続確認も機能した

利用者が追加した、

> レビュー結果へ影響範囲を記載する

という意図について、新版側に十分な受け皿が存在するか調べた。

単に近いruleを探すだけではなく、

* review promptの出力slot
* template
* 人間確認への接続

まで確認した結果、未吸収と判定された。

一方、

> 確認できない場合に推測で「影響なし」としない

という一般原則に近い考えは新版にも存在したが、前提となる影響範囲出力slotがないため、完全吸収ではなく部分吸収とされた。

## 新版作者の履歴も区別できた

新版にはwork notes機能と、スターターキット作者自身のwork noteが存在していた。

Opus 5は、

* work noteのrule
* prompt
* template
* 置き場README

などの仕組み側と、

* 新版作者自身の過去work note

を分けた。

作者自身の履歴は利用者環境へ持ち込まない対象として分類された。

## 検証結果の評価

1段目promptで確認したかった主要点は機能した。

特に、

* 利用者意図を意味単位へ分解する
* 全itemを最後まで追跡する
* 部分吸収を完全吸収と混同しない
* 意味上の衝突を人間へ戻す
* Git mergeで見えないsilent lossを検出する
* ruleだけでなくtaskへの到達性を見る
* 新版作者の履歴をmigration対象から除く

ことを確認できた。

このため、今回のfixtureに対しては、1段目promptは実用可能と判断した。
