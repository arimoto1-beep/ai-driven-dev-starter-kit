# 今回得た知見と次への申し送り

## 1. migrationの単位はファイルではなく意味

今回の検証で最も強く確認できたのは、

> ファイルを正しくmergeすることと、利用者の意図を正しくmigrationすることは別

という点だった。

新版ではファイルの責務そのものが変わることがある。

そのため、

```text
利用者が書いた行が残っている
```

だけでは不十分である。

見るべきなのは、

```text
利用者が守ろうとした意味が、
新版の正しい責務へ移っているか
```

である。

## 2. merge conflictがない方が危険な場合もある

通常はmerge conflictが危険に見える。

しかし今回、実際に危険だったのは無警告でmergeできる変更だった。

Gitは同じ行付近を変更していなければmergeできる。

しかし、

* 正本が移動した
* AIの読み込み導線が変わった
* そのファイルの役割が変わった

ことまではGit conflictとして検出しない。

したがってmigrationチェックでは、

> conflictが発生したか

だけでなく、

> merge後もその記述が意味を持つか

を確認する必要がある。

## 3. 「消えた」と「失われた」は違う

旧ファイルから文章が消えても、新版の別のruleやpromptへ意味が移っていれば失われてはいない。

逆に文章が残っていても、AIが読まなくなれば実質的に失われている。

migrationではテキスト保存ではなく意味保存を見る。

## 4. 吸収済み判定には強さが必要

同じ方向のルールでも、

```text
必ず行う
```

と、

```text
必要に応じて行う
```

は同じではない。

吸収判定では、

* 拘束力
* 適用範囲
* 発動条件
* 頻度

を見る必要がある。

部分吸収という状態を持たせたことは有効だった。

## 5. ruleの存在だけでは機能しているとは言えない

AI駆動開発では、

```text
rule
 ↓
prompt
 ↓
template / output
 ↓
review
 ↓
human
```

のような接続がある。

rule本文だけ存在しても、taskが読まない、出力slotがない、templateに反映されないのであれば運用上は届かない。

migrationでは責務だけでなく導線も確認する必要がある。

## 6. 衝突を見つけるAIと、決める人間を分ける

migration checkの仕事は、

> 何が衝突しているかを見つけること

まででよい。

新版が厳しいから新版を採る、利用者側が明示変更だから利用者側を採る、とAIだけで決定しない。

特にcoreの考え方と利用者固有ルールが正面から衝突する場合は、人間が方針を選ぶ必要がある。

STOPは失敗ではない。

## 7. 作者の履歴は新版機能ではない

work notesのように、新版機能を開発した際の作者自身の記録がリポジトリに存在する場合がある。

migrationでは、

* 機能を成立させるrule / prompt / template / README
* 作者自身の過去の検討履歴

を区別する。

新版に存在するからという理由だけで後者まで利用者環境へコピーしない。

## 8. promptでは目的が重要だった

今回のpromptは手順をかなり細かく書いた。

ただし、検証で効いた可能性が高いのは、上位に、

> 利用者固有の意図をsilent lossさせない

という目的を置いたことだった。

実際、Opus 5は指示された差分分類だけで終わらず、

* 3-way mergeならどう見えるか
* AIの読み込み導線が変わっていないか
* ruleからprompt/templateへつながるか

まで確認した。

複雑なAI作業では、作業手順だけでなく、

> 何を守るためにこの作業をするのか

を明示することが重要と考える。

## 9. 用語はもう少し分けた方がよい可能性がある

Opus 5の報告では、A→BとA→Cの両方で変更された4ファイルを、

> 衝突対象

と表現した箇所があった。

後半では別に、

* Git上のmerge conflict
* 利用者意図と新版方針の意味上の衝突

を扱っている。

同じ「衝突」という言葉が複数の意味で使われる可能性がある。

公開promptでは、たとえば、

```text
双方変更:
A→BとA→Cの双方で変更された

Git conflict:
3-way mergeでGitが衝突と判定する

意味上の衝突:
利用者意図と新版方針が両立しない
```

と分ける案がある。

これは今回の検証から出た改善候補であり、現時点では正式決定していない。

## 10. 次の移行実行promptへの申し送り

2段目では1段目の分析結果を入力として使う。

移行実行promptが独自に利用者意図を再解釈し直すより、

* 維持する利用者意図
* 新版で吸収済みのもの
* 新版へ追加・再配置するもの
* 人間判断結果
* 移行対象外

を明示的に引き継いだ方がよい。

また、単純なCの上書きやgit mergeをmigration方式にはしない。

U-item単位で意味を新版の正しい責務へ再配置する。

## 11. 移行後チェックpromptへの申し送り

3段目では、実行prompt自身の自己評価だけに依存しない。

少なくとも、

* 利用者固有意図のsilent loss
* 新版必須ルールの反映漏れ
* 旧版の古いルールの残存
* 新旧ルールの矛盾
* 二重管理
* core/project/taskの責務逆転
* AI権限の意図しない変更
* context履歴の不要な移行
* ruleとtask導線の断絶

を独立して確認する。

人間判断事項が未解決のまま隠れていないことも確認する。

## 12. 今のところ専用migration機構は作らない

現時点では、

```text
影響チェック
 ↓
移行
 ↓
独立チェック
```

をpromptで提供するところまでを目標とする。

この方式を実際に使った結果、

* 毎回旧版Aを特定するのが難しい
* 同じ対応表を毎回作っている
* 手作業での版管理が負担
* promptだけでは再現性が足りない

といった問題が出た場合に、

* VERSION
* manifest
* CLI
* migration helper

などへ昇格する。

先に大きな仕組みを作ることはしない。
