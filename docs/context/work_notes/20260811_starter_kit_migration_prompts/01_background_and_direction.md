# 背景と今回の方向

## 既存利用者への新版反映が次の問題になった

スターターキット本体では、core、project、promptなどの役割を整理しながら継続的に変更している。

本体を変更するだけなら、新版の資産をそのまま更新できる。

しかし、すでに旧版を使っている利用者環境には、その利用者自身が追加・変更したルールが存在する可能性がある。

新版を単純に上書きすると、その利用者固有の変更を消す可能性がある。

一方で、古い利用者ファイルをそのまま残せばよいとも限らない。

新版では、

* 正本の場所
* ファイルの責務
* AIが読む導線
* core / project / taskの関係
* promptやtemplateの役割

そのものが変わる場合があるためである。

このためmigrationでは、単純なファイルコピーやGit merge以上の判断が必要になる。

## 以前からA/B/C比較を考えていた

migration方法として、以前から次の3状態を使う案を検討していた。

```text
A: 利用者が導入した時点の旧スターターキット
B: 利用者がカスタマイズした現在環境
C: 新版スターターキット
```

A→Bを見ると、利用者が旧版へ何を追加・変更したかが分かる。

A→Cを見ると、スターターキット本体が新版で何を変更したかが分かる。

この2つを別々に見た上で、利用者固有の意味を新版の構造へ移す。

BとCだけを比較すると、

* その差が利用者変更なのか
* 新版側の変更なのか
* もともと存在していた差なのか

を判断しにくい。

そのためAを基準にする方式を維持した。

## 最初はmigration機能化も考えた

既存環境を更新するために、

* VERSION情報
* migration manifest
* 専用CLI
* 自動変換機構

などを用意する方向も考えられる。

ただし、現時点では何が本当に必要なのか分からない。

先に仕組みを大きくすると、まだ実際には困っていない問題まで実装する可能性がある。

そこで今回は、より小さく始めることにした。

## 3段階promptとして提供する

今回の方向は次の3段階である。

```text
1. 移行影響チェック
   ↓
2. 移行実行
   ↓
3. 移行後チェック
```

1段目では変更しない。

利用者固有の意図、新版での吸収状況、衝突、人間判断事項を整理する。

2段目はその結果を使って実際に新版構造へ再配置する。

3段目は別の視点から、silent loss、反映漏れ、矛盾、二重管理などを確認する。

これなら、専用ツールを作らなくてもAIの反復で自然に収束させられる可能性がある。

## 最初のチェックだけは検証したいと考えた

3本すべてを作ってから試すのではなく、最初の影響チェックpromptだけは実際に確認することにした。

理由は、最初の分析が正しければ、その後の移行実行はかなり機械的にできると考えたためである。

逆に最初の分析で、

* 利用者変更を見落とす
* 新版で吸収済みなのに未吸収と判断する
* 部分吸収を完全吸収と判断する
* 衝突を見逃す

と、その後の作業全体がずれる。

そのため1段目を最初の品質ゲートとした。

## 作業手順以上に目的を重視した

今回の会話で、人間側から、

> AIの作業で重要なのは目的で、目的がしっかりしていればそうそう外さない印象がある。逆に目的がなく、作業手順だけだと不安

という考えが出た。

これは今回のprompt設計にも反映した。

単に、

```text
A→Bを比較する
A→Cを比較する
差分を分類する
```

だけではなく、

> 利用者が旧スターターキットへ加えた意図を、新版への移行でsilent lossさせない

ことを上位目的とした。

詳細な手順は、この目的を達成するための手段として扱う。

AIが途中で想定外の構造を見つけた場合にも、目的へ戻って追加調査できることを期待した。
