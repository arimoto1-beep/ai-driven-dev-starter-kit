# スターターキット既存環境向けmigration promptの検討

## 目的

既存のAI駆動開発スターターキット利用環境を新版へ移行するときに、利用者が追加したルールや判断意図を気づかないまま失わない方法を整理する。

今回は専用migrationツールを実装するのではなく、

1. 移行影響チェック
2. 移行実行
3. 移行後チェック

の3段階promptとして提供する方向を試す。

特に最初の「移行影響チェック」が正しければ、後続作業も大きく外れにくいと考え、最初にこのpromptだけをfixtureへ適用して動作確認した。

## 状態

進行中

## 現在地

* migrationは専用CLIや自動変換機構を最初から作り込まず、3段階のpromptとして提供する方向にした。
* 1段目の「移行影響チェックprompt」を作成した。
* promptの中心目的を「ファイル差分を分類すること」ではなく、「利用者固有の意図をsilent lossさせないこと」とした。
* 過去にmigration検討用として作成したA/B/C fixtureを使い、Opus 5へ過去の正解を与えず独立調査させた。
* 1段目の検証では、利用者固有の意図13件をすべて追跡できた。
* 判定は、吸収済み4件、部分吸収3件、未吸収4件、衝突2件、判断不能0件だった。
* 総合判定は `STOP` だったが、これは移行前に人間判断が必要な衝突や未吸収項目を検出できた結果であり、promptの失敗ではない。
* Gitの3-way mergeだけでは検出できないsilent loss候補も検出できた。
* 特に、利用者変更4ファイル中3ファイルはGit上無警告でマージできる一方、新版でファイルの責務や読み込み導線が変わったため、テキストが残ってもルールとして機能しない可能性を検出した。
* 1段目のpromptは実用可能と考えている。
* 2段目の移行実行prompt、3段目の移行後チェックpromptは未作成。

## 決定事項

* migrationは、まず3段階promptとして提供する。
* 構成は「移行影響チェック → 移行実行 → 移行後チェック」とする。
* 最初から専用CLIや大きなmigration機構は作らない。
* まず1段目だけを実地検証する。
* migrationで最優先する目的は、利用者固有の意図のsilent lossを防ぐこととする。
* A/B/Cは次の意味で扱う。

  * A: 利用者が導入した時点の旧スターターキット
  * B: 利用者がカスタマイズした現在環境
  * C: 移行先の新版スターターキット
* A→Bから利用者固有の意図を抽出し、A→Cから新版側の変更を確認する。
* BとCの単純比較やGit mergeの成否だけで移行可否を判断しない。
* GitHub側にはmigrationツールそのものではなく、実際に試して得た知見をwork noteとして残していく。
* prompt本体はnote等で公開できる形を想定する。

## 未決事項

* 2段目の移行実行promptの具体的な入力・出力形式。
* 3段目の移行後チェックpromptの具体的な終了条件。
* 1段目promptで使用した「衝突」という語について、

  * A→BとA→Cの双方で変更されたファイル
  * Git merge conflict
  * 意味上の衝突
    をより明確に用語分離するか。
* 実際の利用者環境で繰り返し使った結果、VERSION、manifest、CLI等が必要になるか。
* 今回のfixtureは旧版からキット32への移行を対象としており、最新版への実移行を検証したものではない。

## 次に行うこと

1. 今回の検証で得た知見を1段目promptへ必要に応じて補正する。
2. 1段目の出力を入力として使える移行実行promptを作成する。
3. 移行後環境を独立して検査する移行後チェックpromptを作成する。
4. 必要に応じて3段階を実際のmigration fixtureで通して確認する。
5. promptを実際に利用して不足が見えた場合だけ、専用機構への昇格を検討する。
