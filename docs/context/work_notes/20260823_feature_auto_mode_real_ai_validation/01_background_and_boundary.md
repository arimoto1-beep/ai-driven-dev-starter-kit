# 背景と人間／AI境界の整理

## 背景

feature開発の自動化では、
仕様、設計、テスト設計、実装、レビューを
AIが連続して進められるようにしたい。

一方で、自動化範囲を広げるほど、
人間がどこで内容を確認し、
どの時点からAIへ製造を任せるのかを
明確にする必要がある。

今回特に問題になったのは、
人間による仕様承認の位置だった。

## 人間側の仕様とAI製造を分ける

今回の整理では、

`20_spec.md`

を人間側で確定する仕様とした。

作成そのものにはAIを利用してもよいが、
最終的に何を作るのかを決める責任は人間側に置く。

そのため工程の境界を、

`20_spec.md`
→ CP1
→ G1
→ G2
→ CP3

とした。

CP1より前が人間側、
CP1より後がAI製造側という考え方である。

## なぜ設計生成前にHuman Gateが必要なのか

AIは仕様に空白があっても、
もっともらしい内容を推測して
先へ進められることがある。

その推測が、

- 設計
- フロー
- テスト計画
- 実装
- テスト

まで一貫して反映されると、
下流成果物同士はきれいに整合する。

しかしその内容が、
人間が実際に承認した仕様とは限らない。

しかも下流が整合しているほど、
後から人間が
「ここは最初から決まっていたのか」
「AIが途中で補ったのか」
を見分けにくくなる。

そのため、
AI製造に入る前に仕様そのものを一度確定する境界が必要と考えた。

## Spec Review

人間が仕様を承認する前に、
AI自身にも仕様をレビューさせる。

このレビューは製造工程とは独立して実行できるようにした。

確認対象は、

- ID
- 検証可能性
- 矛盾
- 曖昧さ
- 未決事項
- 入出力
- 異常系
- 境界条件
- 下流で独自判断が必要になる空白
- 対象範囲

など。

AIが解決できる機械的な問題は、
人間へ渡す前にできるだけ発見させる。

ただし、
業務判断や仕様判断そのものを
AIが黙って補完することは目的にしない。

## CP1

Spec Reviewで問題がない状態になった後、
人間がCP1で仕様を承認する。

このHuman Gateは、
単なる工程上のチェックポイントではない。

「ここから先は、この仕様をbaselineとして
AIが製造してよい」

という境界である。

PJ上位者や顧客など、
runner外で必要な確認がある場合も
この承認前に完了していることを想定する。

## baselineの保護

承認時点の `20_spec.md` は
hashで識別できるようにした。

承認後に仕様が変更されていた場合、
古い承認を使ってAI製造へ進まないようにする。

また、AI製造開始後に仕様不足が判明した場合も、
AIがその場で補完して先へ進むのではなく、
人間側の仕様工程へ戻す考え方とした。

## 今回確認したかったこと

今回の実AI試験では、
設計思想だけでなく実際の挙動として、

- Spec Reviewだけを単独実行できるか
- CP1承認前にAI製造が始まらないか
- CP1承認後に初めてG1へ進むか

を確認することにした。
