# 検証結果と、見つかった不足

## 検証前の runner が扱えていた範囲

先に結論を書く。**修正フローは実装されていなかった。**

`resolve_action()` は、**全stage横断で最新の Gate記録の front matter だけ**を読む。
成果物ファイルの現在の内容は見ていない。

唯一の例外が `spec_hash` による Manufacturing Preflight だが、これは
**製造 stage の Worker を起動する直前**にしか走らない。
`done` に到達した feature では Worker を起動しないため、照合そのものが行われない。

その結果、4つの検証すべてで同じことが起きた。

| 変更した工程 | runner の反応 |
|---|---|
| CP3（実装コード） | `次の動作: done` |
| G2（試験観点） | `次の動作: done` |
| G1（設計・処理方式） | `次の動作: done` |
| CP1（仕様） | `製造開始条件: 満たしていない` と表示しつつ `次の動作: done` |

---

## 検証1: CP3だけを変更

人間が `src/.../ascii_digit_masker.py` の実装を直接書き換えた
（for ループ → ジェネレータ式）。仕様・設計・テスト設計は無変更。

| 確認項目 | 結果 |
|---|---|
| runner がこの状態を表現できるか | **できない**。`次の動作: done` のまま |
| CP3 Worker から再実行できるか | **できない**。完成済み feature に Worker 再入口が無い |
| `--review-current CP3` が使えるか | **使える**。Gate記録 0008 を新規作成、`supersedes: 0007` |
| 古い CP3 PASS が完成扱いにならないか | **なってしまう**（不足） |
| 新しい Gate履歴が追加されるか | **される**。0007 は無変更のまま残った |

通常実行の出力はこうだった。

```text
完了しました。
[7] CP3  PASS / GO
```

`--review-current CP3` を実行すると、新しい記録 0008 が作られ、状態は
`await_human`（人間の受け入れ判断待ち）へ戻った。**ここは期待どおり。**

### 予想外だったこと: Reviewer が「変更されていない」と書いた

CP3 Reviewer は Gate記録の作業後報告へこう書いた。

> 実装・テストの内容は `gates/0007_...` から変更されておらず（`git status` で untracked のまま変化なし）

**実際には人間が書き換えていた。**

成果物そのものは仕様・テスト計画に照らして正しくレビューされ `PASS` だったので、
判定自体は妥当である。しかし「変更されていない」という記述は事実と異なった。

原因は、**runner が「何が変わったか」を Reviewer へ渡していない**こと。
Reviewer には変更の有無を確認する材料がなかった。

## 検証2: G2のテスト設計を変更

`23_test_plan.md` へ TV-007（改行・タブ・空白文字の保持）を追加した。
これは REQ-002 の範囲内であり、仕様そのものは変更していない。
`24_review_checklist.md` のテストレビュー節にも対応行を追加した。

| 確認項目 | 結果 |
|---|---|
| G2変更を runner が認識できるか | **できない**。`次の動作: done` のまま |
| 以前の G2 PASS をそのまま使わないか | **使ってしまう**（不足） |
| 以前の CP3 PASS をそのまま使わないか | **使ってしまう**（不足） |
| G2 Reviewer を再実行できるか | **できる**（`--review-current G2`） |
| G2 PASS 後、CP3 Worker/Reviewer へ進めるか | **進めた**。自動でカスケードした |
| 新しいテスト観点がテストコードへ反映されるか | **反映された**（6件 → 8件） |

### 既存機能で代用できたこと: カスケードは既に動いていた

`--review-current G2` が G2 の新しい PASS 記録を作ると、それが
「全stage横断で最新の1件」になる。`resolve_action` は最新記録の gate から
次 stage を決めるため、そのまま CP3 へ進む。

つまり**下流の再実行そのものは、既存の仕組みで動いていた。**
足りなかったのは「変わったことに気づく」部分だけだった。

実際の Gate記録の連鎖はこうなった。

```text
   7  CP3   PASS                    ← 元の完成状態
   8  G2    PASS                    ← --review-current G2（0003 を supersede）
   9  CP3   BLOCKED (guard_violation)
  10  CP3   PASS                    ← --retry-blocked（0009 による再実行）
```

テストコードには `test_tv007_whitespace_characters` が追加され、
pytest は 6 passed → 8 passed になった。

### 予想外によかったこと（1）: Reviewer が人間の編集ミスを検出した

`23_test_plan.md` の TV-007 行に生の改行・タブが混入し、Markdown テーブルが
壊れていた（`01_verification_method.md` の「ミス（2）」）。

G2 Reviewer はこれを F-001 として検出し、`IN_PROGRESS` にした。

**人間が直した成果物を、AI側が機械的にではなく内容として点検した例である。**

### 予想外によかったこと（2）: Reviewer が stale を言語的に検出した

同じ G2 Reviewer は、Gate記録へ自分から次を書いた。

> なお、現在受け入れ済みのCP3（`gates/0007`）はTV-001〜006の6件にしか対応しておらず、
> TV-007分の実装・テストは未反映です。G2がこの後PASSした場合、CP3の再実行が必要になる点を
> Gate記録の作業後報告に申し送りました。

**runner が検出できなかった stale を、AI は言語的に検出していた。**

ただしこれは申し送りであって、機械的な停止ではない。
Reviewer が気づかなければ素通りする。仕組みとしては当てにできない。

### 再現した既知の問題

CP3 Worker が範囲外の `src/cli_mask_rework/__init__.py` を作成し、
`BLOCKED(guard_violation)` になった（run_seq 9）。

これは `20260823_feature_auto_mode_real_ai_validation` の未決事項
「新規app scaffold の責務が未整理」と同じ事象で、修正フロー固有の問題ではない。
`--retry-blocked` で復旧し、CP3 PASS（条件付きGO）まで到達した。

## 検証4: CP1の仕様を変更

`20_spec.md` の REQ-001 を変更した（置換文字 `*` → `#`）。
これは期待動作そのものが変わる仕様変更である。

**これが最も深刻な形の不足だった。**

```text
$ python tools/feature_runner.py --feature cli_mask_rework/ascii_digit_masker --status
  製造開始条件: 満たしていない
    現在の仕様書に一致する人間承認済み baseline がありません。
      承認時: 18e7b3fb600c
      現在  : 0b24f9817bf3
次の動作: done (stage=CP3)

$ python tools/feature_runner.py --feature cli_mask_rework/ascii_digit_masker
完了しました。
exit=0
```

**runner 自身が「製造開始条件を満たしていない」と表示しながら、
同じ feature を「完了しました」と報告し、終了コード 0 を返した。**

期待していた流れ（Spec Review → CP1 Human Gate → 人間による再承認）には、
そもそも入らなかった。仕様変更が下流へ伝わる経路が動いていなかった。

| # | 確認事項 | 検証前の結果 |
|---|---|---|
| 1 | 上流変更時、下流の古い PASS がどう扱われるか | **そのまま有効として扱われる** |

| 6 | 人間が直接修正しても整合性を回復できるか | `--review-current` で回復できる。ただし人間が気づく必要がある |
| 7 | 古い Gate記録を変更せず新規 Gate を残せるか | **できている**。既存の強み |
| 8 | G1 / G2 変更で stale を安全に検出できるか | **できない** |

## 不足の整理

| # | 現在の挙動 | 期待する挙動 | 何が不足か | なぜ問題か |
|---|---|---|---|---|
| 1 | 成果物を変更しても気づかない | 変更された stage を検出する | stage 成果物の baseline 記録が無い | 古い判定が完成扱いのまま残る |
| 2 | `done` を返して終了コード 0 | 完成扱いにせず停止する | `done` 判定に成果物の状態が入っていない | 未検証の成果物が「完成」として扱われる |
| 3 | 完成済み feature に Worker 再入口が無い | AIに作り直させる操作がある | `--rework` に相当する操作 | Reviewer だけでは「作り直し」ができない |
| 4 | 仕様変更が下流へ伝わらない | CP1 へ戻り、人間の再承認を要する | `done` 経路に Preflight が無い | **承認境界が実質的に無効化される** |

**4番目が最も重い。** CP1 は人間側の仕様と AI 製造の境界であり、
そこが素通りするということは、承認済みでない仕様に基づく成果物が
「完成」として残るということである。
