# 完成済み feature を後から修正するフローの検証

## 目的

feature auto mode は、新規 feature を CP1 → G1 → G2 → CP3 と作り切るところまで実AIで確認済み（`20260823_feature_auto_mode_real_ai_validation`）。

今回確認したのは、**その後**である。

完成した feature の成果物を後から変更したとき、

- 仕様・期待動作を変えた → CP1 へ戻る
- 設計・処理方式を変えた → G1 へ戻る
- 試験項目・試験観点を変えた → G2 へ戻る
- 実装コード・テストコードを変えた → CP3 へ戻る

という扱いが、**現在の runner で本当に実現できているか**を実地で確認する。

重要なのは「誰が変更したか」ではなく「どの工程で決める内容を変更したか」である。
AIが生成した成果物を人間が直接変更することも許容する。

**「実装済みのはず」と仮定せず、現状確認 → 実地検証 → 不足確認 → 修正の順で進めた。**

## 現在地

検証の結果、**修正フローは実装されていなかった**ことが分かった。

runner は最新 Gate記録の front matter しか見ておらず、成果物ファイルの現在の内容を見ていない。
そのため4つの検証すべてで、成果物を変更しても `次の動作: done`（完了）のままだった。

不足を補うため、次を実装した。

1. stage 成果物の内容ハッシュ（`artifacts_hash`）を Gate記録へ残し、次回照合する
2. 通過後に変更された stage を検出したら、完了扱いにせず停止する
3. 通過済み stage を Worker からやり直す `--rework <stage>` を追加する

実AIでの確認も行い、Reviewer が `artifacts_hash` を正しく転記することを確認した。

自動テストは 224 件すべて成功している。

## 決定事項

### 戻り先は「変更した内容の工程」で決める

「誰が変更したか」では決めない。人間が直接直した場合も同じ扱いとする。

### 検出はするが、自動では再開しない

変更を検出しても runner は自動で再実行しない。停止して人間へ渡す。

理由は、**Worker を無条件に再実行すると人間が直した内容を上書きするおそれがある**ため。
「人間の修正を維持したいのか、AIに作り直させたいのか」は runner に判断材料がない。
`BLOCKED` を自動再開しないのと同じ考え方を適用した。

### `artifacts_hash` は runner が計算し、runner が照合する

既存の `spec_hash` と同じ方式を採用した。AIは渡された値を転記するだけで、計算しない。
**この方式を選んだのは、既存の考え方を増やさないためである。**

### 過去の Gate記録に `artifacts_hash` が無い場合は停止しない

「判定不能」として扱う。安全側へ倒すと既存 feature がすべて停止してしまうため、後方互換を優先した。
**この判断の副作用は「未決事項」に記載している。**

### 仕様 stage（CP1）は `artifacts_hash` を使わない

`20_spec.md` の baseline を成立させるのは Gate の `PASS` ではなく**人間の承認**である。
既存の `spec_hash` と仕様承認で判定し、判定経路を二重にしない。

### 3つの復旧操作の用途を分ける

| 操作 | 用途 |
|---|---|
| `--retry-blocked` | `BLOCKED` からの復旧 |
| `--review-current <stage>` | 現在の成果物の再確認（Worker を起動しない） |
| `--rework <stage>` | 通過済み stage のやり直し（Worker から作り直す） |

`--retry-blocked` を完成後の修正へ流用しない。最新が `BLOCKED` でなければ拒否される仕様は維持した。

## 未決事項

### Reviewer が `artifacts_hash` を書き落とした場合、検出が効かなくなる

現在の実装では、`artifacts_hash` が空の記録は「判定不能」として扱い停止しない。
これは既存 feature の後方互換のための判断だが、**新しい記録で Reviewer が転記を忘れた場合も同じ扱いになる**。

`spec_hash` は「値が違えば製造が止まる」ため安全側に倒れるが、`artifacts_hash` は
「値が無ければ検出が効かない」ため安全側に倒れない。

`schema: gate_record/v2` を導入して「v2 なのに値が無ければ異常」と扱う案があるが、
今回は採用しなかった（`03_rejected_options.md` を参照）。整理するかは未決。

### `stage_cp3_artifacts` の既定値をどこまで広げるか

既定は feature 1件ぶんの実装ファイルとテストファイルだけにした。
結合試験や entrypoint テストを CP3 の成果物として扱うプロジェクトでは検出漏れになる。

ディレクトリ単位へ広げると、同じ app の別 feature を変更しただけで「変更あり」と判定される。
**この二択はプロジェクトの feature 分割方針に依存するため、設定で選べる形にとどめた。**

### 新規app scaffold の責務（前回からの持ち越し）

検証中、CP3 Worker が範囲外の `src/<app>/__init__.py` を作成し `BLOCKED(guard_violation)` になった。
`20260823_feature_auto_mode_real_ai_validation` の未決事項と同じ事象で、修正フロー固有の問題ではない。
今回は解決していない。
