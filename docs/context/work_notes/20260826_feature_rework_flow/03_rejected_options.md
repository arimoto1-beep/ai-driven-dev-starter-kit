# 検討したが採用しなかった案

## 1. `--retry-blocked` の意味を広げて修正フローへ流用する

**却下。**

`--retry-blocked` は「`BLOCKED` した stage を Worker から再実行する」という
復旧専用の操作である。完成後の修正はまったく別の用途である。

流用すると、次のどちらも失われる。

- 「最新が `BLOCKED` のときだけ受け付ける」という誤操作防止
- 「BLOCKED は自動再開しない」という設計意図

**用途の違う操作を1つのフラグへ寄せると、フラグの意味が説明できなくなる。**

なお検証の結果、現状の `--retry-blocked` は完成済み feature に対して
正しく拒否されることを確認した。流用の余地はそもそも無かった。

## 2. `--review-current` だけで済ませ、新しい操作を追加しない

**却下。**

`--review-current <stage>` は実際に有効で、人間が直した成果物を
Worker なしで再判定でき、下流のカスケードも動く（`02_findings.md`）。

しかし `--review-current` は **Reviewer だけ**を起動する。
「G1 の設計をAIに作り直させたい」場合の入口が無い。

完成済み feature では `resolve_action` が `done` を返すため、
Worker を起動する経路そのものが存在しなかった。

そのため `--rework <stage>` を追加した。

## 3. stale を検出したら自動で再実行する

**却下。**

利用者の期待としては「G2 を直したら G2 から再実行してほしい」が自然に見える。
しかし runner には、**次のどちらをしたいのかを判断する材料が無い。**

| 状況 | 正しい動作 |
|---|---|
| 人間が成果物を直した。その内容を維持したい | Worker を起動しない |
| AIに作り直させたい | Worker を起動する |

自動で Worker を起動すると、前者の場合に**人間が直した内容を上書きする。**

`BLOCKED` を自動再開しない設計と同じ理由で、停止して人間に選ばせる形にした。

## 4. runner が Gate記録へ後から `artifacts_hash` を書き込む

**却下。**

Reviewer が転記し忘れるリスクを避けるなら、runner が自分で書けばよい。

しかしそうすると、1つの Gate記録に対して
**「Reviewer が書いた部分」と「runner が書いた部分」が混在**する。

- `recorded_by` が事実と合わなくなる
- 「`PASS` を書いた時点で immutable」という境界が曖昧になる
- 既存の `spec_hash` と方式が食い違い、考え方が2つになる

既存の `spec_hash` と同じ「runner が計算 → Reviewer が転記 → runner が照合」を採った。

## 5. `<F>/gates/.artifact_baseline` のような runner 専用サイドカーを持つ

**却下。**

AIの転記に依存せず確実に記録できる。しかし、

- 成果物の baseline に関する正本が Gate記録とサイドカーの2箇所になる
- サイドカーが消えると検出が静かに効かなくなる
- Gate記録を読めば工程が追える、という現在の性質が崩れる

**「後から読む人が Gate記録だけを見れば分かる」ことを優先した。**

## 6. `schema: gate_record/v2` へ上げ、`artifacts_hash` の欠落を異常として扱う

**採用しなかった（ただし未決として残す）。**

現在の実装では、`artifacts_hash` が空の記録は「判定不能」として扱い停止しない。
これは既存 feature（`cli_text_masker` など）の後方互換のためである。

副作用として、**新しい記録で Reviewer が転記を忘れた場合も同じ扱いになる**。
`spec_hash` が fail-safe（値が違えば止まる）なのに対し、
`artifacts_hash` は fail-open（値が無ければ検出が効かない）である。

schema を v2 へ上げれば「v2 なのに値が無いのは異常」と区別できる。

今回採らなかった理由は次の2つ。

- テンプレート・プロンプト・runner・テストへ同時に影響し、最小限の修正を超える
- schema のバージョン運用方針そのものが未整理で、**仕様上の判断が必要**

**この判断は人間に委ねる。** README の未決事項へ記載した。

## 7. `stage_cp3_artifacts` をディレクトリ単位（`src/{app}/features/`）にする

**採用しなかった（設定で選べる形にとどめた）。**

CP3 Worker の変更許可範囲と一致するため一見自然だが、
**同じ app の別 feature を変更しただけで「変更あり」と判定される。**

既定値は feature 1件ぶんの実装ファイルとテストファイルにした。

```text
stage_cp3_artifacts = src/{app}/features/{feature}.py, tests/{app}/features/test_{feature}.py
```

検出漏れ（結合試験など）と誤検出（別 feature の変更）のどちらを取るかは、
プロジェクトの feature 分割方針に依存する。**設定で変えられるようにし、
両方の副作用をルール文書へ明記した。**

## 8. `tasks.md` や `25_review_result.md` を baseline に含める

**却下。**

- `tasks.md` は作業メモであり、工程の判断対象ではない。頻繁に変わるため誤検出が出る
- `25_review_result.md` は Reviewer 自身の出力であり、レビュー対象の成果物ではない

含めると、Reviewer が自分の出力を書いた瞬間に「変更あり」になる。

自動テストで「baseline にこの2つを含めない」ことを固定した。
