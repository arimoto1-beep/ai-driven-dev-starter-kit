# 採用しなかった案と理由

## 1. AGENTS.mdを単純に分割するだけ

### 考えたこと

長くなったAGENTS.mdを複数ファイルへ分け、AGENTS.mdからリンクするだけでも整理はできる。

### 採用しなかった理由

それでは、

- どのtaskがどのruleを必要とするか
- どれが共通でどれがproject固有か
- task固有手順はどこへ置くか
- どの文書が正本か

が解決しない。

見た目だけ軽くしても、AIが毎回全部読むならコンテキスト上の意味も薄い。

そのため「ファイル分割」ではなく「責務分離」を先に行った。

## 2. すべてのpromptからAGENTS.mdを明示参照する

### 考えたこと

重要な入口なので、各promptにもAGENTS.mdを参照させれば読み忘れを防げるように見えた。

### 採用しなかった理由

AGENTS.mdは共通入口として別の役割を持つ。

各promptの参照資料に入れると、taskが読む資料と共通入口の境界がまた曖昧になる。

結果として23本の通常promptからAGENTS.md参照を外した。

## 3. ruleをなるべく多く読ませる

### 考えたこと

「念のため全部読む」方が安全そうにも見える。

### 採用しなかった理由

今回AGENTS.mdを薄くする目的の一つは、必要な情報へ絞って到達させることだった。

毎回ほぼ全部のruleを必須にしたら、ファイル分割した意味が薄くなる。

そのため、taskごとに必要なruleを列挙する方式にした。

## 4. conflict時にAIが優先順位を解釈する

### 考えたこと

core / project / task のどれを優先するかを機械的に決めれば、AIが止まらず進められる。

### 採用しなかった理由

下位taskが上位の安全ルールを意図せず弱める可能性がある。

また、矛盾そのものが「人間がルールを直すべきサイン」である場合もある。

そのため、矛盾時はAIが勝手に解消せず、人間へ戻す方針にした。

## 5. Opusレビューの指摘を全部採用する

### 考えたこと

高性能モデルで全体レビューを行ったため、指摘をまとめて反映すれば早い。

### 採用しなかった理由

レビューは現在の設計意図を完全に知っているわけではない。

実際、`review_context` にproject/50を追加する案は、責務から見て参照を増やしすぎると判断して採用しなかった。

今回の目的は「ルールを漏れなくたくさん読ませる」ことではなく、「必要なものを正しく読む」こと。

レビュー結果もAIの提案なので、採用するかは人間側で決めた。

## 6. 人向けREADMEやtutorialにもrule本文を詳しくコピーする

### 考えたこと

人間には一か所に詳しく書いてある方が分かりやすい。

### 採用しなかった理由

rule変更時の二重管理になる。

実際、構造変更後に人向け文書だけ古い表現が残る問題が起きた。

そのため、人向け文書は概要と導線に留め、詳細はruleへ委譲する方針にした。

## 7. 変更内容を作業メモの中心にする

### 考えたこと

作業記録というと、どのファイルをどう変更したかを並べる形が作りやすい。

### 採用しなかった理由

具体的な変更はGit差分からかなり復元できる。

一方で、

- 何に迷ったか
- どう考えて決めたか
- 何を捨てたか
- なぜレビュー指摘を見送ったか

はGitから復元しにくい。

そのため、この作業メモでは変更一覧より判断経緯を優先する。
