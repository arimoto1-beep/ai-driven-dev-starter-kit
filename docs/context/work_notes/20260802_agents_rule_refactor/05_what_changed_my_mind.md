# 何が考えを変えたか

## 最初は「ルールを分かりやすくする」作業だった

当初の中心課題は、AGENTS.mdが大きくなりすぎたことだった。

そこから、

- core / project / task
- 正本と人向け説明
- taskごとの必須参照ルール
- 矛盾時の停止

まで整理した。

ここまでは「現在AIが何に従うか」を分かりやすくする作業だった。

## 実際に使うと、別の不足が見えた

ルール体系を整理したあと、実作業で使ってみると、今の正しい状態はかなり追いやすくなった。

一方で、作業が終わった後に残るのは主に、

- 完成したrule
- 完成したprompt
- Git差分
- test結果

だった。

これだけでは、

> なぜこの形にしたのか

がかなり消える。

特に、採用しなかった案は完成物からほぼ消える。

## 「履歴を全部残せばいい」でもなかった

この問題に対して、作業チャットをそのまま保存する方向も少し試した。

AIが後から読むという意味では成立する。

しかし、人間が読むにはかなりつらい。

長い会話の中から、

- どこが本当の判断だったか
- どこが一時的な案だったか
- どこで考えが変わったか

を拾い直す必要がある。

そこで、

> 生ログそのものではなく、判断の経緯を落とさない形へ再構成する

という落としどころを考えるようになった。

## きれいにまとめすぎる問題

逆に、AIに「作業をまとめて」と頼むと、

- 最終的に何をしたか
- 何ができたか
- テストが通ったか

へ圧縮されやすい。

これは報告としては読みやすい。

しかし今回残したかったのは、

- 迷ったこと
- 採用しなかったこと
- 一度間違えたこと
- レビューで考え直したこと

だった。

「きれいな成功報告」になると、まさに残したい情報が消える。

このためwork notesでは、Gitに残る変更内容より、**完成物から復元しにくい判断過程を優先して残す**方向へ考えが変わった。

## 指示側AIにまとめさせたい理由もここにある

AIを指示側と作業側へ分けて使う場合、作業者AIは自分の担当範囲しか知らない。

一方、指示側AIは、

- 人間との最初の相談
- 作業者へ出した指示
- 作業者からの報告
- レビュー結果
- 人間が採用・不採用を決めた場面
- 修正依頼
- 最終判断

を通して見ている。

そのため、作業メモを作るなら、通常は指示側の文脈を持つAIの方が適していると考えた。

ただし、これは必須のシステム構成ではない。

単一AIでもよいし、リポジトリを見られないAIでも、提供された会話や報告をもとに作れる。

## AGENTS.md整理からwork notesへ

結果として、AGENTS.md薄型化の作業は、

> 現在有効なルールをどう整理するか

だけでなく、

> そのルールに至るまでの考えをどう残すか

という次の問題を見つける作業になった。

この流れから `docs/context/work_notes/` を作ることになった。

今回のwork note自体が、その考え方を試す最初の実例でもある。
