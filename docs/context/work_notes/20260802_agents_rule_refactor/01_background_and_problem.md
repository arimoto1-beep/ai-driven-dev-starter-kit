# 背景と問題意識

## 最初の違和感

スターターキットを育てていく中で、`AGENTS.md` に書くことが増えていった。

個々のルールは必要だったが、全部を一つの入口へ積み上げていくと、次第に「これは本当に毎回全部読む必要があるのか」という違和感が強くなった。

困っていたのは単純な行数ではない。

- 共通ルール
- このスターターキット固有のルール
- task固有の手順
- 人間向けの説明

が一か所へ寄っていくと、「誰が何を決めているのか」が分かりにくくなることが問題だった。

単にAGENTS.mdを短くしたいのではなく、**ルールの責務を分けたかった**。

## 単純分割では足りないと思った

最初に考えやすいのは、長いAGENTS.mdを複数ファイルへ分割してリンクすることだった。

しかし、それだけでは問題が残る。

分割したファイルを毎回すべて読ませるなら、ファイルが分かれただけでAIが読む情報量はほとんど変わらない。

さらに、

> どのtaskでどのルールが必要なのか

が明示されなければ、利用者もAIも結局「念のため全部読む」方向へ寄りやすい。

このため、ファイル分割より先に、

> ルールをどの層に分けるか  
> taskからどのruleへ到達させるか  
> どこを正本とするか

を決める必要があると考えた。

## 人向け文書との二重管理も気になった

READMEやtutorialは人間には必要だが、そこへルール本文まで詳しく書くと、rule変更時に説明だけ古くなる。

実際、後のレビューでは人向け文書に旧説明が残る問題が何度も出た。

そのため、今回の作業では、

- AIが従うルール
- 人間が理解するための説明

を意識的に分ける方向へ進んだ。

## 「AIの自由を奪う」つもりではなかった

ルールを分け、参照範囲を明示すると、AIを強く縛る仕組みに見える可能性もあった。

しかし、目的は細かく命令することではなく、AIを新人のように扱い、

- どこに正式情報があるか
- どの範囲なら変更してよいか
- 判断できないときはどこで止まるか

を分かりやすくすることだった。

自由度を減らすより、**迷わなくすること**を優先した。

## ここからwork notesの問題も見えてきた

ルール体系をきれいにするほど、逆に消える情報も見えてきた。

完成したruleを見れば「今どうするべきか」は分かる。

Git差分を見れば「何を変えたか」も分かる。

でも、

- なぜその案にしたのか
- 途中で何に迷ったのか
- 何を採用しなかったのか
- レビュー指摘をなぜ見送ったのか

はかなり消える。

この時点ではまだwork notes自体を作る作業ではなかったが、後から振り返ると、今回のAGENTS.md整理が「作業の判断経緯を別に残したい」という問題意識をはっきりさせた。
