# レビューを受けて考え直したこと

## Opusに見てもらう理由

AGENTS.mdやruleを大量に動かした後、自分たちの想定だけで「整った」と判断するのは危険だった。

この作業は、1ファイルの修正ではなく、

- AGENTS.md
- rule
- prompt
- template
- README
- tutorial

の参照関係を変えていた。

そこでOpusには、実装を直させるのではなく、まず読み取り専用で全体整合性を見てもらった。

## 思ったより周辺へ影響していた

レビューでは中程度5件、軽微8件の指摘が出た。

ここで印象的だったのは、core/projectの大きな分け方そのものより、

- 古い説明
- prompt内の参照残り
- 保護対象の不足
- 人向け文書の追随漏れ
- 見出しの意味のズレ

のような周辺部分が多く問題になったこと。

ルール体系を変えるときは、**本体の設計より周辺の整合性維持の方が大変**だと感じた。

## 指摘をそのまま飲まなかった

Opusの指摘はかなり有用だったが、全部を採用する方針にはしなかった。

特に `review_context` にproject/50を追加する案は見送った。

理由は単純で、

> 参照が増えれば安全になるとは限らない

と考えたから。

今回の作業自体が、必要なruleだけを読む方向への整理だった。

完全性レビューで「念のためこれも」と参照を増やし続けると、最終的にはまた全部読む構造へ戻ってしまう。

そのため、一件ずつ、

- これは本当に責務上必要か
- 現在の設計思想に合うか
- 他の文書との二重管理にならないか

を見て採否を決めた。

## 小さな修正にも意味があった

たとえば、

- `implement_bug_fix.md` の見出しを `tasks.md 更新候補` へ変える
- `review_feature_source.md` の `総合判定` を `中間チェック判定` へ変える

といった修正は、単なる言葉直しにも見える。

しかしルール体系を整理した後は、

> その見出しが何の権限を持つのか  
> その判定が最終なのか途中なのか

が以前より気になるようになった。

ファイル構造を分けたことで、言葉の責務にも敏感になった。

## 「全部直したら完成」ではなかった

レビュー指摘を直した後も、実タスクで使わないと本当に機能するか分からなかった。

そのためsimple_calculatorの将来リンク問題や、cli_hello_greetingのUTF-8問題などを扱った。

このとき、

- 将来成果物と現在の正式文書を分ける
- command/appレベルの契約とfeature仕様を分ける
- testだけ直して終わらせず、どこが正本かを先に考える

という動きが自然にできた。

ここで初めて、rule分離は「ファイル構造として正しい」だけでなく「実作業でも使える」と感じた。
