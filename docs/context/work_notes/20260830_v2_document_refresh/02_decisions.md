# 決定事項

**以下はすべて人間が決定した方針です。** AIは調査結果（`01_audit.md`）と選択肢を提示しました。

---

## 決定事項

### 1. feature 新規開発の表玄関はオートモードにする

新規利用者が最初に見る説明・導線は、オートモードを標準として見せます。

### 2. マニュアルモードは残す

**削除しません。** 位置づけを下げるだけです。

### 3. マニュアルモードを「既存変更・バグ対応専用」と限定しない

**この点は明示的に決定しています。** マニュアルモードの用途を、既存機能の変更やバグ対応だけに
狭めて説明してはいけません。

### 4. 新規 feature でも、人間が工程を細かく刻んで進めたい場合はマニュアルモードを利用できる

新規開発 = オートモード専用、という説明にはしません。**新規 feature であっても、
人間が1工程ずつ確認しながら進めたい場合はマニュアルモードを選べます。**

### 5. 現在仕様を説明する場所に残る古い情報は除去・更新する

`01_audit.md` の H-1 〜 H-5、M-1 〜 M-9、L-1 が対象です。

### 6. 過去の判断・実験・Gate・レビュー結果は履歴として維持する

下記「今回の重要な区別」を参照してください。

### 7. README ではまず次を説明する

1. 何をするものか
2. 人間が最初に何を用意するか
3. AIがどこまで進めるか
4. 人間がどこで判断するか
5. 完成までどう流れるか

**構成説明やファイル一覧より先に、この5点を置きます。**

### 8. 詳細機能を README 冒頭へ大量に並べない

`RETURN` / `BLOCKED` / `--rework` / `--retry-blocked` / モデル自動選択 /
Manufacturing Preflight などは、README 冒頭に並べません。

「AIが回す」「止まったら人間が判断する」まででよく、詳細は
`docs/rules/project/70_feature_loop.md` と `tools/README.md` へ委ねます。

### 9. features の上位構造については今回検討しない

今回のスコープ外です。

### 10. V2ドキュメント整理後、別途「最終的になりたい開発フロー」から逆算して features 上位構造を検討する

**今回の作業の後に、別テーマとして扱います。** 今回の作業でその方向へ寄せた変更を先取りしません。

## 今回の重要な区別

```text
古い情報
≠
すべて削除対象
```

**現在仕様を説明する場所**の古い情報は修正対象です。

一方、次は**その時点の事実を残す履歴**なので原則変更しません。

```text
docs/context/work_notes/
docs/context/ai_work_logs/
過去の Gate記録
過去のレビュー結果
rejected 案
実験記録
```

### 判定の基準

各記述について、次を問います。

| 問い | 判定 |
|---|---|
| これは「今こうなっている」と読者に伝える記述か | **現行資料** → 修正対象 |
| これは「そのときこう判断した」という記録か | **履歴資料** → 変更しない |

同じファイルの中に両方が混在することがあります（例：作業メモの README は現在地を示すが、
付随ファイルは当時の経緯を残す）。**ファイル単位ではなく記述単位で判定します。**

### 迷った場合

削除・書き換えではなく、**人間判断事項として報告します。** 履歴を消す方向へ倒しません。

`01_audit.md` の「人間判断が必要なもの」に、現時点で判定が割れているものを記載しています。

## 今回の作業のスコープ

### 対象

- 現在仕様を説明する文書・ルール・テンプレート・prompt の記述是正
- 入口文書のオートモード化
- オートモードのチュートリアル新設

### 対象外

- **V2 実装そのものの再設計**（`tools/feature_runner.py`、`70_feature_loop.md` の仕様変更）
- features の上位構造の設計
- feature 自動生成機能の検討
- 新機能追加
- 履歴資料の現在仕様への書き換え

**今回は「現在あるV2を、現在の説明へ追いつかせる」ことだけを行います。**
