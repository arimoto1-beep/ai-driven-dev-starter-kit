## 1. Phase 2B の微修正（2点）

### 1-1. 個別プロンプトがすべて Worker の委譲先に読める表現

**問題：** 「オートモードでは Worker の委譲先として同じものが使われる」という書き方だと、
`review_*` を含む `prompts/` のすべての個別プロンプトを Worker が使うように読めた。

実際は、Worker（`run_stage.md`）が委譲するのは **`70_feature_loop.md` の `stage_*_prompts` に
設定されたプロンプトだけ**である（現在は `create_feature_spec` / `create_function_design` /
`create_function_call_flow` / `create_test_design` / `create_review_checklist` / `implement_feature`）。
`review_*` 系は Worker の委譲先ではない。

| ファイル | 修正 |
|---|---|
| `docs/how_to_use_prompts.md` | 委譲図を「その stage に設定された作業用 prompt へ委譲」へ。補足を「**委譲されるのは stage に設定された作業用 prompt だけです。`prompts/` にあるすべての個別 prompt が Worker から使われるわけではありません**」へ |
| `docs/how_to_use_prompts.md` の一覧表 | 「**このうち、stage に設定されたものは Worker の委譲先にもなります**（対応は `70_feature_loop.md` が正本）」へ |
| `docs/overview.md` の表 | 同じ趣旨へ修正。あわせて「どの stage がどのプロンプトへ委譲するかは `70_feature_loop.md` の設定が正本。**ここには一覧を複製しません**」と明記 |

**stage とプロンプトの対応表は、入口文書へ複製していません。**

## 3. 新しいオートモードチュートリアル

### ファイル名

```text
docs/tutorials/005_automode_first_feature.md
```

既存の `010` / `020` / `030` / `040` は 10 刻みなので、**その前に入る `005`** としました。
ファイル名の並び順がそのまま「最初の入口」を示します。**既存ファイルの改名はしていません。**

### 題材

```text
コマンド／アプリ名: cli_text_reverser
feature 名:        reverser
内容:              入力された文字列を逆順にして返す
```

### 題材を選んだ理由

**既存サンプルをそのまま使えない理由を先に確認しました。**

| 候補 | 判定 |
|---|---|
| `cli_simple_calculator` | **使えない。** `20_spec.md` と `tasks.md` だけの状態は、**チュートリアル 010 の初期状態そのもの**。オートモードを回すと `21_design.md` 以降が生成され、**010 の fixture を壊す** |
| `cli_hello_greeting` | **使えない。** 成果物が完成済みで、最初から体験できない |
| `cli_text_counter` | **使えない。** 完成済み。さらに 030 / 040 の題材でもある |
| `cli_text_masker` / `cli_mask_rework` / `cli_uppercase_text` | **使わない。** Phase 4 で扱いが未決。勝手に正式チュートリアル用サンプルへ昇格させない |

したがって **読者が自分で新しい小さな command/app を作る**形にしました。

- **既存サンプルを1つも変更しない**（破壊的な初期化が発生しない）
- 読者は「何もない状態」から始められるので、**最初に必要なのが `20_spec.md` だけ**であることが体験できる
- 題材自体は、要求2件・境界条件1件（空文字列）・実装が数行と小さく、**実装より工程を学びやすい**
- 既存サンプルとの名前衝突を避けるよう明記した

**チュートリアル用の fixture ファイルは作成していません。** 読者が作る2ファイル
（`10_overview.md` と `20_spec.md`）の内容を、チュートリアル本文へ例として掲載しています。

### 章構成

```text
このチュートリアルで体験すること     … ★2か所の人間判断を含む6ステップの図
他のチュートリアルとの違い           … オートモード／マニュアルモードの対比表
前提                                 … 実行環境、AI CLI の条件、設定、設定確認
作る題材                             … cli_text_reverser / reverser と選定理由
初期状態：何を用意し、何をまだ作らないか … 人間が作る2ファイル／AIが作るファイル
1. コマンド／アプリの入口を用意する    … 10_overview.md
2. 20_spec.md を用意する              … REQ-ID、AI補助と「確定させるのは人間」
3. Spec Review を実行する             … --spec-review、verdict の読み方
4. ★ CP1：人間が仕様を承認する         … 承認欄、baseline、承認後の変更は無効
5. runner を実行する                  … 通し実行と --once、--status / --history
6. ★ CP3：人間が受け入れを判断する      … feature 要約、保証していない範囲、pytest
7. 完了を確認する                     … done
実行後に何が残ったか                  … 生成物一覧と gates/ の意味
うまく進まないとき                    … RETURN / BLOCKED / rework の入口だけ
次に読むもの / 進めるときの注意
```

### 最初から完了までの流れ

```text
10_overview.md と 20_spec.md を人間が用意
    ↓
--spec-review（Reviewer だけが動く。何度でも実行できる）
    ↓
CP1 Gate記録の「仕様承認（CP1 のみ）」へ人間がチェック
    ↓
--status で「次の動作: run (stage=G1)」を確認
    ↓
runner を実行（G1 → G2 → CP3）
    ↓
CP3 Gate記録の「受け入れ判断（CP3 のみ）」へ人間がチェック
    ↓
再実行して「完了しました。」/「次の動作: done」
```

### 意図的に主役にしなかったもの

`RETURN` / `BLOCKED` / `--rework` / `--retry-blocked` / `--review-current` / `--model-class` /
モデル選択の計算式 / Gate schema。最後の「うまく進まないとき」に**入口の表だけ**置き、正本へリンクしました。

### チュートリアル作成中に確認した、前提として明記すべき事項

過去の実AI検証（`20260823_feature_auto_mode_real_ai_validation/03_blocked_and_recovery.md`）で、
**CP3 の AI がテストを実行できず `BLOCKED(state_error)` になった**事例がありました。

そのため「前提」に、AI CLI の条件として
**「テスト実行コマンドを許可できること（CP3 で AI がテストを実行するため）」**
を明記しました。見落とすと CP3 で止まるためです。

## 4. 実行検証

### 実AIは使用していません

**実AI呼び出しは1回も行っていません。** 理由は次のとおりです。

- チュートリアルの題材は「読者が新しい command/app を作る」形なので、実AIで通すと
  **このリポジトリに新しいサンプル相当のディレクトリ（`docs/` / `src/` / `tests/`）が生成される**
- サンプルの追加・整理は **Phase 4 の人間判断事項**であり、Phase 3 の禁止事項でもある
- 費用と実行時間が発生する

代わりに、**AIを起動しない範囲で状態遷移を実地確認**しました。

### 実際に実行したコマンド

一時的に `docs/_tutorial_check/features/demo/20_spec.md` を作り、確認後に**ディレクトリごと削除**しました
（`git status` に残っていないことを確認済み）。

| # | コマンド | 確認できたこと |
|---|---|---|
| 1 | `--status`（記録なし） | `製造開始条件: 満たしていない` / `CP1 の人間による仕様承認がありません` / `次の動作: run (stage=CP1)` |
| 2 | `--spec-review --dry-run` | Worker を起動せず Reviewer だけが動くこと、Gate記録の作成先パス、`human_gate: yes` |
| 3 | `--dry-run`（承認前） | CP1 の Worker が `prompts/create_feature_spec.md` へ委譲すること、変更してよいファイル |
| 4 | 承認済み CP1 Gate記録を手で作成 → `--status` | `次の動作: run (stage=G1)` へ遷移すること。`feature_difficulty=easy` を読んでいること |
| 5 | `--dry-run`（承認後） | G1 の Worker が `create_function_design` + `create_function_call_flow` へ委譲すること |
| 6 | `--help` | チュートリアルで使う10オプションがすべて実在すること |
| 7 | `python -m pytest --basetemp=.pytest_tmp` | 257 passed |

**「20_spec.md を用意 → Spec Review → CP1 承認 → G1 へ進む」という、チュートリアルの中核部分の
状態遷移を実データで確認できました。**

### 実AIで未検証の部分

**以下はこのチュートリアルでは実AIで確認していません。**

| 未検証 | 補完している根拠 |
|---|---|
| CP1 Reviewer が実際に Gate記録を作成する内容 | 自動テスト（FakeAI による全 stage の往復）＋ `20260823` / `20260829` の実AI検証記録 |
| G1 / G2 / CP3 で AI が生成する成果物の実際の中身 | 同上。ただし**この題材（`cli_text_reverser`）では未実施** |
| CP3 で AI がテストを実行し PASS すること | `20260823` の実AI検証で確認済みだが、**別の題材での結果** |
| 新規 command/app（`src/<app>/` が存在しない状態）での CP3 実行 | 既存の `cli_text_masker` / `cli_mask_rework` は `src/<app>/features/__init__.py` のみで動作しているため成立する見込みだが、**この形での実AI確認はしていない** |
| 所要時間の目安（30分程度） | **実測ではなく目安です。** 本文にも「AI の応答時間により変動します」と記載 |

**この題材で実AIを一周通す検証は、サンプルの扱いが決まる Phase 4 以降に行うべき残作業です。**

## 10. 判断に迷った点

### 1. チュートリアルの題材に既存サンプルを使うか

**使わないと判断しました。** `cli_simple_calculator` は「`20_spec.md` だけがある」状態で
オートモードの出発点として理想的に見えますが、**それは 010 の初期状態そのもの**です。
オートモードを回すと 21_design.md 以降が生成され、010 のチュートリアルが成立しなくなります。

指示にある「既存の正式サンプルを破壊的に初期状態へ戻さない」に反するため、
読者が新しい command/app を作る形にしました。

### 2. fixture を新規作成するか

**しないと判断しました。** 読者が作るのは2ファイルだけで、その内容はチュートリアル本文に
例として全文掲載できます。リポジトリへ fixture を置くと、それ自体が「4つ目のサンプル」になり、
サンプルの扱いが未決（Phase 4）である現状と衝突します。

### 3. 実AIで一周検証するか

**しないと判断しました。** 上記4のとおり、実行するとリポジトリへサンプル相当のディレクトリが
生成されます。Phase 3 では「サンプル整理・正式化」が禁止されているため、
