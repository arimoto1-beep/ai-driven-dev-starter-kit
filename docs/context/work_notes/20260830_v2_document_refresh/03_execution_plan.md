# 作業計画

`01_audit.md` の調査結果と `02_decisions.md` の方針にもとづく作業順です。

**一度に全部直して巨大変更にしません。** 各 Phase が単体でも整合の取れる状態になるよう分けています。
Phase ごとに区切って人間が差分を確認します。

---

## Phase 1：明確な矛盾の除去

**模様替えより先に、現在仕様として明確に誤っている情報を修正します。**

### 目的

**AIが古い規則を根拠に誤判断する経路を先に減らす。**

特に H-1 は、オートモードの feature に対してAIが誤って STOP する経路になっています。
入口文書の模様替え（Phase 2）より、こちらを先に潰します。

### 対象

| 対象 | 監査項目 | 作業 |
|---|---|---|
| `docs/overview.md` の「実装前承認ゲート」 | H-1 | 実装開始条件を2方式（`manual` / `auto`）の条件分岐として書き直す |
| `docs/templates/24_review_checklist_template.md` | H-2 | 「CP1 の下流進行承認」→「CP1 の仕様承認」。「現在の `20_spec.md` と同一 baseline」条件を追記 |
| `docs/rules/project/10_document_structure.md` の `g0` 例 | M-1 | 実在する stage（`cp1` / `g1` など）の例に差し替え |
| `prompts/analyze_code_change_impact.md` | M-4 | 「実装着手承認欄の確認は通常どおり必要」に方式の条件を付す |
| `docs/tutorials/030_update_existing_feature.md` | M-3 の一部 | 同上（243行・260行・516行付近の無条件表現） |

### 完了条件

- 「実装着手承認欄が未チェックなら必ず STOP」と読める無条件記述が、現行資料に残っていない
- 「下流進行承認」という語が現行資料に残っていない
- 現行資料に存在しない stage（`G0`）の例が残っていない

### 注意

**この Phase では位置づけを変えません。** マニュアルモードを「標準工程」と呼んでいる箇所
（M-2）は Phase 3 で扱います。ここで手を広げると、誤り修正と模様替えが差分の中で混ざります。

| `AGENTS.md` | M-8 | 「実装・変更」の起点へ `project/70_feature_loop.md` を追加 |

### README の構成案

`02_decisions.md` の決定 7・8 にもとづきます。

```text
1. 何をするスターターキットか                （3〜4行）

2. 開発の流れ（1枚の図）                     ← 最初に見せる
   人間が 20_spec.md を書く
        ↓
   AIが仕様をレビュー（何度でも）
        ↓
   ★人間が仕様を承認する                    ← 人間の判断①
        ↓
   AIが 設計 → テスト設計 → 実装 を回す
     （各段階でAIレビューと修正の収束ループ。記録は Gate記録に残る）
        ↓
   ★人間が受け入れを判断する                ← 人間の判断②
        ↓
   完成

3. 人間がやること／AIがやること              （表2行程度）

4. 動かすために必要なもの                     （モード別に分ける）
   - Python
   - オートモード：非対話実行できる AI CLI（model 指定可）＋ 設定2項目の記入
   - マニュアルモード：文書を読める AI エージェント（Copilot Agent Mode など）

5. まず試す                                   （5行以内。オートモードのチュートリアルへ1本リンク）

6. もう一つの進め方：マニュアルモード          （短く）
   個別プロンプトを人間が1つずつ実行する。
   工程を細かく刻みたい場合に使える。新規 feature でも使える

7. リポジトリ構成                             （現在の内容＋ gates/ と feature_runner.py）

8. 詳しく知る                                 （現在の「主要な入口」表）

9. サンプル／ライセンス
```

**設計意図**

- **2 を最初に置くのが最大の変更点。** 現在の README は構成説明が先に来るため、「このキットで何が起きるのか」が最後まで分からない
- **★（人間の判断点）を2つだけ明示する**ことが、このキットの主張（最終責任は人間）を最短で伝える
- 詳細機能は README に書かず、`70_feature_loop.md` と `tools/README.md` へ委ねる（決定8）
- **6 で、マニュアルモードを「既存変更・バグ対応専用」と書かない**（決定3・4）

### 完了条件

- 入口文書からオートモードの正本（`70_feature_loop.md`）へ到達できる
- README を読んだ人が、人間の判断点が CP1 と CP3 の2つであると分かる
- マニュアルモードが「新規 feature でも選べる進め方」として読める

## Phase 5：全体整合レビュー

### 目的

ドキュメント、rules、prompts、templates、tutorials、実装、tests の間に、次が残っていないか確認する。

- 古い工程
- 古い用語
- 削除済み概念（`role_design` / `role_build` / `role_review` / `role_fixed` など）
- 誤った承認位置
- 不整合な導線

### 方法

`prompts/review_prompt_integrity.md`（キット自体の完全性確認用プロンプト）を使います。
これは開発対象機能のレビューではなく、キットの整合性を確認する工程外プロンプトです。

### 完了条件

- 現行資料に、現在仕様と矛盾する記述が残っていない
- 履歴資料が書き換えられていない（`git diff` で `work_notes` / `ai_work_logs` / `gates/` に変更が無いこと）
