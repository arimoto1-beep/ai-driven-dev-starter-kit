### 追加した考え方（事実ではなく理由）

| 実装事実 | この文書で書いた「なぜ」 |
|---|---|
| Worker / Reviewer を別プロセスにする | **作ったAIが自己レビューすると、作ったときの文脈に引っ張られる。**「こう作ったのだからこう動くはず」という前提を共有したまま確認するため、前提そのものの誤りに気づきにくい。だから会話履歴や思考の過程を渡さない |
| CP1 が人間側とAI製造の境界 | 線が曖昧だと、**AIが「一般的にはこうだから」と仕様を埋め、誰がいつ決めたのか分からなくなる。** 速さより、誰が決めたかを追えることを優先する |
| 仕様レビューと仕様承認を分ける | AIのレビューは**指摘のため**、人間の承認は**進めてよいと決めるため**。上長・顧客の確認を挟めるようにするため |
| CP1 / CP3 を固定点にする | 都度呼ぶと進まず、最後にまとめると確認範囲が大きすぎる。だから**必ず止まる場所を先に決める**。「その2回以外は見なくてよい」という意味ではない |
| Gate記録を残す・上書きしない | 成果物は残るが**なぜそうなったかは残らない**。前の判断を消すと「なぜ一度そう判断したのか」が追えなくなる |
| 承認後に仕様を変えたら承認が無効 | **「いつの仕様を承認したのか」が曖昧になると、線を引いた意味がなくなる** |

### `cli_text_masker` → **A. 正式サンプルとして整備して残す**

**理由**

- **現行リポジトリで唯一、実AIによる Gate履歴を通しで読めるサンプル**です。特に
  「CP3 で3回止まり（`state_error` 1回、`guard_violation` 2回）、復旧して PASS した」履歴は、
  **Gate記録が何のためにあるかを、テンプレートだけでは伝えられない形で示しています**

  現状は `gate_record_template.md`（空のひな形）しかありません
- 成果物が揃い、テスト6件が通っています。維持コストは低いです
- 既存の正式サンプル3件（`cli_hello_greeting` / `cli_simple_calculator` / `cli_text_counter`）は
  **すべてマニュアルモードの例**であり、オートモードの例と重複しません
