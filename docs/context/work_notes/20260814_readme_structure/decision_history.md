# README整理の判断経緯

## 出発点

主要ディレクトリを見たとき、ルートREADMEから存在自体は分かっても、そのディレクトリを開いた後に「ここには何があり、どれを読めばよいか」が分かりにくい場所があった。

一方で、READMEを増やせば分かりやすくなるとは限らない。

このリポジトリにはすでに、

* ルートREADME
* `docs/rules/README.md`
* command/appごとの `10_overview.md`
* task prompt
* 正式なルール文書

など複数の入口がある。

READMEを各階層へ機械的に追加すると、同じ説明を複数箇所へ書くことになり、将来の不整合を増やす懸念があった。

## READMEの役割を3つに限定した

検討の結果、READMEの役割を次に限定することにした。

1. 説明
2. 一覧
3. 導線

READMEだけを読んで正式な制約や工程判断まで完結させることは目的にしない。

正式なルールを確認する必要がある場合は、`docs/rules/` の正本へ進む構造にする。

これは「READMEを短くすること」自体が目的ではない。

READMEには、そのディレクトリが何であるかを理解するための説明は残す。一方で、

* 実装してよい条件
* STOP条件
* 承認条件
* AIの変更権限
* 正式な変更ルート
* テスト必須条件

など、読んだ人やAIが具体的な行動を決定できる内容は、正本側へ委譲する。

## READMEを追加する場所を絞った

当初確認した主要ディレクトリのうち、入口として効果が大きい場所だけを追加対象にした。

追加対象:

* `docs/`
* `prompts/`
* `docs/templates/`
* `docs/tutorials/`
* `tools/`
* `quality/`

### `prompts/`

prompt数が多く、フラットに並んでいたため、用途からpromptを探す索引が有効と判断した。

個々のpromptの具体的手順や変更範囲までは索引へ複製しない。

### `docs/templates/`

テンプレート数が多いため、「何を作るときにどのテンプレートを探せばよいか」という入口が必要だった。

正式な成果物との対応ルールはREADMEではなくルール正本へ委譲する。

### `docs/tutorials/`

詳細手順を再掲するのではなく、「何を試したい人がどれを読むか」を示す入口とした。

### `tools/` と `quality/`

`tools/` は生成・確認を行う側、`quality/` は結果を置く側として、双方に短い入口を置くことにした。

## READMEを追加しなかった場所

READMEがないことだけを理由に追加しなかった。

### `docs/rules/core/` と `docs/rules/project/`

親の `docs/rules/README.md` が各正本の索引を持つため、子階層にもREADMEを置くと一覧が重複する。

### 各 `docs/<command_or_app_name>/`

既存の `10_overview.md` が設計文書の入口である。

READMEを追加すると、「READMEと10_overviewのどちらが入口か」という新しい曖昧さを作るため採用しなかった。

### `src/` と `tests/`

ディレクトリ構造や責務の正式な説明はルールにあり、ルートREADMEにも全体像がある。

今回READMEを増やす効果より、説明の二重管理を増やす懸念の方が大きいと判断した。

### `quality/events/`

イベントファイルは増えるため、個別ファイル一覧をREADMEへ固定的に管理しないことにした。

親の `quality/README.md` から役割だけ案内する。

## 第1段階の実装方針

第1段階では、新規6 READMEを作成し、既存文書側の重複一覧を減らすことにした。

特に、

* prompt一覧を `prompts/README.md` へ集約
* template一覧を `docs/templates/README.md` へ集約
* tutorial一覧を `docs/tutorials/README.md` へ集約

することで、一覧の正本に近い入口を一か所に寄せた。

`docs/how_to_use_prompts.md` にあったprompt全件一覧は削り、`prompts/README.md` への導線へ変更した。

また `docs/common/README.md` には、共通化の判断条件や制約に相当する記述が直接存在していたため、既存ルールへ委譲した。

## 第1段階のレビューで不足に気づいた

第1段階の実装自体は、依頼した範囲では成立していた。

しかし実装後のREADME全体を改めて見ると、問題は「READMEがない場所」だけではなかった。

ルート `README.md` や、

* `docs/rules/README.md`
* `docs/context/README.md`
* `docs/context/work_notes/README.md`
* `docs/context/ai_work_logs/README.md`

にも、正本に存在するルール本文がかなり残っていた。

例としてルートREADMEには、承認ゲート、変更ルート、実装責務、テスト条件などの詳細があり、その直後で `docs/rules/` を正本として参照していた。

つまり、

```text
README
  ├─ 正式な条件をかなり詳しく説明
  └─ 正本にも同じ内容が存在

docs/rules/
  └─ ルール正本
```

という二重管理が残っていた。

目指した構造は次だった。

```text
README
  └─ 全体像と正本への導線

docs/rules/
  └─ 正式な条件・判断の正本
```

## 最初の実装依頼にも取りこぼしがあった

第1段階のCodex用promptでは、既存READMEの薄型化対象として `docs/common/README.md` を明確に指定した一方、ルートREADMEは「必要なら最小限修正」としていた。

そのためCodexは依頼どおりに作業したが、README全体へ同じ原則を適用するところまでは対象にならなかった。

この手戻りはCodexの実装ミスというより、最初の作業範囲の切り方が狭かったことによる。

これを受け、第2段階として「既存READMEから正本と重複するルール本文を整理する」作業を別途依頼した。

## 第2段階での判断基準

README内の文章が概要かルール本文か迷う場合、次を判断基準にした。

その文章だけを読んで、

> 人間やAIが具体的に何をしなければならないか判断できる

のであれば、ルール本文である可能性が高い。

一方、

> 何が存在するか、何のためのものか、詳細をどこで確認するかが分かる

のであれば、READMEへ残してよい説明とした。

## `docs/rules/README.md` は単なるリンク集にしなかった

`docs/rules/README.md` には `core / project / task` の関係を残した。

これは個別のルール条件ではなく、ルール体系そのものを理解するための地図だからである。

READMEを薄くすることを優先しすぎて、利用者が構造を理解できなくなる形にはしなかった。

## context系READMEの扱い

context系READMEでは、

* 何を置く場所なのか
* 現在どんな種類の記録があるのか
* 新旧の作業記録方式がどう位置づけられているか
* 次にどこを読めばよいか

を残した。

一方、

* 正式資料と矛盾した場合の正式な扱い
* AIが更新できる条件
* work noteの保存・命名・更新方法
* 旧AI作業ログの正式な凍結条件

などはルール正本へ委譲した。

## ファイル名の案内は残した

`docs/context/README.md` に、

> ファイル名は、一覧から内容を識別できる名前を目安にします。

という案内が残った。

対応する強制ルールの正本は確認できなかったが、「必須」「〜しなければならない」ではなく、READMEの一覧性を高めるための目安として書かれている。

そのため、今回は削除もルールへの昇格も行わなかった。

将来、日付形式などを必須化する場合は、その時点で正式なルール変更として扱う。

## 今回採用しなかった考え

### READMEがない場所すべてへREADMEを置く

採用しなかった。

親READMEや既存の設計入口との二重管理になるため。

### READMEに正本の要約を詳しく残す

採用しなかった。

要約が詳細になるほど、正本更新時にREADMEだけ古くなる可能性が高くなるため。

### READMEを単なるリンク集にする

採用しなかった。

初見利用者が「何のための場所なのか」を理解できなくなるため。

### 第2段階でREADME以外の人向け文書まで整理する

採用しなかった。

`docs/how_to_use_prompts.md` などにもルールに近い説明はあるが、How-toとして必要な説明との境界を別途検討する必要がある。

今回のREADME整理から範囲を広げないことを優先した。
