### 自己点検の限界

- **人間によるレビューを受けていない。** AIの自己点検は、自分が書いた文章を自分で読み直しているため、意図の取り違えは検出しにくい。
- 検索ベースの確認は、同じ意味を別の表現で書いた箇所を取りこぼす可能性がある。
- 実際に prompt を使った動作確認は行っていない（下記「残課題」）。

## 残課題（実際に使って確認した方がよい点）

### 1. 型Aの変更を、実際に1件通してみる

`implement_feature.md` は実装着手承認欄のチェックを必須にしている。型A（可読性改善など）でもこれを通す設計にした。

**運用上重すぎないかは、実際にやってみないと分からない。** 重すぎる場合の選択肢:

- 軽量な実装 task prompt を新設する
- `project/20_workflow.md` で承認ゲートの適用条件を定義する

いずれも影響が大きいため、今回は**現行の承認ゲートを維持する判断をした。** 新しい承認制度を増やさないという指示に沿った結果でもある。

### 2. 逆反映候補の記録先

既存の「仕様変更が必要そうな点」へ相乗りさせた。実際のレビュー結果で、仕様確認待ちの項目と逆反映候補が混在して読みにくくならないかを確認したい。

読みにくい場合は、テンプレート2本 + prompt 2本の同期変更として別作業で扱う。

### 3. `review_design_code_consistency.md` の scope 制御

「scope 指定必須」「scope 外は確認候補として報告するだけ」「完遂できない場合は分割提案」という制御を入れたが、実際にAIがこれを守るかは使ってみないと分からない。

特に、scope を command/app 全体にしたときに、浅く広く読んで「矛盾なし」と報告してしまわないかを確認したい。

### 4. 「未記載だが問題ではない実装詳細」欄の分量

出力項目として作ったが、実装詳細を全部列挙して報告が長大になる可能性がある。適切な粒度は使ってみて調整する。

### 5. 型Aの判定精度

AIが「これは実装詳細だ」と判断した内容が、実は責務や共通方針に関わっていた、というケースが起きうる。判断材料チェックリスト9項目と「不明を根拠に確定しない」制約で抑えているが、実運用で外れ方を見たい。

### 6. 人間によるレビュー

今回の改訂全体について、人間のレビューを受けていない。特に次を見てほしい。

- 型A〜E の定義が実務感覚と合っているか
- 「未記載と矛盾」の境界が、実際のレビューで判定できる粒度か
- AI権限の分離が十分に読めるか（薄いと感じないか）

### 7. 未コミット差分の整理

commit / push / branch 作成は行っていない。コミット単位の整理は別作業。

## 依頼と実際の差異

利用者の依頼17項に「新しいAI作業ログを作成してください」とあったが、あわせて「現在のリポジトリの最新ルールに従い」「命名・連番ルールを確認したうえで決めてください」という指示があった。

現在のルールを確認したところ、次だった。

- `docs/rules/README.md`: 旧AI作業ログ（`docs/context/ai_work_logs/`）は**旧方式として凍結**。**新しいAI作業ログは原則として作成しない**
- 新しい作業知識の記録は**作業メモ**（`docs/context/work_notes/`）で扱う
- `docs/rules/project/60_work_notes.md`: 保存場所は `docs/context/work_notes/YYYYMMDD_<short_name>/`、テーマ単位

したがって、**旧形式のAI作業ログではなく、現行の作業メモとして作成した。** これが「現在のリポジトリの最新ルールに従う」という指示への解釈である。

作業メモは保護対象であり、AIは人間の明示指示なしに作成しない（`project/50_ai_permissions.md`）。今回は利用者の依頼そのものを明示指示として扱った。

内容には、依頼17項が指定した項目（元の依頼／変更した大原則／変更したファイル／変更理由／人間の直接修正とAI権限の分離／2種類の prompt の役割／実施したレビュー／テスト結果／残課題／あえて行わなかったこと）をすべて含めている。
