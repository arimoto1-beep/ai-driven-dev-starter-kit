# 人間レビューで見つかった分類軸の混同と、その補正内容

このファイルは、2026-08-10 の初回改訂に対する人間レビューを受けて、2026-08-11 に実施した補正作業の記録です。**初回改訂の内容（`01`〜`04`）を上書きせず、差分として残します。**

## 何が指摘されたか

初回改訂では、変更を次のA〜E「5つの型」として分類していた。

- A. 実装詳細で完結する変更
- B. 正式資料を正本として下流へ反映する変更
- C. コードから正式資料へ逆反映する変更
- D. コード先行
- E. 判断材料不足

人間レビューにより、**この5分類には異なる性質の軸が混ざっている**ことが指摘された。

具体的には、

- C（コードから正式資料へ逆反映）と D（コード先行）は、**同じ変更に同時に該当しうる**。たとえば、人間がコードを先に修正し、その結果として「今後も守るべき設計上の意味だ」と分かって設計書へ逆反映する場合、変更ルートとしては C、実施状態としてはコード先行である。DをCと同じ「変更の型」として扱うと、AIによって同じ変更がCになったりDになったりし、分類が安定しない。
- E（判断材料不足）は、変更の型ではなく、**A〜Dのどれかを判定できない状態**を表しているにすぎない。型と並べて5番目の型として扱うべきではない。

## なぜこれが問題か

この混同を放置すると、次の実害がある。

1. **AI（分析役）ごとに結果がぶれる。** 同じ変更でも、ある分析ではC、別の分析ではDと報告され、人間が「結局どちらが正しいのか」を判断できなくなる。
2. **「コード先行だから逆反映（C）」という誤読が生まれる。** 実際には、コード先行はB（正式資料から下流へ反映すべきだった変更が先行した）でも起こりうる。型として並べると、この関係が見えなくなる。
3. **Eが型として扱われると、「判断できないなりに何かの型に押し込む」圧力が生まれる。** 判断不能を独立した状態として扱わないと、無理な確定を誘発する。

## どう補正したか

**変更ルート**と**実施状態**という、独立した2つの軸に分離した。

### 変更ルート（3種類 + 判断不能）

正式資料への反映関係を表す軸。

- A. 実装詳細で完結する変更
- B. 正式資料を正本として下流へ反映する変更
- C. コードから正式資料へ逆反映する変更
- 判断不能（A〜Cを確定できない状態。4つ目の型ではなく、確定できない状態を表す区分）

### 実施状態（変更ルートとは別に確認する）

- 未着手／一部実施／実施済み
- コード先行：あり／なし
- コード先行の理由（ありの場合）：障害対応／時間制約／検証目的／その他／該当なし

**コード先行は、変更ルートB・Cのどちらでも起こりうる「状態」として扱う。** 独立した変更ルートとしては扱わない。

### 複合状態の許可

次のような組み合わせを、正常な分析結果として扱う。

```text
変更ルート: C（コードから正式資料へ逆反映）
実施状態: 実施済み
コード先行: あり
後追い反映: 必要
```

「Cかコード先行か」のどちらか一方へ無理に分類することはしない。

## Bの反映順の補正

初回改訂の `core/10_workflow.md` には、次の記述が残っていた。

> 正式資料で意味を定義すべき変更について、意味を確定しないまま実装で既成事実を作りません。その場合は、仕様 → 設計 → テスト観点 → 実装 → レビュー の順に、段階的に進めます。

これは、ルートB全体が「必ず仕様から始まる」と読める。実際には、正本が `21_design.md`（設計）や `22_flow.md`（フロー）である場合もあり、その場合は仕様書を無理に更新すべきではない。

補正後は、次のように整理した。

- ルートBの基本骨格は「正本 → 必要な下流資料 → 実装 → テスト → レビュー」
- 「仕様 → 設計 → テスト観点 → 実装 → レビュー」は、正本が仕様である場合（多くは外部から見える動作の変更）に生じる順序の**一例**であり、固定ルートではない
- `project/20_workflow.md` の標準8ステップも、仕様が正本になる場合を主な例として明記しつつ、正本が異なる場合はStep 3〜6の対象と順序が変わることを明記した

## 標準化・共通化の起点判定

初回改訂の tutorial 030 では、「複数featureにまたがる標準化」「共通化候補」を機械的にルートC（逆反映）へ固定していた。

これも軸の混同の一種だった。標準化・共通化は、**起点によってBにもCにもなりうる**。

- 先に人間が「今後この方式を正式ルールにする」と決めて、正式資料から変更する → ルートB
- コードを比較していて、共通の方針として残すべきだと気づいた → ルートC

判定基準を「どこでその正式な意味を定義することになったか」に統一し、`core/10_workflow.md`、`project/20_workflow.md`、`analyze_code_change_impact.md`、tutorial 030 のすべてに同じ基準を明記した。

## 残課題（軸補正後に追加で確認したい点）
