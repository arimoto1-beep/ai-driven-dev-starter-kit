# 人間の直接修正とAI権限の分離、2種類の prompt の役割

## 1. なぜ「人間の直接修正」と「AIの変更権限」を明示的に分けたか

### 混同されやすい構造だった

改訂前の `docs/rules/project/50_ai_permissions.md` は、次の2つを1つの節に混ぜていた。

- 人間が直接修正してよい範囲（誤字・表記ゆれのみ）
- 影響のある修正は人間が直接編集せず、AIへ別作業として依頼することを基本とする

この構造のまま「人間の直接修正を解禁する」と書き換えると、**同じファイル・同じ文脈でAIの権限も緩んだように読める**危険があった。

利用者も、依頼の中で最も強く念を押していた。

> 人間がコードを直接修正してよいことと、AIが自由にコードを修正してよいことは別問題です。
> 今回の変更によって、AIの変更権限を広げないでください。

### 取った対策

**対策1: 節を分けた。**

`project/50_ai_permissions.md` を次の2節構成にした。

- 「人間による直接修正」… 人間の行動範囲
- 「人間の直接修正は、AIの権限ではありません」… AIの制約の再掲

同じファイル内で読み飛ばされないよう、後者を独立した見出しにしてある。

**対策2: core 側にも同じ分離を書いた。**

`docs/rules/core/10_workflow.md` の「人間による直接修正と、AIの変更権限」で、直接修正の解禁とAI制約の維持を**同じ節**に置いた。片方だけを読んで誤解されないようにするため。

**対策3: 「区分Aだから直してよい」という抜け道を明示的に塞いだ。**

新しく型A（実装詳細で完結する変更）を導入したことで、次の抜け道ができる危険があった。

```text
AIが「これは型Aだ」と判断
  → 正式資料の更新も承認も不要
  → だから今すぐ直してよい
```

これを次の3箇所で塞いだ。

| 場所 | 記述 |
|---|---|
| `core/10_workflow.md` | AIは変更の型を判断・提案できるが、それを理由に作業範囲を広げたり、保護対象を変更したり、人間の承認なしに次工程へ進んではならない |
| `project/50_ai_permissions.md` | AIが型Aと判断したことは、AI自身の作業範囲を広げる根拠にならない |
| `prompts/analyze_code_change_impact.md` | 分析の結果を理由に、このプロンプトの作業範囲を広げてはいけない。「型Aだから、そのまま直してよい」という進み方はできない |

さらに `project/20_workflow.md` と `docs/tutorials/030_update_existing_feature.md` に、**「型Aでも実装着手承認は省略しない」**を明記した。

**対策4: 完全性レビューの検出項目にした。**

`prompts/review_prompt_integrity.md` の観点2に、AI権限拡大の検出8項目を追加した。今後の変更でここが緩んだ場合に検出できる。

### 実装後に確認したこと

- `docs/rules/project/50_ai_permissions.md` の保護対象リストは**1行も減っていない**
- 各 prompt の `## 変更してよいファイル` は**1つも広がっていない**
  - `analyze_code_change_impact.md`: いかなるファイルも変更しない（維持）
  - `review_design_code_consistency.md`: いかなるファイルも変更しない（新設時から）
  - `review_feature_source.md`: いかなるファイルも変更しない（維持）
  - `review_feature.md`: `25_review_result.md` と `tasks.md` のみ（維持）
  - `review_command.md`: `12_command_review_result.md` と `tasks.md` のみ（維持）
- 承認ゲート（実装着手承認、バグ修正計画承認）は変更していない
- `GO` / `条件付きGO` / `STOP`、条件付きGO6項目、レビュー結果4値は変更していない

### 重い運用を作らなかった理由

利用者の指示は次だった。

> 人間による直接修正のたびに必ず新しい承認工程や作業メモを作る、といった重い運用は新設しないでください。

対応として、`project/50_ai_permissions.md` に明示的に書いた。

> この確認のために、新しい承認工程・専用の記録様式・毎回の作業メモ作成といった重い運用は新設しません。
> Git差分、通常のコミット履歴、テスト結果、レビュー、既存の作業報告など、現在の通常運用で足りる場合はそれを使います。

「禁止を解いたが、代わりに別の重さを足した」状態にならないようにするため。

## 2. 2種類の prompt の役割分担

### なぜ2本に分けたか

改訂前は `analyze_code_change_impact.md` 1本だけだった。これは「変更案」を入口にしており、次が扱えなかった。

- すでに行われた変更を後から確認する
- 変更の話ではなく、「今の設計書と今のコードがずれていないか」を確認する

この2つを1本に詰め込むと、中心の問いが2つになり、出力も混ざる。分けた。

### 役割の違い

| | `analyze_code_change_impact.md` | `review_design_code_consistency.md` |
|---|---|---|
| 見るもの | **変更** | **現在の状態** |
| 中心の問い | この変更は、正式資料で意味を定義・維持する必要があるか | 現在の正式資料と現在のコードに、意味上の矛盾がないか |
| 入力 | 変更案、または実施済みの変更（Git差分） | 指定された scope |
| 主な出力 | 反映区分（A〜E）と根拠、影響範囲、次の作業 | 意味上の矛盾、未記載だが問題ではない実装詳細、逆反映候補 |
| 時間軸 | 変更の前後どちらでも | 今 |
| ファイル変更 | しない | しない |

覚え方としては次。

- **差分を見たいなら analyze**
- **今の状態を見たいなら consistency**

### 役割の重複を避けるために入れた記述

両方の prompt に、相手を指す「混同しないでください」を入れた。

- `analyze_code_change_impact.md`: 「現在の正式資料とコードの整合そのものを確認したい場合は `review_design_code_consistency.md` を使ってください」
- `review_design_code_consistency.md`: 「変更の意味と反映先を整理したい場合は、そちらを使ってください」

`docs/rules/project/20_workflow.md`、`docs/rules/README.md`、`README.md`、`docs/overview.md`、`docs/how_to_use_prompts.md` にも同じ対比表を置いた。**ルール本文としてはどこにも重複させず、比較表という説明として置いている。**

`prompts/review_prompt_integrity.md` に観点 11-5 を新設し、この役割分離が崩れていないかを検出できるようにした。

### 新 prompt の設計で特に注意した点

**scope の暴走を防いだ。**

「feature だけに限定せず、command / app / 共通処理も確認できるようにしたい。ただし一度にリポジトリ全体を無制限に読むプロンプトにはしないでほしい」という要求があった。

対応:

- scope 指定を必須にした。**指定がない場合は確認を始めずに範囲を尋ねる**
- scope 種別を4つに定義（feature / command_or_app / 共通処理 / 複数 command_or_app）と、それぞれで主に確認する正式資料を表にした
- 「scope を無制限に広げないこと」を独立した節にした
- scope 外に矛盾の疑いを見つけても、その場で確認せず「scope 外の確認候補」として報告する
- scope が大きすぎて完遂できない場合は、**浅く広げず**、確認できた範囲とできなかった範囲を明示して分割を提案する

**「未記載だが問題ではない実装詳細」を出力項目にした。**

単に「指摘しない」と書くだけだと、確認したのか見落としたのか分からない。出力項目として残すことで、「確認したうえで問題なしと判断した」ことが見える。

同時に、**この節の内容を修正すべき事項として扱わないこと**を明記した。項目を作ったせいで、かえって「これも直そう」という圧力にならないようにするため。

**矛盾には根拠を必須にした。**

「根拠となる正式資料の記述を示せない場合、その項目を矛盾欄に書かないでください」と書き、代わりに「未記載だが問題ではない実装詳細」または「判断材料不足」へ回させる。

これがないと、「なんとなく設計と違う気がする」が矛盾として並び、旧来の問題（実装の揺らぎを全部指摘する）が再発する。

### テンプレートを増やさなかった判断

逆反映候補（コードから正式資料へ昇格させるべき知見）を、レビュー結果へどう記録するかを検討した。

- 案1: `25_review_result.md` / `12_command_review_result.md` に新しい見出しを追加する
- 案2: 既存の「仕様変更が必要そうな点」へ、逆反映候補である旨を明記して記録する

**案2を採用した。** 理由:

- 利用者から「既存の出力項目で扱えるなら新しいテンプレート項目を増やさないでほしい」という明示的な指示があった
- 見出しを追加すると、テンプレート2本 + prompt 2本の同期変更が発生する（`docs/rules/project/25_review_policy.md` が定める同期変更の考え方に沿うと、影響範囲の整理と人間承認が必要になる）
- 「仕様変更が必要そうな点」は「現在の仕様では判断できない点や、仕様変更が必要そうな点」を記録する欄であり、逆反映候補はその範囲に収まる

ただし、**逆反映候補があることだけを理由にレビュー結果を `要仕様確認` にしない**ことを明記した。相乗りさせたことで判定が歪むのを防ぐため。この判断が実運用で読みにくいようなら、テンプレート変更を別作業として検討する（README の未決事項に記載）。
