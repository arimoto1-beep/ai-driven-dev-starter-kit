# 変更したファイルと変更理由

実装順は core → project → task → 人向け文書 → 完全性レビュー用 prompt。

## 第1段階: core（原則の正本）

### `docs/rules/core/10_workflow.md`

**今回の原則の唯一の正本。** 最も大きく変えた。

| 節 | 変更 |
|---|---|
| このファイルを読む作業 | 「変更に着手する前の影響分析」→「変更の影響分析（着手前・着手後のどちらでも）」。整合確認作業も追加 |
| 段階的に進める | 「いきなり実装しません」→「**正式資料で意味を定義すべき変更について、意味を確定しないまま実装で既成事実を作りません**」。あわせて「すべての変更を仕様書から始めることを求めるものではない」を明記 |
| 実装前後の整合確認 | 「設計書と実装内容にズレがないか」→「正式資料が定義している意味と**矛盾していないか**」 |
| 未記載と矛盾を区別する | **新設。** 表で定義し、実装方式の揺らぎ自体を問題にしないことを明記 |
| 変更に着手する前の分類と分析 | **「変更の意味を見極める」へ置換。** 中心の問いを提示し、判断材料9項目を列挙。着手前の分析だけを唯一の入口としない |
| （新設） | **「変更の型」を新設。** A〜E の定義と、型ごとの守るべきこと |
| 変更の正本と上流からの反映 | **「変更の正本と、正本を持たない変更」へ置換。** 正本の概念を維持しつつ、「正本が見つからない」を2分岐にした |
| （新設） | **「人間による直接修正と、AIの変更権限」を新設。** 直接修正を禁止せず、同じ節でAI権限が変わらないことを明記 |
| バグ対応の段階 | 「型D（コード先行）を理由に基本ルートを省略できない」「AIが自ら緊急対応と判断しない」を追記 |

変更理由: 旧記述が「常に正本が存在する」「必ず変更前に分析する」「必ず正本から下流へ」と読める一本道だったため。ここを変えないと、下位の project / task を変えても実運用が変わらない。

### `docs/rules/core/40_official_docs_and_context.md`

- 3分類表の正本行「常に基準とする。**変更は上流から順に反映する**」→「正本が定義する意味を変更する場合は、正本で意味を確定してから下流へ反映する」
- **「正式資料が意味を定義していない実装詳細」を新設。** 定義、例、守ること（未記載は不整合ではない／すべての変更に正本があるとは限らない／実装詳細の写しへ拡張しない／矛盾は実装詳細として扱わない）
- **「コードから正式資料への反映（逆反映）」を新設。** 昇格の条件、示すべき4点、AIが自動更新しないこと

変更理由: 3分類表に反映方向が埋め込まれており、「全変更が正本経由」という読みを補強していた。また、実装詳細という概念と逆反映の経路が正本側になかった。

### `docs/rules/core/30_change_safety.md`

- 「ついで修正の禁止」に、これは**作業の混在を禁止するもの**であり、人間が意図した作業としてコードを直接修正すること自体を禁止しない旨を追記。AIには作業対象の限定と保護対象がそのまま適用されることも併記
- 「関連するルール」の参照先名称を更新

変更理由: 元の記述（レビュー中・調査中・説明中のついで修正禁止）は今回の方針と両立するが、人間の直接修正解禁と読み違えられないよう境界を明示した。**禁止自体は一切緩めていない。**

### `docs/rules/core/20_approval_and_review.md`

- 「STOPとする場合」に2段落追記
  - 「更新が必要」とは正式資料が定義している意味を変更・追加する必要がある場合であり、未記載の実装詳細は該当しない
  - 正本が見つからないことだけを理由に一律 STOP としない。2分岐と、区別できない場合の人間判断へ戻す

変更理由: 判定値・承認境界は一切変えていないが、STOP の入力条件が旧原則のままだと実装詳細の変更まで止まる。**判定3値、条件付きGO6項目、承認境界は変更していない。**

## 第2段階: project

### `docs/rules/project/50_ai_permissions.md`

- 「人間による軽微変更の範囲」→**「人間による直接修正」へ改題・改訂。** ソースコードとテストコードの直接修正を明記。修正後に型A〜Dのどれかを確認する表を追加。**重い運用（新しい承認工程・専用記録様式・毎回の作業メモ）を新設しないことを明記**
- 「影響のある修正の扱い」（人間が直接編集せずAIへ別作業として依頼することを基本）を**削除し**、上記へ統合
- **「人間の直接修正は、AIの権限ではありません」を新設。** AIの制約6点を再掲し、区分判定を理由に権限が広がらないことを明記
- 「変更する場合の注意」に、人間の行動範囲をAI権限へ転用しない旨を追記

変更理由: 旧「影響のある修正の扱い」が今回の方針と最も強く衝突していた。「実装に影響する修正」がほぼ全コード変更を含み、人間の直接修正を実質禁止していた。

**保護対象リストは1行も減らしていない。** 各 task の変更可能範囲も広げていない。

### `docs/rules/project/20_workflow.md`

- 「変更を検討する場合」を**型ごとの入口表**に置換。A〜E それぞれの進み方への導線
- 2つの prompt の役割分担を明記
- **「実装詳細で完結する変更の進め方」を新設。** 型Aでも実装着手承認は省略しないことを明記
- **「コードから正式資料へ逆反映する場合」を新設**
- **「コードを先に変更した場合」を新設**
- 「仕様変更の進め方」に**スコープ明示**（型Bに適用する標準フローであること）
- 標準8ステップの Step 7 の「整合性の確認」が矛盾の確認であることを明記
- バグ対応フローに**「障害対応などでコードを先に修正した場合」を最小限追記**（緊急バイパスは作らない）
- レビュー工程表に `review_design_code_consistency.md` を追加
- 「変更する場合の注意」に、骨格は正式資料で意味を定義すべき変更に適用されること、型A〜Eを再定義しないことを追記

変更理由: 変更作業全体が一本道に見える構造を解消するため。既存の仕様変更フローとバグフローは残した。

### `docs/rules/project/10_document_structure.md`

- 「実装とテストコードは正本の下流」に、整合確認は**矛盾の確認**であり、正本が意味を定義していない実装詳細が実装側にだけ存在することは不整合ではない旨を追記

### `docs/rules/project/25_review_policy.md`

- チャット報告のみでレビュー結果4値を使わない prompt の一覧に、`review_design_code_consistency.md` と `analyze_code_change_impact.md` を追加。この2本が総合判定として次工程移行判定3値を出すことも明記

変更理由: 新 prompt の追加に伴う一覧の追随。**レビュー結果4値そのものは変更していない**ため、テンプレートや `tools/quality_report.py` の同期変更は発生していない。

### `prompts/review_design_code_consistency.md`（新設）

**中心の問い:** 現在の正式資料と現在のコードに、意味上の矛盾がないか。

命名は既存の `review_*` 規則に合わせた。`review_feature.md` / `review_command.md` / `review_context.md` / `review_feature_source.md` / `review_prompt_integrity.md` と並ぶ。

主な設計:

- **scope 指定が必須。** 指定がない場合は確認を始めずに範囲を尋ねる。scope 種別は feature / command_or_app / 共通処理 / 複数 command_or_app
- **リポジトリ全体を無制限に読まない。** scope 外は「scope 外の確認候補」として報告するだけ。完遂できない場合は分割を提案し、確認できた範囲と できなかった範囲を明示
- 確認観点6種（外部から見える動作／責務と境界／呼び出し関係・処理フロー／共通設計／テスト／逆反映候補）
- 出力で「意味上の矛盾」と「未記載だが問題ではない実装詳細」を**明示的に分ける**
- 矛盾には**どの正式資料のどの記述と食い違うか**を必須にした。根拠を示せないものは矛盾欄に書かせない
- 逆反映候補を別枠で報告。採否は人間
- ファイルを一切変更しない。`review_feature.md` / `review_command.md` の正式なレビュー結果を代替しない

## 第5段階: 完全性レビュー用 prompt

### `prompts/review_prompt_integrity.md`

- 確認対象に2つの prompt のフローを追加
- **前提の「実装前に仕様・設計・フロー・テスト計画をそろえる」を、正式資料で意味を定義すべき変更に限定した表現へ改訂。** 未記載/矛盾の区別、人間の直接修正とAI権限の区別を前提へ追加
- レビュー目的に4項目追加（旧一本道の残存、人間直接修正禁止の残存、AI権限拡大、未記載だけを理由にした不整合扱い）
- 観点1に「『いきなり実装しない』をすべての変更が仕様書から始まる意味で使っていないか」を追加
- 観点2に**AI権限拡大の検出8項目**を追加
- 観点11を「コード変更影響分析フロー」→**「変更の意味と反映区分のフロー」へ改訂**し、反映区分と正本の扱いの検出項目を追加
- **観点 11-2（未記載と矛盾の区別）、11-3（逆反映）、11-4（コード先行）、11-5（2種類の prompt の役割分離）を新設**
- 観点12に、型の定義の一本化、未記載/矛盾の一本化、人間の行動範囲とAI権限の書き分けを追加
- 禁止事項に4項目追加（未記載だけを理由に指摘しない／AGENTS.md へ再集約しない／正本の概念を廃止しない／実装詳細を全部記録する方向へ戻さない）
- 実行時の注意の順序に新 prompt を追加

**このファイルを最後に変更した理由:** 先に変更すると改訂中の中間状態を誤検出し、後に変更しないと旧前提で全体を「矛盾」と判定するため。
