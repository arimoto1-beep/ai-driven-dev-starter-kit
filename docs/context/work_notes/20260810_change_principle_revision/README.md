# 作業メモ: 変更作業の基本原則の見直し（変更ルート・実施状態・未記載/矛盾の分離）

## 目的

変更管理の大原則を、次の一本道から見直す。

```text
いきなり実装しない → 変更前に分類・分析 → 正本を特定 → 正本から上流→下流へ反映
```

生成AIが作るコードには、同じ仕様・設計でも実装上の揺らぎ（関数の切り方、変数名、局所的な書き方など）がある。これらをすべて正式資料へ反映すると、設計書が実装詳細の写経になり、変更作業が過剰になる。

新しい中心原則は次。

```text
この変更は、正式資料で意味を定義・維持する必要があるか。
```

「どこから変更を始めたか」「誰が変更したか」ではなく、変更の**意味**で判断する形へ変える。

あわせて、人間がソースコードを直接修正することの禁止を解く。ただし、**それをAIの変更権限拡大へ転用しない**ことを明示する。

- 「類似機能間の実装方式の統一」のような、内容だけでは変更ルートが一意に決まらない変更例は、固定分類ではなく起点判定（正式資料から先に決めたか＝B、コードから気づいたか＝C、揺らぎの解消に留まるか＝A）で説明する。

**2026-08-11 追加分（軸の補正）:**

- 変更ルート（A〜C、または判断不能）と実施状態（未着手・一部実施・実施済み、コード先行の有無）を、独立した2軸として `docs/rules/core/10_workflow.md` に定義し直す。project と task では再定義せず、進め方だけを定める（この一本化の方針自体は継続）。
- コード先行を独立した変更ルートとして扱わない。ルートB・Cのどちらでも起こりうる「実施状態」として扱う。
- 「判断材料不足」を変更ルートと並ぶ型として扱わない。A〜Cを判定できない状態を表す「判断不能」という区分にする。
- 複数 feature にまたがる標準化・共通化を、内容だけを理由に機械的にルートCへ分類しない。「どこでその正式な意味を定義することになったか」（先に人間が正式資料から決めたか＝B、コードを比較していて気づいたか＝C）で判定する。
- ルートBの反映順を「仕様→設計→テスト計画」に固定しない。基本原則は「正本 → 必要な下流資料 → 実装 → テスト → レビュー」とし、正本が仕様以外（設計・フロー・共通設計など）の場合も扱えるようにする。

**2026-08-10 決定分（初回改訂。以下は現在も有効）:**

- 「未記載と矛盾の区別」は core に一本化し、review 系 prompt は参照のみとする。
- 正本の概念は廃止しない。ただし「すべてのコード変更に正本があるとは限らない」を明記する。
- 「正本候補なし」を2種類に分ける。実装詳細ならルートA（STOPにしない）、置き場がないだけなら従来どおり人間判断。区別できない場合も人間判断へ戻す。
- 人間の直接修正のために、新しい承認工程・専用の記録様式・毎回の作業メモ作成は新設しない。Git差分・コミット履歴・テスト・レビュー・既存の作業報告で足りる場合はそれを使う。
- AIのルート判定は「提案」まで。ルートAと判断したことを理由に、AI自身の作業範囲・保護対象・承認ゲートを動かせない。
- ルートAでも実装着手承認欄の確認は省略しない。
- 逆反映候補は、既存のレビュー結果テンプレートの「仕様変更が必要そうな点」で扱う。**テンプレートに新しい見出しを追加しない**（同期変更を増やさないため）。
- 新 prompt の名称は既存の `review_*` 規則に合わせて `review_design_code_consistency.md` とする。
- レビュー結果4値、次工程移行判定3値、条件付きGOの6項目は変更しない。
