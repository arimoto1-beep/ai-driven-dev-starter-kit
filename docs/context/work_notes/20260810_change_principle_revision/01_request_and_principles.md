# 元の依頼と、今回変更した大原則

## 元の依頼

利用者からの依頼は2段階だった。

### 1回目: 調査のみ（ファイル変更なし）

「AI駆動開発スターターキットの『変更作業の基本原則』を見直したい。今回は大原則に関わる変更なので、まだファイルを変更しないでほしい。現在のリポジトリを調査し、有効なルール体系・正本関係・task prompt・人向け導線を確認したうえで、影響範囲と改訂案を提示してほしい」

指定された調査観点（要約）:

- 現在のルール構造（core / project / task / 人向けの責務）
- 今回の原則の現在の正本
- 新しい考え方と衝突する箇所
- 維持すべき安全原則
- 改訂後の基本原則案
- ファイル別変更計画
- `analyze_code_change_impact.md` の再設計案
- バグフローへの影響
- 整合性レビュー観点
- 実装時の推奨順

### 2回目: 実装

1回目の調査結果を前提に、実際の改訂を依頼された。指定された実装順は core → project → task → 人向け文書 → 完全性レビュー。

追加で指定された主な内容:

- 設計⇔コードの意味上の整合を確認する汎用 prompt を新設する
- `analyze_code_change_impact.md` を、変更前後どちらでも使える羅針盤へ再設計する
- 人間の直接コード修正を禁止しない方向へ変える
- ただしAIの変更権限は広げない
- commit / push / branch 作成はしない

## 依頼の背景（利用者の問題意識）

利用者が言語化していた問題は次だった。

> 生成AIが作るソースコードには、同じ仕様・設計でも実装上の揺らぎがある。
> 関数の切り方、局所的な処理の書き方、変数名、冗長な処理の整理、設計上の意味を変えない内部実装、同じ意味を持つ複数の実装方法など。
> これらをすべて正式資料へ反映しようとすると、設計書が実装詳細の写経になり、変更作業も過剰になる。

もう一点。

> 人間がソースコードを直接修正すること自体を避ける必要もないと考え直した。
> 重要なのは「人間が直接コードを修正したか」「AIが修正したか」ではなく、その変更が何を意味するか。

利用者が最も強く念を押していたのは次の分離だった。

> 「人間が直接コードを直してよい」と「AIが好きなタイミングでコードを変更してよい」を混同しないでください。

これが今回の改訂で最も壊しやすい箇所であり、実装中も繰り返し確認した。

## 変更前の原則（何が強すぎたか）

調査時点の `docs/rules/core/10_workflow.md` は、変更作業を次の一本道として定義していた。

```text
変更を思いつく
  ↓ 分類が未確定なまま作業を始めない
分析専用工程で影響範囲を整理する（ファイル変更なし）
  ↓
変更内容を定義すべき「最上流かつ役割の合う資料」を特定 = 正本
  ↓ 正本が存在しない場合は人間判断へ戻す
正本から下流へ順に反映
  ↓
実装 → テスト → レビュー
```

すでに整備されていた点もあった。「上流優先＝すべての上流資料を変更する」ではないことは、旧 `core/10` にも `analyze_code_change_impact.md` にも明記されていた。ここは今回の思想と衝突しない。

不足していたのは次の4点だった。

1. **「正式資料が意味を定義していない実装詳細」という概念がなかった。** 旧 `core/10` は「変更内容を定義すべき資料を特定し、それを正本とする」と書いており、**常に正本が存在する**前提だった。存在しない場合は一律で人間判断へ流れる。
2. **コード起点で正式資料へ逆反映する経路が明文化されていなかった。** 補助記録（`docs/context/`）→正本の経路は `core/40` にあったが、コードで得た知見を昇格させる経路がない。レビュー結果の「仕様変更が必要そうな点」欄が事実上の受け皿だったが、正本側に位置づけがなかった。
3. **コード先行の扱いがなかった。** 一律に「正本から下流へ」であり、`implement_bug_fix.md` は「仕様・設計・テスト計画の変更が必要と判明したら STOP」だった。
4. **人間の直接コード修正が事実上禁止に近かった。** `project/50_ai_permissions.md` が「設計・仕様・**実装**・テスト・現在地メモに影響する修正は、人間が直接ファイルを編集するのではなく、AIに別作業として依頼することを基本」としており、「実装に影響する修正」はほぼ全コード変更を含む。人間が直接修正してよいのは誤字・表記ゆれだけだった。

## 変更後の大原則

### 中心の問い

```text
この変更は、正式資料で意味を定義・維持する必要があるか。
```

「どこから変更を始めたか」「誰が変更したか」を中心にしない。

### 変更の型（A〜E）

`docs/rules/core/10_workflow.md` に定義した。**ここが唯一の正本**であり、project と task は進め方だけを定める。

| 型 | 内容 |
|---|---|
| A. 実装詳細で完結する変更 | 正式資料が意味を定義していない範囲だけが変わる |
| B. 正式資料を正本として下流へ反映する変更 | 正式資料で定義・維持すべき意味が変わる |
| C. コードから正式資料へ逆反映する変更 | 今後も守るべき仕様・設計・共通方針だと分かった |
| D. コード先行 | 反映が必要だが、順序が後になった |
| E. 判断材料不足 | A〜Dを確定できない |

ひとつの作業に複数の型が混在する場合は、変更点を分けて扱う。無理にひとつへ押し込まない。

**型A と型D の混同を防ぐ記述を、core・project・task・人向けのすべてに入れた。** ここは利用者も明示的に注意していた箇所。

- 型A = 正式資料への反映がそもそも不要
- 型D = 反映が必要だが順序が後になった

### 未記載と矛盾の区別

| | 内容 | 扱い |
|---|---|---|
| 未記載 | 正式資料が実装詳細を規定していないが、意味には反していない | それだけでは問題としない |
| 矛盾 | 正式資料が定義している意味と食い違っている | 従来どおり問題 |

「設計書に書いてない」≠「設計書と矛盾している」。

**実装方式の揺らぎが存在すること自体を問題として扱わない**ことを明記した。ただし、次は「未記載だから問題なし」としない。

- 仕様にない便利機能
- 外部から見える動作の変更
- 責務・境界としての意味の変更
- 維持すべき呼び出し関係の変更
- 共通設計との食い違い

### 正本の2分岐

正本の概念は維持したうえで、「正本が見つからない」を2つに分けた。

| 状況 | 扱い |
|---|---|
| 正式資料がそもそも意味を定義していない実装詳細 | 型A。**「正本がないので STOP」としない** |
| 本来は正式資料へ残すべき意味だが、役割の合う置き場がない | 従来どおり人間判断。AIは新しい資料種別や配置場所を作らない |

**区別できない場合も、どちらかに断定せず人間判断へ戻す。**

### 人間による直接修正

人間がソースコードを直接修正することを禁止しない。修正後、必要に応じてどの型に当たるかを確認する。

新しい承認工程・専用の記録様式・毎回の作業メモ作成は新設しない。Git差分、コミット履歴、テスト、レビュー、既存の作業報告で足りる場合はそれを使う。

## 維持したもの（今回弱めなかった安全原則）

- AIの作業対象の限定、ついで修正の禁止、保護対象、レビューと修正の分離
- 承認境界（実装着手承認、バグ修正計画承認、AIが承認欄をチェックしない）
- `GO` / `条件付きGO` / `STOP` の3値、条件付きGOの6項目、AIが単独で「軽微」と確定しない
- レビュー結果4値と次工程移行判定の分離
- 正本の概念、正式資料の定義、成果物の3分類
- 補助記録を確定仕様として扱わない
- 仕様にない機能の追加禁止、不明点の暗黙補完禁止
- バグ対応の通常フロー（報告→調査→修正計画→人間承認→実装）
- 検証と作業報告、更新しなかった資料と理由の明示
- 旧AI作業ログと過去の作業メモを変更しない
- `AGENTS.md` を薄い入口のまま維持する
