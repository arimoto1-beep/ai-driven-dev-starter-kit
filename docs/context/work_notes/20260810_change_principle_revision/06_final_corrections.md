## 補正1（必須）: `analyze_code_change_impact.md` の自己矛盾

### 何が問題だったか

[analyze_code_change_impact.md](../../../../prompts/analyze_code_change_impact.md) は、変更ルートA〜Cを判定するプロンプトとして再設計されていたが、「他のプロンプトとの違い」節に次の記述が残っていた。

> `review_design_code_consistency.md` と役割を混同しないでください。**このプロンプトは変更を見ます。** 現在の正式資料とコードの整合そのものを確認したい場合は `review_design_code_consistency.md` を使ってください。**このプロンプトでは、変更ルート（A〜C）の判定を行いません。**

末尾の「このプロンプトでは、変更ルート（A〜C）の判定を行いません」は、直前の文脈（`review_design_code_consistency.md` を使ってください）を受けて「`review_design_code_consistency.md` は判定を行わない」と言うつもりの記述だったが、主語が読み取りにくく、「このプロンプト（analyze_code_change_impact.md 自身）は判定を行わない」とも読める自己矛盾になっていた。

### どう修正したか

単純な文言置換ではなく、2つのプロンプトの役割が明確に読める文章へ書き直した。

> `review_design_code_consistency.md` と役割を混同しないでください。**このプロンプトは変更を見て、変更ルート（A〜C、または判断不能）を判定します。** `review_design_code_consistency.md` は現在の状態を見るプロンプトであり、**変更ルートの判定は行いません。** 現在の正式資料とコードの整合そのものを確認したい場合は、変更ルートを判定するこのプロンプトではなく `review_design_code_consistency.md` を使ってください。

主語を明確にし、「このプロンプト（analyze）は判定する」「review_design_code_consistency.md は判定しない」の2文に分離した。

## 補正2（必須）: `project/20_workflow.md` に残る旧「工程の骨格」表現

### 何が問題だったか

`docs/rules/core/10_workflow.md` 側は前回の補正で「正本 → 必要な下流資料 → 実装 → テスト → レビュー」を基本骨格とし、「仕様→設計→…」を「正本が仕様の場合の一例」と明記済みだった。しかし `docs/rules/project/20_workflow.md` には、次の3箇所に、限定なしの旧表現が残っていた。

1. 冒頭の「このファイルに含めないもの」: `工程の骨格（仕様→設計→テスト観点→実装→レビュー） → docs/rules/core/10_workflow.md`
2. 「変更する場合の注意」: `core/10_workflow.md` の骨格（仕様 → 設計 → テスト観点 → 実装 → レビュー）から逸脱しないでください
3. 「関連するルール」: `工程の骨格 → docs/rules/core/10_workflow.md`

いずれも、ルートB全体が「必ず仕様から始まる」と読める記述だった。

### どう修正したか

3箇所とも、骨格の正しい定義（正本→必要な下流資料→実装→テスト→レビュー）を明記し、「仕様→設計→…」は正本が仕様である場合の一例だと分かる表現へ補正した。特に「変更する場合の注意」は次のように書き換えた。

> 工程を増減する場合も、`docs/rules/core/10_workflow.md` の骨格（**正本 → 必要な下流資料 → 実装 → テスト → レビュー**）から逸脱しないでください。この骨格は、**正式資料で意味を定義すべき変更（ルートB）** に適用されます。正本は仕様とは限りません。設計やフローが正本の場合はそこから始まり、仕様書を形式的に更新する必要はありません。「仕様 → 設計 → テスト観点 → 実装 → レビュー」は、正本が仕様である場合に生じる一例です。実装詳細で完結する変更（ルートA）まで、この骨格を通すことを求めるものではありません。

なお、[core/10_workflow.md](../../../../docs/rules/core/10_workflow.md) と [project/20_workflow.md](../../../../docs/rules/project/20_workflow.md) の「標準8ステップ」節（正本が仕様になる場合を主な例とする限定表現）は、前回補正時点ですでに正しく限定されていたため、今回は変更していない。

## 補正3（軽微）: コード先行の対象ルート

### 何が問題だったか

`docs/rules/project/20_workflow.md` の「変更を検討する場合」に、次の記述が残っていた。

> ルートA〜Cのいずれかがコード先行（正式資料への反映より先にコードを変更した状態）である場合は……

ルートAは正式資料が意味を定義していない実装詳細で完結する変更であり、そもそも「正式資料へ反映すべき内容をコードから先に実施した」という意味でのコード先行には該当しない。A〜Cすべてに適用されると読めるのは誤り。

### どう修正したか

対象を「ルートB またはルートC」に限定し、Aが該当しない理由を明記した。

> ルートB またはルートC の変更が**コード先行**（正式資料への反映より先にコードを変更した状態）である場合は、下記「コードを先に変更した場合」もあわせて確認します。**コード先行は独立したルートではなく、B または C の変更が先行して実施された状態です。ルートAは、正式資料への反映がそもそも不要な変更であり、この意味でのコード先行には該当しません。**

他の全ファイル（`core/10_workflow.md`、`analyze_code_change_impact.md`、`project/50_ai_permissions.md`、tutorial 030、tutorial 040、README、overview）を横断確認したところ、コード先行の対象は既にすべて「B・C」または「B/Cのどちらでも」と正しく限定されており、修正が必要だったのは `project/20_workflow.md` のこの1箇所のみだった。

## 補正4（軽微）: tutorial 030「類似機能間の実装方式の統一」

### 何が問題だったか

変更パターン表の該当行が、前回の補正で「AまたはC（起点による）」と整理されていた。しかし、この変更が持つ性質はBにもなりうる。

- **Aになる例**: 正式資料では統一方式を定めておらず、単に実装上の揺らぎをそろえるだけ。将来も守るべき共通ルールとしては扱わない
- **Bになる例**: 人間が先に「今後はこの方式を正式な標準として採用する」と決め、役割の合う正式資料へ定義してから下流へ反映する
- **Cになる例**: 複数のコードを比較・修正している途中で「この方式は今後も共通して守るべきだ」と気づき、正式資料へ逆反映する

「AまたはC」への固定は、Bという正当なケースを見落とす誤分類だった。

### どう修正したか

表の該当セルを「A・B・Cいずれもあり得る（起点による）」へ変更し、注意点欄に3ルートそれぞれの判定条件を明記した。

> **「他と違う」だけを理由に統一しない。** 差異が仕様由来かを先に確認する。単なる実装上の揺らぎをそろえるだけで、正式な意味として維持しないならルートA（実装だけ）で足りる。人間が先に「今後はこの方式を正式な標準にする」と決めて正式資料から変更するならルートB。コードを比較・修正している途中で「今後も共通して守るべきだ」と気づいたならルートC。**変更内容だけで固定せず、正式な意味として維持するか・どこを起点に決まったかで判定する。** すべての統一を正式資料へ残す方向にはしない。

同じ表の「複数 feature にまたがる標準化」「共通化候補」の2行は、前回補正時点ですでに「BまたはC（起点による）」と正しく整理されていたため、今回は変更していない。

「例2: 正常に動いているコードの改善案を整理する」の具体例（「ルートA にも ルートC にもなりえます」の箇所、`cli_hello_greeting` とのスタイル統一）は、その例自体がコード読解中に気づいた場面（Bの前提となる「人間が先に正式ルールと決める」場面ではない）として書かれているため、A/Cのままで矛盾はなく、変更していない。
