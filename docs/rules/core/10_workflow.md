# core: 進め方の原則

## このファイルの目的

AI駆動開発を、人間が理解・レビュー・引き継ぎ・責任を持てる形で進めるための、工程の骨格を定めます。

## このファイルを読む作業

- 仕様・設計・フロー・テスト計画などの文書を作成する作業
- 実装作業
- 変更の影響分析（**着手前・着手後のどちらでも**）
- 仕様変更を反映する作業
- 正式資料とコードの意味上の整合を確認する作業
- バグ対応の入口（報告・調査）

## このファイルに含めないもの

- 承認、停止判定、レビューの進め方 → `20_approval_and_review.md`
- 変更してよい範囲、保護対象 → `30_change_safety.md`
- 具体的な工程の並び（何ステップか、成果物のファイル名） → `docs/rules/project/20_workflow.md`
- 実装言語、テストコマンド、ディレクトリ配置 → `docs/rules/project/` の各ファイル
- 各工程の詳細手順と出力形式 → 対応する `prompts/*.md`

## ルール

### 段階的に進める

- **正式資料で意味を定義すべき変更について、意味を確定しないまま実装で既成事実を作りません。** その場合は、役割の合う正本を特定し、正本で意味を確定してから、必要な下流・実装・テスト・レビューへ小さく進めます（下記「変更ルート」の B を参照）。
- 仕様に書かれていない機能を勝手に追加しません。
- 不明点は勝手に決めず、仮定として明記します。
- 小さく設計し、小さく実装し、小さくテストします。人間がレビューできる単位に分けます。
- **この原則は、すべての変更を仕様書から始めることを求めるものではありません。** 「仕様 → 設計 → テスト観点 → 実装 → レビュー」は、正本が仕様である場合（多くは外部から見える動作の変更）に生じる順序の一例であり、すべての変更に適用される固定順序ではありません。正本が設計であれば設計から、正本が呼び出しフローであればフローから始まります。どの変更がここに当たるかは、下記「変更の意味を見極める」と「変更ルート」で判断します。

### 実装前後の整合確認

- 実装前に、対象機能の仕様書と設計書を確認します。
- 実装後に、正式資料が定義している意味と実装内容が**矛盾していないか**を確認します。
- **正式資料に書かれていない実装詳細が存在すること自体は、不整合ではありません。** 未記載と矛盾を区別します（下記「未記載と矛盾を区別する」）。
- 実装・修正の後に、プロジェクトで定めた検証を実施します。

### 未記載と矛盾を区別する

正式資料とコードの関係を確認するときは、次の2つを常に区別します。

| | 内容 | 扱い |
|---|---|---|
| **未記載** | 正式資料がその実装詳細を規定していない。コード側に具体的な実装が存在するが、正式資料が定義する意味には反していない | **それだけでは問題として扱いません** |
| **矛盾** | 正式資料が定義している外部動作・入出力・制約・エラー契約・責務・境界・維持すべき呼び出し関係・共通設計・テスト上維持すべき条件と、コードの意味が食い違っている | **従来どおり問題として扱います** |

**「正式資料に書かれていない」ことと、「正式資料と矛盾している」ことは別です。**

生成されたコードには、同じ仕様・設計でも実装上の揺らぎ（関数の切り方、局所的な書き方、変数名、同じ意味を持つ複数の実装方法など）があります。**揺らぎが存在すること自体を問題として扱いません。** 問題として扱うのは、上表の「矛盾」に当たる根拠を示せる場合です。

### 責務の分離

- 入口処理と業務ロジックの責務を分け、入口を薄く保ちます。
- 文書の分割単位を、実装都合だけで決めません。
- 仕様・実装・テストの対応関係を、後から追える構成にします。

### 理解できる複雑さに保つ

- **成果物と実装は、プロジェクトが想定する読者・保守者が理解できる複雑さに保ちます。**
- **必要性を説明できない抽象化や複雑化を追加しません。**
- 想定読者と、採用してよい設計スタイルはプロジェクトが定めます（`docs/rules/project/30_development_rules.md`）。
- プロジェクトが具体値を定めていない場合も、この原則自体は適用されます。説明できない複雑化は、プロジェクト設定の有無にかかわらず追加しません。

### 変更の意味を見極める

変更を扱うときの中心となる問いは、次です。

```text
この変更は、正式資料で意味を定義・維持する必要があるか。
```

- **「どこから変更を始めたか」や「誰が変更したか」を中心に判断しません。** 中心は、その変更をどこまで正式な意味として残す必要があるかです。
- 見極めは、変更に着手する前でも、着手した後でも行えます。**着手前の分析だけを唯一の入口としません。**
- 見極めの材料として、少なくとも次を確認します。
  - 外部から見える動作が変わるか
  - 入力・出力・制約・エラー契約が変わるか
  - 機能や層の責務・境界が変わるか
  - 呼び出し関係や処理フローとして維持すべき意味が変わるか
  - 複数機能で守るべき共通設計・共通方針になるか
  - テスト観点として正式に維持すべき条件が変わるか
  - 将来の実装でも守らせる必要がある内容か
  - 単なる実装詳細・実装上の選択肢に留まるか
  - 現在の正式資料と矛盾していないか
- バグなのか、仕様変更なのか、内部設計の改善なのかが未確定な場合は、**分類を確定させないまま結論を出しません。** 判断できない材料は「不明」として残します。
- 分析の結果の採否と、次に進むフローは人間が決めます。
- 仕様どおりに動いているが期待と違う場合は、バグではなく仕様変更候補として扱います。
- 影響分析を専用の工程として行う場合、**その工程ではファイルを変更しません。**

### 変更ルートと実施状態を分けて扱う

変更を整理するときは、**2つの異なる軸**を混同しません。

- **変更ルート**：この変更を、正式資料でどう扱うべきか（A〜C、または判断不能）
- **実施状態**：この変更が、実際にどこまで進んでいるか（未着手・一部実施・実施済み、コード先行の有無）

この2軸は独立しています。**「コードから正式資料へ逆反映する変更（ルートC）」と「コード先行」は、同じ変更に同時に当てはまります。** 人間がコードを先に直し、その結果として「今後も守るべき意味だ」と分かって正式資料へ反映する場合、変更ルートは C、実施状態はコード先行済みです。コード先行を独立した変更ルートとして扱うと、同じ変更が C になったり別の型になったりし、分類が安定しません。

### 変更ルート

変更は、必ずしも上流から始まりません。少なくとも次のルートがあります。

| ルート | 内容 |
|---|---|
| **A. 実装詳細で完結する変更** | 正式資料が意味を定義していない範囲だけが変わる。可読性の改善、冗長な処理の整理、局所的なリファクタリング、正式資料で規定していない実装方式の変更など |
| **B. 正式資料を正本として下流へ反映する変更** | 正式資料で定義・維持すべき意味が変わる。外部から見える動作、責務、制約、処理フロー、共通設計など |
| **C. コードから正式資料へ逆反映する変更** | コードを読み、あるいは修正・検証した結果、単なる実装詳細ではなく今後も守るべき仕様・設計・共通方針だと分かった内容を、正式資料へ反映する |

**ひとつの作業に複数のルートが混在する場合は、変更点を分けて扱います。** 無理にひとつのルートへ押し込みません。

**A. 実装詳細で完結する変更**

- 正式資料を無理に変更しません。**正式資料に書かれていない実装詳細が変わったことを、不整合として扱いません。**
- ただし、コードとテストの整合、必要な検証、通常必要となるレビューと報告は省略しません。
- **正式資料と矛盾する変更を、このルートとして扱いません。**

**B. 正式資料を正本として下流へ反映する変更**

- 変更内容を定義すべき**最上流かつ役割の合う資料**を特定し、それを変更内容の**正本**とします。
- 正本で意味を確定し、**必要な下流資料**・実装・テストへ反映します。基本の流れは「正本 → 必要な下流資料 → 実装 → テスト → レビュー」です。
- **正本が仕様以外の場合もあります。** 正本が設計であれば設計から、正本が呼び出しフローであればフローから、正本が共通設計であれば共通設計から始まります。「必ず仕様から始める」という意味ではありません。
- **上流資料を形式的にすべて変更しません。** 変更不要な資料は更新せず、更新不要と判断した理由を明示します。正本が設計であれば、外部動作が変わらない限り仕様書を無理に更新しません。
- 設計書・実装・テストを一括でまとめて修正しません。影響範囲を洗い出してから、資産ごとに更新要否を確認します。

**C. コードから正式資料へ逆反映する変更**

- 得た知見のうち、**今後も守るべき意味を持つものだけ**を、役割の合う正式資料へ反映します。
- **コードから見つかったものを何でも正式資料へ昇格させません。** 昇格させる場合は、なぜ今後も守るべき意味なのかを示します。
- 反映先を決めた後、そこからさらに下流への反映が必要かを確認します。
- **起点で機械的に決めません。** 複数機能にまたがる標準化や共通化であっても、正式資料からその方針を決めた場合はルートBです。コードを比較していて気づいた場合にルートCになります。「標準化・共通化だから常にC」ではなく、「どこでその正式な意味を定義することになったか」で判定します。

### 実施状態

変更ルートとは別に、変更がどこまで進んでいるかを記録します。

- **未着手**：まだ変更していない
- **一部実施**：一部のファイルだけ変更済み
- **実施済み**：変更が完了している

さらに、必要に応じて次を記録します。

- **コード先行**：あり／なし
- **コード先行の理由**：障害対応／時間制約／検証目的／その他／該当なし

**コード先行は、変更ルートではなく実施状態です。** 本来は正式資料への反映も必要な内容について、コードを先に変更した状態を指します。

- **コード先行そのものを禁止しません。**
- コード先行がある場合、その変更ルートが B または C であれば、後から正式資料へ反映し、必要なテストとレビューを行います。
- **未反映事項を残したまま、作業を完了として扱いません。** 未了項目は残課題として明示します。
- **ルートA と混同しません。** ルートA は正式資料への反映がそもそも不要な変更です。コード先行は「反映が必要だが順序が後になった」という状態であり、ルートAには本来当てはまりません。

### 判断不能

変更ルート（A〜C）のいずれかを確定できない場合は、無理にA〜Cへ分類せず、**判断不能**として扱います。

- 断定せず、不足している情報と、人間が判断すべき事項を提示します。
- 判断不能は変更ルートと並ぶ4つ目の型ではなく、A〜Cを判定できない状態を表す区分です。

### 変更の正本と、正本を持たない変更

- **正本の概念は維持します。** 変更内容を正式に定義する資料を特定し、下流がそれを参照・具体化する関係は変わりません。
- ただし、**すべてのコード変更に、変更対象となる正式資料があるとは限りません。** 適切な正本が見つからない場合は、次の2つを区別します。

| 状況 | 扱い |
|---|---|
| **正式資料がそもそも意味を定義していない実装詳細である**（ローカル変数名、設計書が規定していない範囲の関数分割、同じ意味を保つ実装方式の変更、局所的な可読性改善など） | ルートA として、正本を持たずにコードとテストだけで変更が完結してよい。**「正本がないので STOP」としません。** 正式資料を変更しない理由と、コードとテストだけで完結できる根拠を示します |
| **本来は正式資料へ残すべき意味だが、役割の合う置き場が現在の構成に存在しない**（複数機能で守るべき新しい共通方針、既存の横断設計の責務に当てはまらない横断ルール、新しい種類の正式な設計判断など） | 従来どおり**人間判断**が必要。AIは新しい資料種別や配置場所を勝手に作りません。選択肢を整理して人間判断へ戻します |

- **この2つを区別できない場合も、どちらかに断定せず人間判断へ戻します。**

### 人間による直接修正と、AIの変更権限

- **人間がソースコードを直接修正することを禁止しません。**
- 重要なのは、誰が修正したかではなく、**その変更が正式資料で維持すべき意味を持つか**です。人間が直接修正した場合も、上記の見極めを行い、必要な場合は正式資料へ反映します。
- 人間の直接修正のたびに、新しい承認工程や記録を一律に増やしません。Git差分、コミット履歴、テスト、レビュー、既存の作業報告など、通常の運用で足りる場合はそれを使います。
- **これはAIの変更権限を広げるものではありません。** AIは引き続き、今回の作業で許可された範囲だけを変更します。次は別の問題として維持されます。
  - AIが調査中・レビュー中に修正すること
  - AIが今回の task で許可されていないファイルを変更すること
  - AIが保護対象を変更すること
  - AIが人間判断事項を確定すること
  - AIがついで修正を行うこと
- **AIは変更ルートと実施状態を分析結果として判断・提案できます。** ただし、**その判断を理由に、AI自身の作業範囲を広げたり、保護対象を変更したり、人間の承認なしに次工程へ進んだりしてはなりません。**

### バグ対応の段階

バグを発見しても、いきなり修正しません。次の段階に分けて進めます。

```text
報告 → 調査 → 修正計画 → 人間承認 → 実装
```

各段階で作成する文書と、承認の扱いは `20_approval_and_review.md` と `docs/rules/project/20_workflow.md` を参照してください。

**この基本ルートは、コード先行を理由に省略できません。** 障害対応などでコードを先に修正するかどうかを選ぶのは人間です。**AIが自ら「緊急だからコード先行にする」と判断して、この基本ルートを迂回してはなりません。**

### 検証の粒度

- 検証は粒度ごとに確認対象を分けます。細部のロジックと、つなぎ込みを同じ試験で確認しません。
- すべての粒度を常に実施する必要はありません。必要な範囲だけ実施します。
