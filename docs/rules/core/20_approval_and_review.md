# core: 承認とレビュー

## このファイルの目的

AIが人間の承認と判断を代行しないための境界と、工程を止める判断の基準を定めます。

## このファイルを読む作業

- 実装作業（承認ゲートを通る作業）
- 各種レビュー作業
- バグ修正の実装
- 工程の区切りで、次へ進んでよいかを判定するとき

## このファイルに含めないもの

- 承認欄の具体的なファイル名と場所 → `docs/rules/project/50_ai_permissions.md`
- レビュー結果の保存先 → `docs/rules/project/10_document_structure.md`
- 承認を置く工程の位置 → `docs/rules/project/20_workflow.md`
- 各レビューの確認観点と出力形式 → 対応する `prompts/review_*.md`

## ルール

### 承認境界

- **人間の承認が完了していない作業を開始しません。**
- **AIは、自分に対する承認を自ら記録しません。** 承認欄にチェックを入れるのは人間です。
- **承認の前提となる未決事項が残っている場合、承認済みとして扱わず停止します。** 承認そのものについては、条件付きで進むという扱いをしません。

なお、承認とは別に、工程の区切りで「次工程へ進んでよいか」を判定します。そこでは条件付きで進める場合があります。両者の関係は下記「未決事項と判定の関係」を参照してください。

### レビューと修正の分離

- レビュー作業と修正作業を分けます。**レビュー中・調査中は、レビュー結果を記録するファイル以外を変更しません。**
- 既存のレビュー結果があっても、古い判定をそのまま採用せず、現在の状態を読み直して再レビューします。
- 指摘を見つけても、その場で勝手に修正しません。
- **AIは、人間が承認した指摘だけを対象に修正します。**

### 指摘を反映した後

- **指摘を反映した後は、人間が再レビューの要否を判断します。** すべての反映後に再レビューを必須とはしません。
- **AIは、再レビューの要否を独断で確定しません。** 必要と考える場合は、作業報告で提案するにとどめます。
- 再レビューを実施する場合は、**変更後の現在の状態を読み直して確認します**（上記「古い判定をそのまま採用しない」に従います）。
- 反映と再レビューは別の作業です。同じ作業の中で混ぜません。

### 2種類の判定を区別する

レビュー結果の評価と、次工程移行判定は目的が異なります。

- **レビュー結果**は、成果物の状態を表します。
- **次工程移行判定**は、未解決事項や人間判断待ちを含めて、次の工程へ進んでよいかを表します。

成果物に大きな問題がなくても、人間判断待ち、承認の前提となる未決事項、安全に次工程へ進めない未決事項、または整理されていない未解決事項が残っている場合は、次工程へ進んではなりません。
この2つを混同しないでください。

**レビュー結果の評価値は、プロジェクトが定めます。次工程移行判定の値は、共通で固定します。**
このプロジェクトのレビュー結果の評価値は `docs/rules/project/25_review_policy.md` にあります。

### 次工程移行判定

次工程へ進む前に、以下を確認します。

**確認するのは「未解決事項が存在しないこと」ではなく、「未解決事項が整理されていること」です。**

- 要検討項目・未解決項目が残っている場合、**分類と判定根拠が整理されているか**
- 人間判断待ちの項目が残っていないか
- 承認の前提となる未決事項が残っていないか
- 安全に次工程へ進めない未決事項が残っていないか
- **未対応の指摘が残っている場合、その扱いと次工程への影響が整理されているか**
- AIが仕様未確定の内容を暗黙に補完していないか

判定は、以下の3つのいずれかで出力します。**この3値はプロジェクトで変更しません。**

- **GO**：次工程へ進んでよい
- **条件付きGO**：未解決項目が残るが、後続工程への影響を明記したうえで進んでよい
- **STOP**：次工程へ進んではならない。何を解決すれば進めるかを明記して停止する

### 記録したことと、解決したことを区別する

「要検討として記録した」ことは、「解決した」ことではありません。
要検討項目・未解決項目・人間判断待ち項目が1件以上残っている場合、それらを**無視して**次工程へ進んではなりません。

無視しないとは、下記の分類へ整理し、判定の根拠として明示することです。
**整理せずに進むことと、整理したうえで条件付きで進むことは別です。**

### 未決事項の分類

次工程へ進む前に、各項目を以下のいずれかへ整理します。

- **解決済み**
- **今回スコープ外**
- **仮決定**（仮置き内容・理由・リスク・見直し条件を明記する）
- **人間判断待ち**

### 未決事項と判定の関係

**未解決事項が存在すること自体は、直ちに STOP を意味しません。** 問題になるのは、未解決事項が整理されていない状態、または性質上そもそも先送りできない状態です。

```text
未解決事項が存在する
  → それだけでは直ちに STOP とは限らない

未解決事項が未整理 ／ 人間判断待ち ／ 承認の前提 ／ 安全に進めない
  → STOP

未解決事項が整理済みで、条件付きGO の6項目を満たし、安全に進める根拠がある
  → 条件付きGO が可能
```

**次のいずれかが残る場合は STOP とします。**

- 未解決事項が整理されていない（分類がない、影響が整理されていない、仮置きの理由がない、見直し条件がない）
- 人間判断待ちの項目
- 承認の前提となる未決事項
- 安全に次工程へ進めない未決事項（後続工程への影響を説明できないもの、影響が管理できないものを含む）

**その他の未解決事項**は、下記「条件付きGO とする場合」の6項目をすべて満たし、後続工程への影響が管理できる場合に限り、**条件付きGO** として扱えます。

条件付きGO について、次を守ってください。

- **条件付きGO は、未決事項を無視するための判定ではありません。**
- **安全に次工程へ進める根拠を説明できる場合だけ**使います。説明できないものは STOP です。
- 未決事項を記録しただけで解決したものとして扱いません。
- **AIが単独で「軽微」と確定して条件付きGO にしません**（下記参照）。
- 人間判断待ちが残る場合は、原則として STOP です。

### 条件付きGO とする場合

条件付きGOとする場合は、以下の6項目を必ず明記します。

- 未解決項目
- 仮置きする内容と理由
- 条件付きでも進める理由
- 後続工程への影響
- 見直しが必要になる条件
- 人間判断が必要かどうか

### AIが単独で「軽微」と確定しない

これは、**個別の未決事項**（仕様影響・設計影響・利用者導線への影響などを含む）を、AIが単独で軽微と判断してはならない、という禁止です。

「影響は軽微」と判断して条件付きGOにする場合でも、その判断自体が仕様・設計・利用者導線に関わる場合は、人間判断待ち（STOP）として扱います。

**AIが単独で「軽微」と確定し、未決事項を解決済みとして扱ってはなりません。**

「軽微」という語は、次の3つの異なる場面で使われます。混同しないでください。

| 場面 | 誰が判断するか | 正本 |
|---|---|---|
| 個別の未決事項が軽微かどうか | **AIは判断しない**（人間判断待ち／STOP） | このファイル |
| 成果物全体のレビュー結果としての評価 | プロジェクトが定めた評価値を、レビュー作業で付与する | `docs/rules/project/25_review_policy.md` |
| 変更内容そのものが軽微かどうか（誤字修正など） | **人間が判断する** | `docs/rules/project/50_ai_permissions.md` |

成果物全体のレビュー結果がどうであっても、それだけを理由に次工程移行判定を `GO` にしてはなりません。次工程移行判定は、このファイルに従って別に行います。

### STOP とする場合

STOPとする場合は、**次工程の成果物を作成せず**、何を解決すれば進めるかを明記して停止します。

作業の途中で、仕様・設計・テスト計画の更新が必要と判明した場合も、作業を中断して STOP し、別作業として報告します。
