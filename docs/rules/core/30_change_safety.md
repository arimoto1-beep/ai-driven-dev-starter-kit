# core: 変更範囲と安全性

## このファイルの目的

AIが、今回許可された範囲の外を変更しないための境界を定めます。

## このファイルを読む作業

- 実装作業
- バグ修正
- 共通設計の作成・更新
- 共通化の提案
- 変更に着手する前の影響分析

## このファイルに含めないもの

- 保護対象の具体的な一覧 → `docs/rules/project/50_ai_permissions.md`
- 許可依存、実装言語、共通処理の置き場 → `docs/rules/project/30_development_rules.md`
- 今回の作業で変更してよいファイル → 対応する `prompts/*.md`（作業範囲の指定であり、保護対象とは別のレイヤです）
- 承認と停止の判断 → `20_approval_and_review.md`

---

## ルール

### 作業対象の限定

- **今回の作業対象外のファイルを、都合で勝手に変更しません。**
- 承認済みの計画に記載された範囲だけを変更します。
- 実装しにくい、テストしにくいと判断した場合でも、対象外のファイルを勝手に変更しません。必要な見直しは作業報告に記載し、人間レビューに回します。

### ついで修正の禁止

- **AIも人間も、レビュー中・調査中・説明中に、ついで修正やこっそり修正を行いません。**
- 影響のある修正は、別の作業として扱います。

### 保護対象

- 変更に人間の明示指示を要するファイル群（保護対象）をプロジェクトで定めます。
- **AIは、保護対象を明示指示なしに作成・更新しません。**
- ルール文書そのものの更新は、人間の明示的な依頼があった場合に限り、必要最小限で行います。AIが自らの判断でルールを書き換えません。

### 範囲外資産と依存

- プロジェクトが範囲外と定めた資産を、AIが勝手に追加しません。
- プロジェクトが許可した依存以外を、勝手に追加しません。
- 必要だと感じた場合も実装せず、**今後の拡張候補・提案として記録**します。

### 共通化と横断的な取り決め

- 共通化候補があっても、勝手に共通モジュールへ切り出しません。提案として記録します。
- 判断に迷う場合は、まず機能内に閉じた実装を優先します。
- **AIは、複数の機能に影響する取り決めを、個別機能の文書や実装の中で勝手に定義しません。**
- **横断的な取り決めだと判断できる内容は、プロジェクトが定めた横断設計の管理対象として提案します。**
- **プロジェクトが定めた対象一覧にないからといって、個別機能内で勝手に確定しません。** 一覧は判断材料であり、網羅を保証するものではありません。一覧にない場合は、横断設計の対象に加えるかどうかを人間判断へ回します。
- 既存の横断設計を、明示指示なしに変更しません。

共通化を提案する場合は、以下を明記します。

- 候補となる処理
- 想定される共通化先
- 共通化を検討する理由
- 影響を受ける機能
- 現時点で共通化すべきかどうか

### 固定ルールと個別依頼を分ける

- 固定の作業ルール（プロンプトなど）と、都度の依頼情報を分けて管理します。
- **固定の作業ルールを、個別作業のたびに書き換えません。** 今回固有の情報は、依頼側で渡します。

### 無関係な文脈を持ち込まない

- **AIは、今回の作業と無関係な案件・組織・会話の文脈を、成果物へ持ち込みません。**
- 以前の会話や他の案件で得た前提を、今回の成果物へ暗黙に混入させません。
- 成果物に含めてよい情報の範囲は、プロジェクトが定めます。
