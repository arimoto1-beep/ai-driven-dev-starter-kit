# project: 実装ルール（何で作るか）

## このファイルの目的

このプロジェクトの技術構成と実装規約、層ごとの責務分担を定めます。

## このファイルを読む作業

- feature 実装、entrypoint 実装
- ソースレビュー
- 関数設計、フロー作成
- 共通設計の作成・更新

## このファイルに含めないもの

- テストの実行方法と試験の単位 → `40_testing_rules.md`
- 保護対象、AIの更新権限 → `50_ai_permissions.md`
- 成果物の配置 → `10_document_structure.md`
- 共通化を勝手に行わない原則 → `docs/rules/core/30_change_safety.md`

## 現行スターターキットの初期値

### 言語と依存

- 実装コードでは、**Python 標準ライブラリのみ**を使用します。
- 単体テストでは `pytest` を使用してかまいません。
- **許可依存は `pytest` のみ**です。`requirements.txt` には、単体テスト用の `pytest` 以外の依存を追加しません。

### 実装規約

- CLI引数の解析には `argparse` を使います。
- ファイル名と関数名はスネークケースにします。
- 複雑なクラス設計は避け、まずは関数中心で実装します。
- **想定読者は初学者**です。初学者が読んでも理解しやすいコードにします。
- 仕様にない便利機能を追加しません。

### 責務分担：entrypoint と features

`src/<command_or_app_name>/entrypoint.py` は入口として薄く保ちます。

entrypoint の責務:

- CLI引数を受け取る
- `features/` 配下の機能を呼び出す
- 結果を標準出力に出す
- 終了コードを返す

entrypoint に入れてはいけないもの:

- 業務ロジック本体
- 複雑な変換処理
- 機能固有の判断
- 共通化候補の実装
- 仕様にない便利機能

機能実装は `src/<command_or_app_name>/features/<feature_name>.py` に置きます。
複数 feature を束ねる場合は、`argparse` の `subparsers` を使い、サブコマンド名と feature 呼び出しを1対1で対応させます。

### 共通処理の置き場

- 共通処理の置き場は `src/common/` です。**保護対象です**（`50_ai_permissions.md` を参照）。
- 共通化提案の置き場は `docs/common/` です。

### 共通設計で扱う対象

次は、feature 個別の設計書に書かず、共通設計として扱います。

- DBテーブル、DBカラム、DB制約、DBインデックス、トランザクション方針
- ファイル形式、ディレクトリ構成
- 共通データ項目、ID体系、ステータス定義
- 共通ログ形式、共通エラー形式

DBを利用する feature は、`common_design/33_db_design.md` を参照し、その範囲内で設計・実装します。

**この一覧は判断材料であり、網羅を保証するものではありません。** 一覧にない内容でも、複数機能に影響する取り決めだと判断できる場合は、個別機能内で確定させず、横断設計の対象に加えるかどうかを人間判断へ回してください（`docs/rules/core/30_change_safety.md`）。

### プロンプトの利用方法

- `prompts/` 直下には、実プロジェクトでも使う汎用プロンプトだけを配置します。
- `prompts/*.md` は直接編集しません。チャットで「参照するプロンプトのパス」と「対象機能情報」を渡して使います。
- チュートリアルでも汎用プロンプトを参照して使います。チュートリアル専用プロンプト置き場は作成しません。
- 渡す情報の項目と依頼例は `docs/how_to_use_prompts.md` を参照してください。

## 変更する場合の注意

- 言語や依存を変更する場合、`docs/rules/core/30_change_safety.md` の「許可された依存以外を勝手に追加しない」という原則は変わりません。**許可リストの中身だけを書き換えてください。**
- 想定読者や設計スタイルを変更する場合も、`docs/rules/core/10_workflow.md` の「理解できる複雑さに保つ」は変わりません。**想定読者と採用してよい設計スタイルの具体値だけを書き換えてください。** 「必要性を説明できない抽象化や複雑化を追加しない」という歯止めは、具体値を変えても適用されます。
- 共通設計で扱う対象を変更する場合も、`docs/rules/core/30_change_safety.md` の「対象一覧にないからといって個別機能内で勝手に確定しない」は変わりません。
- CLI以外の入口形態（API、バッチなど）に変更する場合、entrypoint の責務リストを書き換えてください。ただし「入口処理と業務ロジックの責務を分ける」という core の原則（`docs/rules/core/10_workflow.md`）は維持してください。
