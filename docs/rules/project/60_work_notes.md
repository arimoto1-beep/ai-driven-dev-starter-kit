# project: 作業メモ（保存方法と運用）

## このファイルの目的

このスターターキットにおける作業メモの保存場所・保存単位・README形式・付随ファイルの扱い・作成条件・AI権限・完了後の更新方法を定めます。

**このファイルは、このスターターキットにおける作業メモ運用の正本です。** 他の project ルールへ、ここに書く詳細を複製しません。

## このファイルを読む作業

- `prompts/prepare_work_note.md` を実行する作業
- 作業メモの作成候補を判断するとき
- 作業完了報告で作業メモ作成を提案するかどうか判断するとき

## このファイルに含めないもの

- 作業メモに共通する原則（プロジェクト非依存） → `docs/rules/core/60_work_notes.md`
- 成果物3分類における位置づけの定義そのもの → `docs/rules/core/40_official_docs_and_context.md`
- `docs/context/work_notes/` という置き場の存在と一覧上の分類 → `10_document_structure.md`（ここでは配置の存在だけを示し、詳細はここへ委譲される）
- テンプレート対応表への登録 → `15_document_templates.md`（ここでは詳細運用だけを扱う）
- 保護対象一覧への登録 → `50_ai_permissions.md`（ここでは詳細運用だけを扱う）

## ルール

### 保存場所

保存場所は次です。

```text
docs/context/work_notes/
```

各作業メモは、テーマ単位のフォルダとして保存します。

```text
docs/context/work_notes/YYYYMMDD_<short_name>/
```

- `YYYYMMDD` は作業開始日です。
- `<short_name>` は、内容が識別できる短い名前とします。英小文字、数字、アンダースコアを基本とし、過剰に長くしません。
- 複数日にまたがってもフォルダ名の日付は変更しません。

### 保存単位

1日単位ではなく、**作業テーマ単位**とします。

- 同じテーマが複数セッション・複数taskにまたがる場合は、原則として同じフォルダへ記録します。
- 派生した作業が次のいずれかに該当する場合は、別フォルダへ分けられます。
  - 独立して完了判定できる
  - 別の担当者や別の時期へ引き継がれる
  - 元の作業と現在地を分離した方が理解しやすい
- 分けた場合は、両方の README.md から相互参照します。

### README.md

各作業フォルダには、必ず README.md を置きます。

README.md は、詳細記録の要約版ではなく、**入口・現在地・索引**です。

**必須項目**

- 目的
- 状態
- 現在地
- 決定事項
- 未決事項
- 次に行うこと
- 付随ファイル一覧

状態は、次のいずれかとします。

- 進行中
- 中断
- 完了

**任意項目**

- 作業期間
- 関連する正式文書
- 関連する作業メモ
- 完了後の追記

該当しない任意項目は省略できます。

付随ファイルを追加・削除・名称変更した場合は、README.md の付随ファイル一覧も更新します。

付随ファイル一覧は、次の程度の簡潔な形式とします。

```text
| ファイル | 内容 |
|---|---|
| `investigation.md` | 調査の経緯と結果 |
```

「このファイルにしか書かれていないこと」のような、運用負担が大きい列は必須にしません。

具体的なひな形は `docs/templates/work_note_readme_template.md` を参照してください。

### 付随ファイル

付随ファイルは、作業内容に応じて自由形式の Markdown として作成できます。

例:

- `investigation.md`
- `decisions.md`
- `implementation_notes.md`
- `review_notes.md`
- `troubleshooting.md`
- `rejected_options.md`
- `timeline.md`

ファイル名や種類を固定しすぎません。本文の見出し構成も固定しません。

ただし、次は満たします。

- ファイルの目的がタイトルまたは冒頭で分かる
- 確認した事実、推測、未確認を区別する（`docs/rules/core/60_work_notes.md`）
- 付随ファイルを README.md から参照する
- 正式仕様やルールの正本であるように記述しない
- 別目的の内容が混在して読みにくくなった場合は分割する
- 長いという理由だけで機械的に分割しない

**付随ファイル用の固定テンプレートは作成しません。** 作成日・記録主体・種別等のメタ情報は、有用な場合に記載できますが、すべての付随ファイルへ一律強制しません。

### 作成候補になる条件

次のいずれかに該当した場合、AIは作業完了報告で作業メモの作成を提案できます。

1. 人間が作業メモの作成を明示した
2. 複数セッションまたは複数taskにまたがり、次回への引き継ぎが必要になった
3. 判断理由や調査経緯が、正式文書やGit差分だけでは残らない
4. ミス、見落とし、手戻り、AI報告と実態との差異、原因未確定の問題が発生した

**上記へ該当するかはAIが判定します。実際に作業メモを作るかどうかは人間が決定します。**

どの条件にも該当しない小さな作業では、AIは作業メモの作成を毎回機械的に提案しません。

### 記録対象と粒度

作業メモとして何を1つの単位にまとめるか、どこまで詳しい粒度で残すかは、**人間が最終決定します。** これは `prompts/prepare_work_note.md` 固有の手順ではなく、このスターターキットにおける作業メモ運用そのものの方針です。

- AIは、記録対象の範囲と粒度の候補を提案できます。
- **AIは、人間が指定した対象範囲を、独自に広げたり縮めたりしません。**
- 次のように複数の解釈がありうる場合は、本文を作成する前に人間へ確認します。
  - どこからどこまでを1つの作業メモにするか
  - 別テーマとして分けるべき作業が混在していないか
  - 作業者AI単位の記録も別に残すか
  - 詳細な経緯まで残すか、主要判断だけにするか

### AIの利用形態

作業メモを構成するにあたり、AIを「指示側」と「作業側」に分けることは**必須ではありません。**

- 1つのAIだけで作業している場合は、そのAIが作業メモを構成できます。
- 複数のAIを使い分けている場合、通常は作業全体の経緯を把握しているAIが作業メモを構成します。このAIを「指示側AI」と呼んでもかまいませんが、必須のシステム構成として固定するものではありません。
- 作業者AIの作業完了報告は、作業メモを構成するための**入力資料**として使います。作業者AI自身に、担当範囲を超えた作業全体の要約を求める必要はありません。
- 作業者AI単位の記録を別に残すかどうかも、人間が決定します。

### リポジトリ参照可否

作業メモを構成するAIがリポジトリを参照できるかどうかは問いません。

- リポジトリを参照できる場合は、必要な範囲で実ファイル・Git差分・Git状態・正式文書を確認します。
- リポジトリを参照できない場合でも、作業メモ案を構成できます。この場合、提供された会話・作業報告・資料を根拠とします。
- どちらの場合も、**リポジトリで確認できていない内容を確認済みの事実として扱いません。** 確認できない事項は未確認のまま残します。

### 新規作成と更新

AIが作業メモを新規作成・更新できる条件（何が人間の明示指示に当たるか、保存できるAIとできないAIでの扱いの違いを含む）は `docs/rules/project/50_ai_permissions.md` の「作業メモの更新権限」を正本とします。ここでは複製しません。

進行中・中断状態では、情報を失わない範囲で README や付随ファイルを整理・更新できます。

完了状態では、次のとおりとします。

- 原則として日付付きの追記を使う
- 過去の経緯を現在の状態へ合わせて消さない
- 明白な誤記は、人間の明示指示により訂正できる
- 訂正した事実と理由を残す

### 正本との関係

作業メモへ決定事項が書かれていても、それだけで正式仕様へ反映されたことにはなりません。

- 正式文書への反映が必要な場合は、**別の正式な変更作業**として実施します。
- 作業メモを根拠に、AIが自動的に仕様、設計、ルール、レビュー結果を更新してはいけません。

この扱いは `docs/rules/core/40_official_docs_and_context.md` の「補助記録から正式資料への反映」と同じ原則です。

### context レビューとの関係

`docs/context/work_notes/` は、通常の context 整合性レビュー（`prompts/review_context.md`）における**横断探索対象へ含めません**。作業メモは、通常作業で常に全件読ませる資料ではありません。**通常作業で `docs/context/work_notes/` 全体を横断探索してはいけません。**

作業メモを参照してよい条件は、次の4条件です。**このスターターキットにおける参照条件は、このファイルを正本とします。** `prompts/review_context.md` はこの条件に従う task 手順であり、条件を再定義しません。

1. 人間が作業メモの参照を明示した
2. 対象の作業メモが、現在の作業の引き継ぎ元として指定されている
3. 特定の問題について、過去の経緯確認が必要である
4. 現在の作業に直接関係する作業メモフォルダが特定されている

**「現在の作業に直接関係する」という理由だけで、対象フォルダを特定せずに全件探索できることにはなりません。** 参照する場合は、対象フォルダを特定したうえで、必要な範囲だけを参照します。

## 変更する場合の注意

- フォルダ命名規則やREADME必須項目を変更する場合、`docs/templates/work_note_readme_template.md` と `prompts/prepare_work_note.md` が同じ値に依存していないか確認してください。
- 作成候補の条件を変更する場合、判断主体（AIが該当判定、人間が作成可否を決定）の分離を維持してください。「必要に応じて作成する」のような、判断主体や条件が不明な表現は使わないでください。
