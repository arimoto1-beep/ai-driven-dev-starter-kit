# project: 工程（どの順番で進めるか）

## このファイルの目的

このプロジェクトの標準工程と、各工程で使う task プロンプトの対応を示します。

## このファイルを読む作業

- 次にどの工程へ進むか判断するとき
- 承認をどこで受けるか確認するとき
- バグ対応や仕様変更の全体像を確認するとき

## このファイルに含めないもの

- **各工程の詳細手順、出力形式、確認観点** → 対応する `prompts/*.md`（ここには複製しません）
- 成果物の配置とファイル名 → `10_document_structure.md`
- どのひな形を使うか → `15_document_templates.md`
- **レビュー結果の評価値** → `25_review_policy.md`
- 承認の原則、停止判断、次工程移行判定 → `docs/rules/core/20_approval_and_review.md`
- 工程の骨格（正本 → 必要な下流資料 → 実装 → テスト → レビュー。正本が仕様の場合は仕様→設計→テスト観点→実装→レビューとなる） → `docs/rules/core/10_workflow.md`

## オートモード（feature 収束ループ）

feature 単位の新規開発を、AIレビューと修正の収束ループで進める進め方です。
**正本は `70_feature_loop.md` です。このファイルには全体像と入口だけを置きます。**

```text
G0（要求確定）           AI Gate
CP1（上流設計）          人間 Gate ... 下流進行承認
G2（詳細設計・テスト設計） AI Gate
CP3（実装・テスト）       人間 Gate ... 受け入れ判断
```

| 使うもの | 役割 |
|---|---|
| `tools/feature_runner.py` | Worker と Reviewer を別プロセスで交互に起動し、Gate記録の front matter で状態遷移する |
| `prompts/run_stage.md` | Worker。成果物の作成と、FINDING の修正 |
| `prompts/review_stage.md` | Reviewer。レビュー、収束判定、Gate記録の作成 |

- **オートモードは、上記の標準工程を置き換えません。** マニュアルモードは従来どおり利用できます
- Worker は手順を自分で定義せず、**上表の個別プロンプトへ委譲します。** 成果物の作り方の正本は個別プロンプトのままです
- 途中でマニュアルモードへ降り、その後オートモードへ復帰できます
- 実装開始条件は、方式によって異なります（下記「承認を置く工程」）

## 承認を置く工程

| 承認 | 工程 | 承認欄の場所 |
|---|---|---|
| 実装着手承認（**マニュアルモード**） | 9a（feature 実装の前） | `24_review_checklist.md` 末尾 |
| 下流進行承認（**オートモード CP1**） | CP1（上流設計の後） | 最新の CP1 Gate記録 |
| 受け入れ判断（**オートモード CP3**） | CP3（feature 完成時） | 最新の CP3 Gate記録 |
| バグ修正実装の承認 | バグ対応フローの4段階目 | `30_bug_fix_plan.md` の人間承認欄 |
| レビュー指摘の反映承認 | レビュー後、修正作業の前 | 承認欄なし。人間がレビュー結果を確認して個別に判断 |

承認欄がすべてチェックされていない場合、AIは次の工程を開始しません。
AIは承認欄を自らチェックしません。詳細は `docs/rules/core/20_approval_and_review.md` を参照してください。

### 実装開始条件

どちらの方式が適用されるかは、`24_review_checklist.md` の「実装開始条件」に記載されます。

| 方式 | 実装開始条件 |
|---|---|
| `manual`（既定。記載がない場合を含む） | `24_review_checklist.md` の「実装着手承認欄」が全項目チェック済み |
| `auto` | **CP1 の下流進行承認 AND 最新 G2 Gate記録の `verdict: PASS`** |

**CP1 の下流進行承認は、実装着手承認ではありません。** CP1 の時点では詳細設計・テスト設計が存在せず、人間が承認しているのは上流設計の方向です。実装可能性の判定は G2 が担います。定義の正本は `70_feature_loop.md` です。

## 共通設計を扱う場合

複数 feature にまたがる設計が必要になった場合、標準工程とは別に、feature 設計（工程6）より前に共通設計を整えます。
feature 個別の設計書に重複して書かず、共通設計として分けて管理します。すべての command/app で必須ではありません。

対象の成果物と、それぞれに対応するプロンプトは `15_document_templates.md` の対応表を参照してください。
共通設計書は人間が直接作成してもかまいません。

## バグ対応フロー

```text
報告 → 調査 → 修正計画 → 人間承認 → 実装
```

| 段階 | task プロンプト |
|---|---|
| バグ報告書の作成 | `prompts/create_bug_report.md` |
| バグ調査書の作成 | `prompts/investigate_bug.md` |
| バグ修正計画書の作成 | `prompts/create_bug_fix_plan.md` |
| 人間が修正計画書の承認欄を確認 | — |
| 承認済み計画に従って修正 | `prompts/implement_bug_fix.md` |

修正計画書に記載されていないファイルは変更しません。
仕様・設計・テスト計画の更新が必要と判明した場合は、修正を中断して STOP し、別作業として報告します。

**この基本ルートは維持します。** 今回のコード先行（実施状態）の扱いを理由に、緊急バイパス用のプロンプトや、通常の承認を簡単に回避できる仕組みを設けません。

#### 障害対応などでコードを先に修正した場合

- **コード先行を選ぶのは人間です。AIが自ら緊急対応と判断して、上記の基本ルートを迂回してはいけません。**
- 人間がコード先行を選んだ場合は、事後に上記「コードを先に変更した場合」の手順で扱います。
- 事後に通常のバグ管理文書（`10_bug_report.md`、`20_bug_investigation.md`、`30_bug_fix_plan.md`）を作成するかどうかは、人間が判断します。
- 未了項目は残課題として明示し、対応せずに完了として扱いません。

## レビュー工程

レビューは段階を分けて行います。

| レビュー | タイミング | task プロンプト | 記録先 |
|---|---|---|---|
| ソースレビュー | 実装直後の中間チェック | `prompts/review_feature_source.md` | チャット報告のみ |
| feature 単体レビュー | feature 完成後 | `prompts/review_feature.md` | `25_review_result.md` |
| command/app 全体レビュー | entrypoint・結合試験を含む最終確認 | `prompts/review_command.md` | `12_command_review_result.md` |
| 補助コンテキストの横断確認 | 必要に応じて随時 | `prompts/review_context.md` | チャット報告のみ |
| 正式資料とコードの意味上の整合確認 | 必要に応じて随時（指定した scope に対して） | `prompts/review_design_code_consistency.md` | チャット報告のみ |

`review_design_code_consistency.md` は、標準工程の特定のステップに固定されたレビューではありません。指定した scope（feature / command/app / 共通処理など）について、**現在の正式資料と現在のコードに意味上の矛盾がないか**を確認します。feature 単体レビューや command/app 全体レビューを置き換えるものではありません。

レビュー結果に記録する評価値と、集計の運用は `25_review_policy.md` を参照してください。

## 変更を検討する場合

**変更は、必ずしも仕様書から始まりません。** 変更ルート（`docs/rules/core/10_workflow.md`）ごとに入口が異なります。

変更を整理するときは、**変更ルート**（正式資料でどう扱うべきか）と**実施状態**（未着手・一部実施・実施済み、コード先行の有無）を別の軸として扱います。同じ変更ルートでも、実施状態は変更前だったり、コード先行済みだったりします。

| ルート | 入口 | このプロジェクトでの進み方 |
|---|---|---|
| **A. 実装詳細で完結する変更** | コード | 正式資料を更新せず、実装とテストの変更・検証・レビューだけで完結できる。下記「実装詳細で完結する変更の進め方」 |
| **B. 正式資料を正本として下流へ反映する変更** | 正式資料 | 下記「仕様変更の進め方」の標準8ステップ（正本が仕様以外の場合の扱いを含む） |
| **C. コードから正式資料へ逆反映する変更** | コード | 下記「コードから正式資料へ逆反映する場合」 |

ルートB またはルートC の変更が**コード先行**（正式資料への反映より先にコードを変更した状態）である場合は、下記「コードを先に変更した場合」もあわせて確認します。**コード先行は独立したルートではなく、B または C の変更が先行して実施された状態です。ルートAは、正式資料への反映がそもそも不要な変更であり、この意味でのコード先行には該当しません。**

どのルートか判断できない場合、または分類が未確定な場合は、まず影響と意味を整理します。

| 段階 | task プロンプト |
|---|---|
| 変更の意味・変更ルート・実施状態・影響範囲の整理（変更前でも変更後でも使える。ファイルは変更しない） | `prompts/analyze_code_change_impact.md` |
| 現在の正式資料と現在のコードに意味上の矛盾がないかの確認（ファイルは変更しない） | `prompts/review_design_code_consistency.md` |

2つのプロンプトの役割は異なります。混同しないでください。

- `analyze_code_change_impact.md` は**変更**を見ます（この変更をどこまで正式な意味として残すか）
- `review_design_code_consistency.md` は**現在の状態**を見ます（今の正式資料と今のコードが意味として矛盾していないか）

分析結果を人間が確認し、バグ候補ならバグ対応フローへ、正式資料で意味を定義すべき変更なら下記の仕様変更の進め方へ接続します。

### 実装詳細で完結する変更の進め方

正式資料が意味を定義していない範囲だけが変わる場合（可読性の改善、冗長な処理の整理、局所的なリファクタリング、正式資料で規定していない実装方式の変更など）は、次のとおりです。

- **正式資料を無理に更新しません。** 正本を探すこと自体が目的ではありません。
- 実装とテストの整合を確認し、`40_testing_rules.md` の検証を実施します。
- 実装直後のソースレビュー（`prompts/review_feature_source.md`）は、通常どおり行えます。
- 作業報告には、正式資料を更新しない理由と、コードとテストだけで完結できる根拠を記載します。
- **正式資料と矛盾する変更は、このルートとして扱いません。**
- **「正本が見つからないので STOP」としません。** ただし、正式資料へ残すべき意味なのに置き場がない場合は、従来どおり人間判断です（`docs/rules/core/10_workflow.md`）。

AIへ実装を依頼する場合の task プロンプトと承認ゲートは、標準工程と同じです（工程10・`prompts/implement_feature.md`）。**このルートを理由に、実装着手承認を省略できるわけではありません。**

### コードから正式資料へ逆反映する場合

コードを読んだ結果、今後も守るべき仕様・設計・共通方針だと分かった内容がある場合です。

```text
逆反映候補に気づく（レビュー・調査・実装のいずれでもよい）
  ↓
prompts/analyze_code_change_impact.md で、正式化すべき知見と反映先を整理する
  ↓
人間が、正式化するかどうかと反映先を判断する
  ↓
反映先に対応する作成系プロンプト（create_*）で、別作業として反映する
  ↓
必要に応じて下流資料・実装・テストへ反映する
```

- **コードから見つかったものを何でも正式資料へ昇格させません。**
- 役割の合う置き場がない場合は、新しい文書やディレクトリを作らず人間判断へ戻します。
- **複数 feature にまたがる標準化・共通化だからといって、機械的にこのルートへ分類しません。** 先に人間が「今後この方式を正式ルールにする」と決めて正式資料から変更する場合はルートBです。コードを比較していて気づいた場合にルートCになります。判定基準は「どこでその正式な意味を定義することになったか」です。

### コードを先に変更した場合

障害対応、時間制約、検証目的などで、正式資料への反映より先にコードを変更した場合です。**これは変更ルートではなく実施状態（コード先行）であり、その変更ルートが B または C の場合に生じます。**

- **コード先行を選ぶのは人間です。AIが自ら「緊急だからコード先行にする」と判断しません。**
- 事後に、次を行います。

```text
1. prompts/analyze_code_change_impact.md で、実施済みの変更（Git差分）を入力に変更ルートと実施状態を整理する
2. 人間が、正式資料への反映要否と反映先を確認する
3. 反映が必要な資料を、下記「仕様変更の進め方」の標準8ステップに沿って別作業として更新する
4. 必要なテストを実施する
5. 必要なレビューを行う
6. 未了項目を残課題として明示する
```

- **未反映事項を残したまま、作業を完了として扱いません。**
- これはルートA（実装詳細で完結する変更）とは別です。ルートAは正式資料への反映がそもそも不要であり、混同しないでください。

### 仕様変更の進め方

**この節は、正式資料で意味を定義・維持すべき変更（ルートB）に適用する標準フローです。** 実装詳細で完結する変更には適用しません。

**仕様変更専用の task プロンプトはありません。** 次の流れで進めます。

```text
仕様変更の入口
  ↓
prompts/analyze_code_change_impact.md で変更ルート・実施状態・影響分析（ファイルは変更しない）
  ↓
人間が、変更の正本・更新範囲・進むフローを確認する
  ↓
下記の標準8ステップで反映する
```

#### 標準8ステップ

このスターターキットでの標準手順です。**正式資料で意味を定義すべき変更（ルートB）で使います。** コード先行だった場合の後追い反映（ルートB または C が先行実施された状態）でも、反映が必要な資料についてはこの8ステップに沿って進めます。

**この8ステップは、外部から見える動作の変更など、正本が `20_spec.md` になる場合を主な例として記載しています。** 正本が異なる場合（`21_design.md`、`22_flow.md`、`common_design/` など）は、Step 3〜6 の対象と順序がそれに応じて変わります。**「ルートB は必ずこの8ステップの順序（仕様→設計→フロー→テスト計画）を通る」という意味ではありません。** 基本原則は「正本 → 必要な下流資料 → 実装 → テスト → レビュー」であり、正本が設計であれば `20_spec.md` を無理に更新しません。

| Step | 内容 | 使うプロンプト |
|---|---|---|
| 1 | 変更内容を整理する | `prompts/analyze_code_change_impact.md` |
| 2 | 影響範囲を洗い出す | 同上 |
| 3 | 正本となる正式資料の更新要否を確認する | — |
| 4 | 正本を具体化する下流資料の更新要否を確認する | — |
| 5 | テストの更新要否を確認する | — |
| 6 | 更新対象ごとに、正本から下流へ順に修正する | 上表の各作成系・実装系プロンプト |
| 7 | 正本・下流資料・ソースコード・テストの整合性を確認する | — |
| 8 | 最終チェックを実施する | — |

Step 6 の反映順は、このプロジェクトでは次のとおりです。

- command/app の責務や feature 分割へ影響する場合は、`10_overview.md` から確認・更新する
- **外部から見える動作へ影響し、`20_spec.md` が正本になる場合は**、設計書や実装より先に `20_spec.md` を更新する
- **正本が `21_design.md` や `22_flow.md` など仕様以外の資料である場合は、その正本から更新し、`20_spec.md` を無理に変更しない**
- 正本から、`21_design.md` → `22_flow.md` → `23_test_plan.md` → 実装 → テストの順（正本より下流にあたる資料の順）に進む

変更ルート、実施状態、正本の特定、変更不要な資料の理由明示、一括修正の禁止、未記載と矛盾の区別は `docs/rules/core/10_workflow.md` を参照してください。
Step 7 の「整合性の確認」は、**正式資料が定義している意味とコードが矛盾していないか**を確認するものです。正式資料に書かれていない実装詳細が存在すること自体は、不整合として扱いません。
Step 7・8 の結果の報告項目は `docs/rules/core/50_records_and_reporting.md` を参照してください。ここには複製しません。

将来、仕様変更専用プロンプトを追加した場合は、詳細手順の正本を task プロンプト側へ移し、このファイルには全体像と参照先だけを残すことを検討します。

なお、次の2つのプロンプトは、この標準工程（仕様→設計→実装→レビュー）には含まれない、工程外の補助taskです。無理に標準工程へ組み込まないでください。位置づけは `docs/rules/README.md` を参照してください。

- `prompts/review_prompt_integrity.md`：キット自体の完全性確認用。開発対象機能のレビューではありません。
- `prompts/prepare_work_note.md`：作業経緯の記録（作業メモ）用。仕様・設計・実装・レビューのいずれの成果物も作成しません。

また、`prompts/analyze_code_change_impact.md` と `prompts/review_design_code_consistency.md` は、標準工程の特定のステップに固定されない**随時利用のプロンプト**です。必要になった時点で使います。いずれもファイルを変更しません。

---

## 変更する場合の注意

- 工程を増減する場合も、`docs/rules/core/10_workflow.md` の骨格（**正本 → 必要な下流資料 → 実装 → テスト → レビュー**）から逸脱しないでください。この骨格は、**正式資料で意味を定義すべき変更（ルートB）** に適用されます。正本は仕様とは限りません。設計やフローが正本の場合はそこから始まり、仕様書を形式的に更新する必要はありません。「仕様 → 設計 → テスト観点 → 実装 → レビュー」は、正本が仕様である場合に生じる一例です。実装詳細で完結する変更（ルートA）まで、この骨格を通すことを求めるものではありません。
- 承認を置く工程を減らす場合は、`docs/rules/core/20_approval_and_review.md` の承認境界を満たせるか確認してください。core の承認原則を緩和することはできません。
- 変更ルート（A〜C）、実施状態、判断不能の区分を増減・再定義しないでください。定義の正本は `docs/rules/core/10_workflow.md` です。このファイルは、各ルートをこのプロジェクトでどう進めるかだけを定めます。
