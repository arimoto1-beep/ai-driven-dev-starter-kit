# project: AIの権限と保護対象

## このファイルの目的

このプロジェクトで、AIが何をどこまで変更してよいかを具体的に定めます。

## このファイルを読む作業

- 実装作業、バグ修正
- 補助コンテキストを扱う作業
- 現在地メモの更新を検討するとき
- 承認欄の場所を確認するとき

## このファイルに含めないもの

- 今回の作業で変更してよいファイル → 対応する `prompts/*.md`（**保護対象とは別のレイヤです**）
- 承認の上位原則、停止判断の詳細、次工程移行判定 → `docs/rules/core/20_approval_and_review.md`
- 変更範囲の上位原則 → `docs/rules/core/30_change_safety.md`
- 記録の書き分け → `docs/rules/core/50_records_and_reporting.md`
- **レビュー結果の評価値** → `25_review_policy.md`（ここには置きません）
- 作業メモの保存場所・保存単位・README形式・作成条件の具体値 → `60_work_notes.md`（ここでは更新権限だけを扱います）

## 現行スターターキットの初期値

### 保護対象

AIは、人間の明示指示なしに次を変更しません。

- `AGENTS.md`
- `CLAUDE.md`
- `docs/rules/` 配下（README・core・project を含むルール体系全体）
- `prompts/*.md`
- `docs/templates/`
- `docs/context/`（人間が管理する入力資料）
- `docs/context/work_notes/`（作業メモ。更新権限の詳細は下記「作業メモの更新権限」を参照）
- `src/common/`
- `requirements.txt`
- `tools/`（品質確認ツールなど）
- CI/CD、デプロイ関連ファイル

利用者が明示的にルール更新を依頼した場合のみ、`AGENTS.md` や `prompts/*.md` を必要最小限で更新します。

`docs/rules/project/` 配下（このディレクトリ）は、利用者がプロジェクトに合わせて編集する設定です。AIが明示指示なしに変更しない点は同じです。

### 範囲外資産

AIは、次を勝手に追加しません。必要だと感じた場合は、実装せず「今後の拡張候補」として記載します。

- CI/CD設定
- GitHub Actions
- デプロイ設定
- 外部システム連携
- 環境別設定ファイル
- 複雑なテスト基盤

### 現在地メモ（`tasks.md`）の工程別更新権限

ハイブリッド方式に従います。

| 工程 | AIの扱い |
|---|---|
| **ドキュメント作成工程**（overview 作成、仕様作成、設計作成、フロー作成、テスト計画作成、レビュー観点作成、レビュー結果作成など） | 現在地メモとして**最小限の更新を行ってよい** |
| **実装工程・バグ修正工程**（feature 実装、entrypoint 実装、結合試験実装、バグ報告書作成、バグ調査書作成、バグ修正計画書作成、バグ修正実装など） | **直接更新しない。** 更新が必要な場合は、作業報告に「tasks.md 更新候補」として記載し、人間が反映を判断する |

### 補助コンテキスト（`docs/context/`）の更新権限

- **AIは記録候補を提案します。実際のファイル更新は、人間の明示指示後に行います。**
- 提案（チャットでの報告）と、ファイル更新は別のことです。提案は行ってかまいませんが、それをもって更新してよいことにはなりません。
- 補助コンテキストの内容を正本へ反映する場合は、別の正式な変更作業として扱います。

### 作業メモ（`docs/context/work_notes/`）の更新権限

`docs/context/work_notes/` は保護対象です。**AIは人間の明示指示なしに、作業メモのフォルダ・README.md・付随ファイルのいずれも作成・更新しません。**

- 作成候補への該当は、AIが `docs/rules/project/60_work_notes.md` の条件に基づき判定できます。**ただし、これは作業完了報告での提案にとどまります。** 提案はチャット出力であり、ファイル更新ではありません。
- `prompts/prepare_work_note.md` を使って作業メモ案を構成することと、それをリポジトリへ保存することは別です。案を構成しただけでは、保存してよいことにはなりません。
- 人間が作業メモ案を確認したうえで、同じAIへ保存を指示した場合、その指示を作成・更新の明示指示として扱います。
- リポジトリを操作できないAIが自己完結した反映指示を作成し、**人間がその反映指示を別のAIへ渡して実行を依頼した場合**、その依頼を作成・更新の明示指示として扱います。**AI同士が人間を介さずに反映指示を受け渡しただけでは、明示指示にはなりません。**
- この運用のために「反映担当AI」という新しい権限主体は設けません。反映を行うAIも、他のAIと同じ権限境界に従います。
- 保存してよい内容は、人間が確認した作業メモ案の内容に限定します。保存時に独自の内容を追加しません。
- 新規作成・更新のいずれも、**指定された作業メモフォルダの外は変更しません。**
- 作業メモの内容を正式文書（仕様・設計・ルール・レビュー結果など）へ反映する場合は、別の正式な変更作業として扱います。作業メモを根拠に、AIが自動的に正式文書を更新してはいけません。
- 完了状態の作業メモの扱い（追記が原則、誤記訂正は人間の明示指示による）は `docs/rules/project/60_work_notes.md` に従います。

### 承認欄の場所と承認者

| 承認 | 承認欄の場所 | 承認者 |
|---|---|---|
| 実装着手承認 | `24_review_checklist.md` 末尾の「実装着手承認欄」 | 人間 |
| バグ修正実装の承認 | `30_bug_fix_plan.md` の「人間承認欄」 | 人間 |
| レビュー指摘の反映承認 | 承認欄なし。人間がレビュー結果を確認し、反映する指摘を判断する | 人間 |

**AIは、これらの承認欄にチェックを入れません。**

### 人間による直接修正

**人間がソースコードやドキュメントを直接修正することを、このプロジェクトでは禁止しません。**

次は、人間が直接修正してかまいません。

- ソースコードとテストコード（正式資料が意味を定義していない実装詳細の範囲を含む）
- 誤字
- 明らかな表記ゆれ
- 記述内容に影響しない軽微な修正

人間が直接修正した場合は、必要に応じて、その変更が `docs/rules/core/10_workflow.md` の**どの変更ルートに当たるか**を確認します。

| 変更ルート | 確認すること |
|---|---|
| A. 実装詳細で完結する | 正式資料と矛盾していないか。コードとテストが整合しているか。必要な検証を行ったか |
| B. 正式資料から下流へ反映すべきだった | 正本を特定し、別作業として反映する |
| C. 正式資料へ逆反映すべき知見 | 今後も守るべき意味かを確認し、別作業として反映する |

**変更ルートが B または C で、かつコードが先行して実施されている場合は、** 後追いで反映すべき資料、必要なテスト、必要なレビュー、未了項目をあわせて整理します。**コード先行は独立した変更ルートではなく、実施状態です。**

**この確認のために、新しい承認工程・専用の記録様式・毎回の作業メモ作成といった重い運用は新設しません。** Git差分、通常のコミット履歴、テスト結果、レビュー、既存の作業報告など、現在の通常運用で足りる場合はそれを使います。

変更ルートの判断に迷う場合や、正式資料への反映要否を整理したい場合は、`prompts/analyze_code_change_impact.md` を実施済みの変更に対して使えます。

**なお、変更内容そのものが軽微かどうかを判断するのは人間です。AIは行いません。**
AIが「影響は軽微」と単独で確定して未決事項を解決済みとして扱わないことは、`docs/rules/core/20_approval_and_review.md` に定めています。

### 人間の直接修正は、AIの権限ではありません

**人間がコードを直接修正してよいことと、AIが自由にコードを修正してよいことは、別の問題です。**

上記は人間の行動範囲についての定めであり、**AIの変更権限を一切広げません。** 次は従来どおり維持されます。

- AIは、今回の task で許可された範囲だけを変更します（`docs/rules/core/30_change_safety.md`、各 `prompts/*.md` の「変更してよいファイル」）
- AIは、調査中・レビュー中・説明中に修正しません
- AIは、ついで修正を行いません
- AIは、上記の保護対象を人間の明示指示なしに変更しません
- AIは、人間判断事項を確定しません
- **AIが変更ルートを分析して「実装詳細で完結する変更（ルートA）」と判断したことは、AI自身の作業範囲を広げる根拠になりません。** AIは変更ルート・実施状態と根拠を提示できますが、それをもって保護対象や task の範囲外を変更したり、人間の承認なしに次工程へ進んだりしてはなりません。

### ルール文書の更新条件

- `AGENTS.md`、`docs/rules/core/`、`prompts/*.md` の更新は、人間の明示的な依頼があった場合のみ、必要最小限で行います。
- `docs/rules/project/` 配下は、プロジェクトの事情に合わせて利用者が編集する対象です。ただし core を無効化または緩和する変更はできません。

### 指摘の重大度区分

**このプロジェクトでは、個々の指摘に付ける重大度区分は現在定義していません。**

重大度区分を追加する場合は、別の正式なルール変更として扱ってください。
AIは、重大度区分を推測で作らず、「未対応の指摘が残っていないか」という形で確認します。

なお、成果物全体に付けるレビュー結果の評価値は `25_review_policy.md` で定義しています。個々の指摘の重大度とは別のものです。

## 変更する場合の注意

- 保護対象を減らす場合、`docs/rules/core/30_change_safety.md` の「変更に人間の明示指示を要するファイル群を定める」という原則自体は変えられません。**リストの中身だけを調整してください。**
- 人間の直接修正の範囲を変更する場合も、**それをAIの変更権限へ転用しないでください。** 人間の行動範囲とAIの変更権限は別に定めます（`docs/rules/core/10_workflow.md` の「人間による直接修正と、AIの変更権限」）。
- 補助コンテキストの更新権限を緩める場合、`docs/rules/core/40_official_docs_and_context.md` の「補助記録を確定仕様として扱わない」を満たせるか確認してください。
- 承認欄を減らす場合、`docs/rules/core/20_approval_and_review.md` の承認境界を満たせるか確認してください。
