# 統合後のシステム全体を再評価してください

このプロンプトは、複数の feature・機能仕様・設計・実装が組み上がった後に、**現在の要件全体からシステム構造をあらためて見直す**ためのものです。

個々の feature が正しく実装されているか、現在の正式資料とコードが整合しているかだけを確認するレビューではありません。

機能仕様を一つずつ作成し、それらを束ねてシステムを構築すると、各段階では妥当でも、全体として見ると次のような状態が生じる可能性があります。

- 機能ごとの境界が、そのまま実装境界として残りすぎている
- 複数機能を通して見ると統合できる責務が分かれている
- 逆に、一つのコンポーネントに異なる責務が隠れている
- 同じ判断・変換・データ保持が複数箇所に生じている
- 個別機能では自然だった構造が、全体では変更・試験・障害解析を難しくしている
- 実装の積み上げ順を前提にしなければ、別の構造の方が単純である

このプロンプトでは、**現在の実装構造や feature 分割を正解として固定せず**、現在までに確定した要件・制約を一つのシステムとして読み直します。

また、一般的な設計品質だけでなく、**人間とAIが継続的に理解・変更・検証しやすい構造か**というAI駆動開発の観点も明示的に評価します。

**このプロンプトでは、いかなるファイルも変更しません。** 結果は改善の強制指示や次工程移行判定ではなく、全体を再考するための示唆としてチャットで報告します。

---

## 中心となる問い

次の2つを中心に評価してください。

```text
現在までに確定した要件・制約を最初からすべて知っていたとしても、今のシステム構造を選ぶか。
```

```text
現在の構造は、人間とAIが全体像を理解し、局所的に変更し、自分で結果を検証しやすい構造になっているか。
```

「技術的に実装できること」と「全体として筋がよいこと」を混同しないでください。

## このレビューで固定するもの／固定しないもの

### 原則として固定するもの

現在の正式資料から確認できる、以下の**要件として維持すべき意味**は尊重してください。

- 外部から見える動作
- 入力・出力
- 制約
- エラー契約
- 今回やらないこと
- 外部システムとの契約
- 性能・運用・セキュリティなど、正式に定義された非機能要件
- 人間が明示的に変更不可と指定した条件

### 正解として固定しないもの

以下は、現在そう実装されているという理由だけで正解として固定しないでください。

- feature の境界
- ファイル・モジュール・クラス・関数の分け方
- コンポーネント分割
- entrypoint と feature の現在の切り方
- ワークフロー上の処理分割
- 同じ処理をまとめる／分けるという現在の判断
- 現在の呼び出し階層
- 現在採用されている抽象化
- 現在の実装順序や、過去に追加された順番

ただし、これらが正式資料で**今後も維持すべき意味として明示的に定義されている場合**は、勝手に無視せず、「現在の制約として維持する場合」と「その制約自体を再考できる場合」を分けて示してください。

---

## 特定の構造を先に正解としない

次のような単純なルールで結論を出さないでください。

- 分割が細かいほどよい
- まとめるほどよい
- feature 数が少ないほどよい
- コンポーネント数が少ないほどよい
- マイクロサービスがよい
- モノリスがよい
- 共通化が多いほどよい
- 重複をゼロにすべき
- AI向けに特殊な構造へ変えるべき

**人間とAIが、責務・処理フロー・変更範囲・試験範囲を自然に理解できること**を、単純さの重要な判断基準としてください。

AI駆動開発に適していることと、人間にとって分かりやすいことは、原則として両立させてください。

| prompt | 主な問い |
|---|---|
| `review_feature.md` | 1つの feature の仕様・設計・実装・テストが整合しているか |
| `review_command.md` | 現在の overview・feature 分割・entrypoint・結合試験を前提に、command/app 全体が整合しているか |
| `review_design_code_consistency.md` | 現在の正式資料と現在のコードに意味上の矛盾がないか |
| `analyze_code_change_impact.md` | 特定の変更を正式資料で維持すべき意味として扱う必要があるか |

このプロンプトは、`review_command.md` の代替ではありません。

`review_command.md` は現在定義されている構造に対する正式な全体レビューです。このプロンプトは、**その現在の構造自体に再考余地がないかを見る随時利用の分析レビュー**です。

このプロンプトの結果だけで、既存の正式資料や実装を変更しないでください。

## 利用者が指定する項目

- 対象 scope の種別: `command_or_app / 複数 command_or_app`
- 対象 scope: `対象名を具体的に指定する`
- 現在の要件として特に維持すべき条件: `必要に応じて指定。なければ「正式資料から判断」`
- 重点的に見たい観点: `必要に応じて指定。なければ「なし」`
- 除外したい範囲: `必要に応じて指定。なければ「なし」`
- 補足条件: `必要に応じて指定。なければ「なし」`

対象 scope が指定されていない場合は、レビュー対象を推測で決めないでください。

scope が大きく、全体像を十分な確信度で復元できない場合は、浅く広く結論を出さず、確認できた範囲・確認できなかった範囲・不足している情報を明示してください。

## 評価観点

### 1. 全体像の復元容易性

AIまたは初見の開発者が、現在のシステムについて次を正しく復元できるか確認してください。

- 何をするシステムか
- 主な入口と出口
- 主要な処理経路
- データがどこを通るか
- 各コンポーネントの責務
- 外部システムとの境界
- 正常系・主要な異常系でどの経路を通るか

全体像を復元するために、多数の資料・設定・条件分岐・実装内部を横断しなければならない場合、その事実自体を評価対象にしてください。

**構成上の見た目と実際の処理単位が一致していない場合は明示してください。**

### 2. 機能仕様の集合と全体構造

個々の機能仕様が妥当でも、それらをまとめて見たときに次の問題がないか確認してください。

- 同じ責務が複数 feature に分散している
- 異なる責務が一つの feature／コンポーネントへ集まりすぎている
- 同じ入力・出力変換が複数箇所にある
- 同じデータを異なる形で持っている
- 機能単位では自然だった境界が、全体では不自然になっている
- 機能仕様の境界を、そのまま実装境界として扱う必要がない箇所がある

### 3. 制御フローと判断の所在

同じ意味の判断・振り分け・状態判定が、複数の層やコンポーネントに重複していないか確認してください。

上位層ですでに決定されたことを下位層で再度判定する構造がある場合は、次を評価してください。

- その二重化に必要性があるか
- 変更時に複数箇所を同期する必要が生じないか
- 試験すべき組み合わせを増やしていないか
- 障害時に実際の処理経路を追いにくくしていないか

### 4. 変更の局所性

代表的な変更について、変更対象をどこまで限定できるか確認してください。

- 1機能の軽微な変更
- 入出力の変更
- 新しい機能の追加
- 既存機能の削除
- データ構造の変更
- エラー処理の変更
- 性能改善

局所的な変更でも、多数の feature、設定、ワークフロー、共通処理、テストを同時に理解・変更する必要がある場合、その原因を示してください。

### 5. 試験と自己確認の局所性

変更したAIが、変更結果の正しさを自分で確認しやすい構造か評価してください。

- 1機能の変更を、その機能に近い試験で十分に確認できるか
- 構造上の理由だけで不要な結合試験・回帰試験が増えていないか
- どの試験を通せば何が確認できたと言えるか分かるか
- モックだけでは確認できない重要な接続点が明確か
- 変更箇所と試験対象の対応をAIが推測しやすいか

### 6. AIが必要とするコンテキスト範囲

AIへ「この機能を変更して」と依頼したとき、安全に変更するために必要なコンテキストが広がりすぎないか確認してください。

次のような要因がないか見てください。

- 離れた場所にある暗黙の依存
- 巨大な共有コード
- パラメータによって役割が大きく変わるコンポーネント
- 実行時にしか分からない振り分け
- 同じ意味を複数箇所で表現している構造
- 設計資料・インフラ定義・コードをすべて読まないと1処理が理解できない構造

### 7. AIによるレビュー容易性

変更差分をAIがレビューする際、変更意図・影響範囲・正しさを追いやすいか確認してください。

「変更されたファイルだけ」を見ても影響を判断できず、広範囲な構造復元が毎回必要になる場合は、そのコストを示してください。

### 8. 障害解析・観測可能性

障害発生時に、人間やAIが次を追いやすいか確認してください。

- どの処理で失敗したか
- どの入力を処理していたか
- どの経路を通ったか
- どこまで正常だったか
- どの責務の問題か

ログ・メトリクス・トレース・実行履歴が存在する場合は、処理単位と自然に対応しているかも確認してください。

### 9. 構造の見た目と実態

ファイル名、ディレクトリ、コンポーネント名、ワークフロー、構成図などから見える構造と、実際の責務・処理単位が一致しているか確認してください。

複雑性が削減されているのではなく、単に内部へ隠されている場合は、そのことを明示してください。

### 10. 過剰設計と過小設計

将来性、共通化、柔軟性、拡張性などのために、現在の理解・変更・試験コストが不必要に高くなっていないか確認してください。

逆に、単純さを優先しすぎた結果、一つの巨大な責務へ集約され、変更影響が広がっていないかも確認してください。

### 11. ゼロベースで見た代替構造

現在の実装を部分修正することだけを考えず、**現在の要件全体を最初から与えられた場合に選び得る構造**を検討してください。

ただし、代替案を必ず採用すべきとは扱わないでください。

現在構造との差分から、次を明らかにすることが目的です。

- 現在も必要な複雑性
- 実装の積み上げによって生じた可能性がある複雑性
- 現在の構造を維持する合理的な理由
- 再考すると効果が大きそうな境界

### 12. 現実的な変更コスト

構造上の改善余地があっても、既存資産、運用、移行、リスク、納期などにより、変更しない方がよい場合があります。

「ゼロからなら別案がよい」と「今から変更すべき」を区別してください。

このプロンプトは、理想構造への全面改修を推奨することが目的ではありません。

## AI駆動開発として特に確認すること

一般的な保守性とは別に、次を明示的に評価してください。

- AIが「何を理解すべきシステムなのか」を正しく復元できるか
- AIへ局所的な変更依頼を出したとき、対象範囲を限定できるか
- AIが変更影響を追うために必要なコンテキスト量が妥当か
- AIが自分の変更結果を試験・ログ・実行結果から確認できるか
- AIによるレビューで、別機能への意図しない影響を見つけやすいか
- 人間の機能分割や過去の実装順を、AIが暗黙の絶対条件として引き継がなくてもよい構造か
- AIが現在の実装を正当化するだけでなく、全体として別案を比較できるだけの情報が明示されているか

**AIが読めるから問題ない、とは判断しないでください。**

大量のコンテキストを読めば理解できる構造と、局所的な変更に必要な範囲だけ読めば安全に作業できる構造は別です。

## 出力

結果はチャットで、以下の内容を整理して報告してください。

### 1. 対象 scope

- 確認した範囲
- 確認できなかった範囲
- 除外した範囲

### 2. 復元したシステム全体像

- 目的
- 主な入口・出口
- 主要コンポーネントと責務
- 主要な処理フロー
- 主要なデータの流れ

### 3. 全体像の復元容易性

- 復元確信度: `High / Medium / Low`
- 全体像を把握するために横断する必要があった主な資料・実装
- 復元を難しくした要因
- 構造の見た目と実態に差があった箇所

### 4. 現在構造の良い点

現在の構造を維持する合理的な理由や、人間・AIの双方にとって扱いやすい点を示してください。

### 5. 全体としての再考候補

各候補について、次を示してください。

- 現在の構造
- 気になる理由
- 個別機能だけを見た場合には自然だった可能性
- 全体で見たときに生じている影響
- AI駆動開発上の影響
- 再考した場合の方向性
- 今すぐ変更する必要性: `高 / 中 / 低 / 変更不要`

### 6. AI駆動開発への適合性

少なくとも次を個別に評価してください。

- 全体像の復元容易性
- 変更の局所性
- 必要コンテキストの局所性
- 試験・自己確認の局所性
- レビュー容易性
- 障害解析容易性
- 責務・境界の明示性

各項目は `良好 / 注意 / 再考余地あり` と、その根拠を示してください。

### 7. ゼロベースで見た場合の構造

現在の要件全体を最初から知っていた場合、現在と同じ構造を選ぶかを回答してください。

- `ほぼ同じ構造を選ぶ`
- `一部の境界を変える可能性が高い`
- `大きく異なる構造を検討する`
- `判断材料不足`

理由と、現在構造との差分を示してください。

### 8. 採用判断とは分けた示唆

理想的には改善できるが、現時点で変更する必要がないものも分けてください。

- 今すぐ検討する価値が高いもの
- 次回大きな変更時に再検討するとよいもの
- 現状維持でよいもの

### 9. 人間判断が必要な事項

要件・制約そのものを見直さないと結論が出ない事項を列挙してください。

## 判定の扱い

このプロンプトでは、`GO` / `条件付きGO` / `STOP` の次工程移行判定を行いません。

また、`OK` / `要修正` などの正式レビュー判定も行いません。

このレビューの目的は、**現在のシステムを否定することでも、変更を強制することでもなく、機能単位の積み上げだけでは見えにくい全体最適の再考材料を出すこと**です。

改善案の採否、正式資料の変更、リファクタリングの実施は、別作業として人間が判断してください。

---

## 禁止事項

- 現在の feature 分割を正解として固定しないでください
- 逆に、feature 分割を変えること自体を目的にしないでください
- 「AI向け」という理由だけで、人間にとって不自然な構造を推奨しないでください
- コンポーネント数やファイル数だけで単純さを判定しないでください
- 現在の実装履歴を、現在構造を維持すべき理由として無条件に採用しないでください
- 過去の設計意図を読んだだけで、その意図を正しい前提として扱わないでください
- 改善候補を見つけても、この task の中で修正を始めないでください
- この分析結果だけで次工程を停止・承認しないでください
- 全体像を十分に復元できていない状態で、断定的なアーキテクチャ変更を提案しないでください
