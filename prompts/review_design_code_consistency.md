# 正式資料とコードの意味上の整合を確認してください

このプロンプトは、**現在の正式資料**と**現在のコード**に、意味上の矛盾がないかを確認するためのものです。

## 中心となる問い

```text
現在の正式資料と現在のコードに、意味上の矛盾がないか。
```

変更の有無を問いません。今この瞬間の状態を確認します。

**このプロンプトでは、いかなるファイルも変更しません。** 見つかった問題は、修正候補としてチャットで報告するだけです。

---

## 最も重要な原則：未記載と矛盾を区別する

| | 内容 | 扱い |
|---|---|---|
| **未記載** | 正式資料がその実装詳細を規定していない。コード側に具体的な実装が存在するが、正式資料が定義する意味には反していない | **それだけでは指摘しません** |
| **矛盾** | 正式資料が定義している意味と、コードの意味が食い違っている | **指摘します** |

**「設計書に書いてない」ことは、「設計書と矛盾している」ことではありません。**

生成されたコードには、同じ仕様・設計でも実装上の揺らぎ（関数の切り方、局所的な書き方、変数名、冗長さ、同じ意味を持つ複数の実装方法など）があります。**この揺らぎが存在すること自体を問題として扱わないでください。**

指摘する場合は、**どの正式資料の、どの記述が定義している意味と、どう食い違っているか**を必ず示してください。根拠を示せないものは指摘ではなく、下記「未記載だが問題ではない実装詳細」または「判断材料不足」として扱ってください。

矛盾の判断対象となる「正式資料が定義している意味」の例:

- 外部から見える動作
- 入力・出力
- 制約
- エラー契約
- feature / command / app の責務と境界
- 維持すべき呼び出し関係・処理フロー
- 共通設計（ファイル設計・データ設計・DB設計など）
- テスト上維持すべき条件

原則の正本は `docs/rules/core/10_workflow.md` の「未記載と矛盾を区別する」と、`docs/rules/core/40_official_docs_and_context.md` の「正式資料が意味を定義していない実装詳細」です。このプロンプトはこれらを再定義しません。

## 利用者が指定する項目

**対象 scope を必ず指定してください。** scope の指定がない場合は、確認を始めずに、確認したい範囲を尋ねてください。

- 対象 scope の種別: `feature / command_or_app / 共通処理 / 複数 command_or_app`
- 対象 scope: 下記「scope の指定例」に従って具体的に指定する
- 重点的に確認したい観点: `必要に応じて書く。なければ「なし」`
- 除外したい範囲: `必要に応じて書く。なければ「なし」`
- 補足条件: `必要に応じて書く。なければ「なし」`

### scope の指定例

| scope 種別 | 指定内容 | 主に確認する正式資料 |
|---|---|---|
| **feature** | 対象機能フォルダ、実装ファイル、テストファイル | `20_spec.md`、`21_design.md`、`22_flow.md`、`23_test_plan.md`、該当する `common_design/` |
| **command_or_app** | コマンド/アプリ名 | `10_overview.md`、`11_integration_test_plan.md`、配下の feature 資料、`common_design/` |
| **共通処理** | 対象の共通処理（`src/common/` 配下など） | `docs/common/`、`common_design/`、参照元 feature の設計 |
| **複数 command_or_app** | 対象のコマンド/アプリ名を列挙 | 各 `10_overview.md` と、比較に必要な範囲の feature 資料 |

### scope を無制限に広げないこと

- **指定された scope の外へ、確認範囲を自動的に広げないでください。**
- **リポジトリ全体を無制限に読むレビューにしないでください。**
- scope 外に矛盾の疑いを見つけた場合は、その場で確認せず、「scope 外の確認候補」として報告してください。
- scope が大きすぎて確認を完遂できないと判断した場合は、無理に浅く広げず、**確認できた範囲と、確認できなかった範囲を明示してください。** そのうえで、分割して実施する提案を行ってください。

## 作業手順

1. 対象 scope を確認してください。指定がない場合は、確認せずに範囲を尋ねてください
2. scope に含まれる正式資料を読み、**そこで定義されている意味**を整理してください
3. scope に含まれる実装とテストを読んでください
4. 下記「確認観点」に沿って、正式資料が定義している意味とコードを照合してください
5. 見つかった事項を、「意味上の矛盾」「未記載だが問題ではない実装詳細」「逆反映候補」「判断材料不足」に分類してください
6. 各矛盾について、根拠（どの資料のどの記述と食い違うか）を特定してください
7. チャットで結果を報告してください

**テストの実行は必須ではありません。** 実行する場合は `python -m pytest` を使い、結果を報告に含めてください。

## 確認観点

### 1. 外部から見える動作

- `20_spec.md` が定義する入力・出力・制約・エラー動作と、実装の動作が食い違っていないか
- 仕様にない機能や便利機能が実装に追加されていないか
- 仕様が定めた出力形式・終了コードと実装が食い違っていないか

**「仕様に書かれていない便利機能が追加されている」ことは、未記載ではなく矛盾として扱います。** 仕様は外部から見える動作を定義しているためです。

### 2. 責務と境界

- `10_overview.md` が定めた command/app の責務・Boundary・feature 分割と、実装の配置が食い違っていないか
- `21_design.md` が定めた feature の責務と、実装の責務が食い違っていないか
- entrypoint に feature 固有のロジックが入っていないか（`docs/rules/project/30_development_rules.md`）
- feature に entrypoint の責務（CLI引数解析、標準出力など）が混ざっていないか
- `src/common/` に、共通化の判断を経ていない処理が置かれていないか

**「設計書に書かれていない関数が存在する」こと自体は矛盾ではありません。** ただし、その関数が設計書の定める責務の外にある処理を担っている場合は矛盾です。

### 3. 呼び出し関係・処理フロー

- `22_flow.md` が**維持すべき意味として**定めている呼び出し順・依存関係と、実装が食い違っていないか

**内部的な関数分割の違いや、補助関数の有無は、それだけでは矛盾ではありません。** `22_flow.md` が定めた呼び出しの意味（どの機能がどの順で呼ばれるか、依存の方向）が崩れている場合に矛盾とします。

### 4. 共通設計

`docs/<command_or_app_name>/common_design/` が存在する場合:

- 実装のDBアクセスが `33_db_design.md` の定義と食い違っていないか
- 実装のファイル入出力が `31_file_design.md` の定義と食い違っていないか
- 実装のデータ項目が `32_data_design.md` の定義と食い違っていないか
- 共通設計で扱うべき内容（`docs/rules/project/30_development_rules.md` の「共通設計で扱う対象」）が、個別 feature の中だけで定義されていないか

### 5. テスト

- `23_test_plan.md` が定めたテスト観点を、テストが確認しているか
- `11_integration_test_plan.md` が定めた確認内容と、結合試験が食い違っていないか
- テストが、正式資料が定義していない実装詳細に依存しすぎていないか
- テストが、実装の誤りを追認する形になっていないか

**テストが実装詳細に依存していること自体は、直ちに矛盾ではありません。** ただし、正式資料が定めた観点を確認できていない場合や、実装を変えると仕様どおりでもテストが壊れる構造になっている場合は、改善候補として報告してください。

### 6. 逆反映候補

コードを読んだ結果、次に当たるものが見つかる場合があります。

- 単なる実装詳細ではなく、**今後も守るべき仕様・設計・共通方針**として維持すべき内容
- 複数の feature が暗黙に守っている取り決めで、正式資料に記載がないもの

これらは**矛盾ではありません。** 「正式資料への逆反映候補」として、別枠で報告してください。

- **コードにあるものを何でも昇格候補にしないでください。** 今後も守るべき意味を持つ根拠を示してください。
- 昇格の採否は人間が判断します。**AIが正式資料を更新してはいけません。**
- 役割の合う置き場が現在の構成にない場合は、新しい文書やディレクトリを提案するにとどめ、勝手に作らないでください。

## 出力形式

以下の形式でチャットに報告してください。

---

### 1. 総合判定

以下のいずれかを記載してください。

**判定値そのものの定義は、`docs/rules/core/20_approval_and_review.md` の `GO` / `条件付きGO` / `STOP` を正本とします。** このプロンプトでは再定義しません。

- `GO` — 意味上の矛盾は見つからなかった。または、見つかった事項が整理され、後続作業へ安全に進める
- `条件付きGO` — 未解決項目が残るが、後続工程への影響を明記したうえで進んでよい
- `STOP` — 意味上の矛盾があり解決が必要、人間判断待ちが残る、または確認を完遂できなかった

条件付きGOとする場合は、`docs/rules/core/20_approval_and_review.md` の6項目（未解決項目／仮置きする内容と理由／条件付きでも進める理由／後続工程への影響／見直しが必要になる条件／人間判断が必要かどうか）を必ず明記してください。

**「未記載だが問題ではない実装詳細」が多いことを理由に、判定を下げないでください。**

### 2. 対象 scope

確認した scope と、その範囲を記載してください。**確認できなかった範囲がある場合は、必ず明記してください。**

### 3. 参照した正式資料

実際に読んだ正式資料を記載してください。

### 4. 参照した実装・テスト

実際に読んだ実装ファイル・テストファイルを記載してください。

### 5. 意味上の矛盾

見つかった矛盾を記載してください。矛盾がない場合は「なし」と記載してください。

各項目は以下の形式にしてください。

- 対象（ファイルと箇所）:
- 根拠となる正式資料（**ファイル名と、該当する記述**）:
- 正式資料が定義している意味:
- 実際のコードの意味:
- どう食い違っているか:
- 影響（外部動作／テスト／責務／共通設計のどこに及ぶか）:
- 修正候補（どちらを直すべきかの案。正式資料側かコード側かを含む）:
- 人間判断の要否:

**根拠となる正式資料の記述を示せない場合、その項目をここに書かないでください。** 下記6または8へ回してください。

### 6. 未記載だが問題ではない実装詳細

正式資料が規定していないが、正式資料の意味には反していない実装を記載してください。

**これは指摘ではありません。** 確認済みであることを示すために記載します。

| 対象 | 実装詳細の内容 | 問題ないと判断した理由 |
|---|---|---|

該当がない場合は「なし」と記載してください。

**この節の内容を、修正すべき事項として扱わないでください。**

### 7. 正式資料への逆反映候補

コードに存在し、今後も守るべき意味を持つと判断した内容を記載してください。なければ「なし」と記載してください。

| 候補 | 現在の所在 | 今後も守るべき意味だと判断した理由 | 反映先として適切な正式資料 | 置き場がない場合の選択肢 |
|---|---|---|---|---|

**採否は人間が判断します。** このプロンプトでは反映しません。

### 8. 判断材料不足

矛盾かどうかを判断できなかった事項を記載してください。なければ「なし」と記載してください。

- 事項:
- 何が分からないか:
- 何が分かれば判断できるか:

### 9. scope 外の確認候補

指定 scope の外で気づいた確認候補があれば記載してください。なければ「なし」と記載してください。

**この場でscope外を確認しないでください。**

### 10. 推奨する次の作業

- 意味上の矛盾がある場合: 人間が、正式資料側とコード側のどちらを直すかを判断する → 該当する作成系プロンプトまたは実装系プロンプトで別作業として修正する

- 矛盾がなく、確認だけが目的だった場合: 追加作業は不要である旨を記載する
- 確認を完遂できなかった場合: scope を分割して再実施する提案を行う

## 禁止事項

- ファイルを変更すること
- ソースコードを修正すること
- テストコードを修正すること
- 正式資料（仕様・設計・フロー・テスト計画・overview・共通設計）を修正すること
- レビュー結果ファイルを作成・更新すること
- `tasks.md` を更新すること
- `docs/context/` を変更すること
- **正式資料に未記載であることだけを理由に、指摘すること**
- **実装方式の揺らぎ（関数の切り方、変数名、局所的な書き方など）そのものを問題として扱うこと**
- **根拠となる正式資料の記述を示さずに、矛盾として報告すること**
- 逆に、**仕様にない便利機能、外部動作の変更、責務上の意味の変更、維持すべき呼び出し関係の変更を「未記載だから問題なし」として見逃すこと**
- 指定された scope を超えて確認範囲を広げること
- リポジトリ全体を無制限に読むこと
- コードにあるものを、今後も守るべき意味かを確認せずに逆反映候補とすること
- 逆反映候補を、AIの判断で正式資料へ反映すること
