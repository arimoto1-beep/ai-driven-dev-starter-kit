# コード変更の意味と、正式資料への反映要否を整理してください

このプロンプトは、**コードに関する変更**について、その変更をどこまで正式な意味として残す必要があるかを整理するためのものです。

**変更する前でも、変更した後でも使えます。**

| 使う場面 | 例 |
|---|---|
| **変更する前** | コードを読んでいて変更を思いついた。どこから手を付けるべきか判断したい |
| **変更した後** | 人間またはAIがすでにコードを変更した。正式資料へ反映すべき内容が含まれていないか確認したい |

ソースコードを読んでいると、次のような変更を思いつくことがあります。

- 処理は正常だが、少し実装を直したい
- 同じような機能なのに、実装方式が微妙に異なっている
- 命名、責務分担、例外処理、戻り値の扱いを類似機能間でそろえたい
- 一部だけ古い実装方式が残っている
- 重複している処理を整理したい
- 保守しやすい構造へ変更したい
- 将来の変更に備えて内部構造を見直したい
- レビューで指摘されてはいないが、コードを読んでいて違和感がある

これらは、必ずしもバグではありません。また、**必ずしも仕様書や設計書を変更する必要があるとも限りません。**

一方で、「コードをどう変えたいか」「どう変えたか」はイメージできても、「これはバグなのか」「正式資料を変更すべきなのか」「実装詳細として扱ってよいのか」「外部動作は変わるのか」「テスト計画を更新すべきか」「他の類似機能も一緒に確認すべきか」の判断には高い思考負荷がかかります。

このプロンプトは、その判断を支援します。

## 中心となる問い

```text
この変更は、正式資料で意味を定義・維持する必要があるか。
```

**「どこから変更を始めたか」や「誰が変更したか」を中心に判断しません。**

人間が直接修正したか、AIが修正したかは、この分析の結論を変えません。判断するのは、その変更が持つ**意味**です。

**これは、変更案を実装するためのプロンプトではありません。** このプロンプトでは、いかなるファイルも変更しません。Git を参照する場合も読み取り専用です。分析結果はチャットで報告し、どの変更を採用するか、どのフローへ進むかは人間が判断します。

---

## 2つの異なる軸を分けて扱う

この分析では、**変更ルート**と**実施状態**という、独立した2つの軸を扱います。混同しないでください。

- **変更ルート**：この変更を、正式資料でどう扱うべきか（A〜C、または判断不能）
- **実施状態**：この変更が、実際にどこまで進んでいるか（未着手・一部実施・実施済み、コード先行の有無）

この2つは同時に成立します。たとえば、人間がコードを先に直し、その結果として「今後も守るべき意味だ」と分かって正式資料へ反映する場合、**変更ルートはC、実施状態はコード先行済み**です。「コード先行だから何かの型になる」という扱いはしません。コード先行は変更ルートではなく実施状態です。

軸の定義の正本は `docs/rules/core/10_workflow.md` です。このプロンプトでは再定義しません。

## 作業手順

1. 利用者が指定した項目を整理し、未指定項目を洗い出してください
2. `10_overview.md` と対象 feature の正式資料（`20_spec.md`〜`24_review_checklist.md`）を読み直してください
3. 対象 feature の実装ファイルと単体テストファイルを確認してください
4. 実施状態が一部実施・実施済みの場合は、Git差分または変更後のコードを確認してください
5. 類似機能・比較対象がある場合は、その仕様・設計・実装・テストも確認してください
6. 「現在の正式資料が定義している意味」と「今回の変更」を分けて整理してください
7. 変更点を単位ごとに分けてください（1つの作業に複数の性質が混在する場合、無理に1つへ押し込まない）
8. 変更点ごとに、判断材料チェックリストを埋めてください
9. 変更点ごとに、**変更ルート（A〜C、または判断不能）** を判定し、根拠を示してください
10. 変更点ごとに、**実施状態**（未着手／一部実施／実施済み、コード先行の有無）を確認してください
11. ルート・実施状態の組み合わせに応じて必要な整理を行ってください（下記「ルートごとに整理すること」「実施状態ごとに整理すること」）
12. 影響する資産を洗い出してください
13. リスクとトレードオフを整理してください
14. チャットで分析結果を報告してください

## 変更内容の整理方針

コードの変更内容を、そのまま正しい仕様や設計として扱わないでください。

必ず、以下を分けて整理してください。

1. 現在の正式仕様
2. 現在の設計
3. 現在の実装
4. 今回の変更（希望している変更、または実施済みの変更）
5. 変更後に期待する／実際に生じる外部動作
6. 変更後に期待する／実際に生じる内部構造

特に、次を混同しないでください。

- **「現在の実装が仕様どおりであること」と「変更する価値がないこと」は別です。** 正常に動いていても、可読性や保守性の改善が必要な場合があります。
- **「正式資料に書かれていないこと」と「正式資料と矛盾していること」は別です。** 定義は `docs/rules/core/10_workflow.md` の「未記載と矛盾を区別する」を正本とします。

一方で、**「他と違う」という理由だけで、無理に統一してはいけません。**

## 判断材料チェックリスト

変更点ごとに、次を確認してください。**「はい」「いいえ」「不明」と、その根拠を示してください。**

| 確認項目 | 判定 | 根拠 |
|---|---|---|
| 外部から見える動作が変わるか | はい／いいえ／不明 | |
| 入力・出力・制約・エラー契約が変わるか | はい／いいえ／不明 | |
| feature / command / app の責務や境界が変わるか | はい／いいえ／不明 | |
| 呼び出し関係や処理フローとして維持すべき意味が変わるか | はい／いいえ／不明 | |
| 複数機能で守るべき共通設計・共通方針になるか | はい／いいえ／不明 | |
| テスト観点として正式に維持すべき条件が変わるか | はい／いいえ／不明 | |
| 将来のAI実装でも守らせる必要がある内容か | はい／いいえ／不明 | |
| 単なる実装詳細・実装上の選択肢に留まるか | はい／いいえ／不明 | |
| 現在の正式資料と矛盾していないか | 矛盾なし／矛盾あり／不明 | |

**「不明」が残る項目を根拠にして、変更ルートを確定しないでください。** 判断に必要な項目が不明な場合は「判断不能」とします。

## 変更ルート

変更点ごとに、次のいずれかを判定してください。**定義の正本は `docs/rules/core/10_workflow.md` の「変更ルート」です。**

| ルート | 内容 |
|---|---|
| **A. 実装詳細で完結する変更** | 正式資料が意味を定義していない実装詳細だけが変わる。コードとテストだけで完結できる |
| **B. 正式資料を正本として下流へ反映する変更** | 正式資料で定義・維持すべき意味が変わる |
| **C. コード起点の知見を正式資料へ逆反映する変更** | 単なる実装詳細ではなく、今後も守るべき仕様・設計・共通方針だと判断できる |
| **判断不能** | A〜Cのいずれかを確定できない |

- **ひとつの変更に複数のルートが混ざる場合は、変更点を分けてください。** 無理に一つへ押し込まないでください。
- **ルートAは、現在の正式資料と矛盾しないことを確認したうえでのみ選べます。** 矛盾がある場合はルートAにしません。
- **「判断不能」は、変更ルートと並ぶ4つ目の型ではありません。** A〜Cを判定できない状態を表す区分です。
- **複数 feature にまたがる標準化・共通化だからといって、機械的にルートCへ分類しないでください。** 先に人間が「今後この方式を正式ルールにする」と決めて正式資料から変更する場合はルートBです。コードを比較していて気づいた場合にルートCになります。判定基準は「どこでその正式な意味を定義することになったか」です。

---

## 実施状態

変更ルートとは別に、変更点ごとに次を確認してください。**変更ルートを確定させる材料として使わないでください。実施状態は、変更ルートが決まった後、その反映をどう進めるかを左右する別の軸です。**

- **未着手**：まだ変更していない
- **一部実施**：一部のファイルだけ変更済み
- **実施済み**：変更が完了している

さらに、必要に応じて次を確認してください。

- **コード先行**：あり／なし
- **コード先行の理由**（ありの場合）：障害対応／時間制約／検証目的／その他／該当なし

**コード先行は、変更ルートではなく実施状態です。** ルートB またはルートC の変更について、正式資料への反映より先にコードを変更した状態を指します。ルートAには本来当てはまりません（ルートAはそもそも正式資料への反映が不要なため）。

## ルートごとに整理すること

### ルートA（実装詳細で完結する変更）

- **正本を無理に探さないでください。** 「正本候補なし」を STOP の理由にしないでください。
- 正式資料を変更しない理由を、正式資料ごとに示してください
- コードとテストだけで完結できる根拠を示してください（判断材料チェックリストを根拠にする）
- 現在の正式資料と矛盾していないことを、どの資料のどの記述で確認したか示してください
- 必要な検証（実行すべきテスト）を示してください
- 実装とテストの整合が崩れないか確認してください

**ルートAであっても、コードとテストの整合、必要な検証、通常必要となるレビューと報告は省略できません。**

### ルートB（正式資料を正本として下流へ反映する変更）

- 変更内容の正本とする正式資料と、その理由（なぜ役割の合う資料なのか。正本は仕様とは限らない）
- 変更不要と判断した上流資料と、その理由
- 正本から下流への更新順（基本の流れは「正本 → 必要な下流資料 → 実装 → テスト → レビュー」）
- 適切な正本が存在しない場合の扱い（下記「正本候補が見つからない場合」）

### ルートC（コード起点の知見を正式資料へ逆反映する変更）

- どの知見を正式化すべきか
- **なぜ今後も守るべき意味なのか**（実装上の一案ではなく、維持すべき取り決めである根拠）
- どの正式資料が役割として適切か
- その正式資料からさらに下流へ反映が必要か
- 正式化しない場合に起きうる問題

**コードから見つかったものを何でも正式資料へ昇格させないでください。** 昇格させない方がよい候補も、その理由とともに示してください。

### 判断不能

- 何が分からないのか
- 何が分かれば変更ルートを確定できるのか
- 人間が判断すべき事項

## 実施状態ごとに整理すること

### コード先行がある場合（ルートB またはルートC の変更で、コードが先に実施されている）

- 現在コードへ先行して入っている内容
- 正式資料との現在の未整合（どの資料の、どの記述と、どうずれているか）
- 後追いで変更すべき資料
- 反映順
- 必要なテスト
- 必要なレビュー
- 未了項目

**コード先行であることを、後追い反映が不要な理由として扱わないでください。** 未反映事項を残したまま完了として扱えません。**ルートAと混同しないでください。** ルートAは正式資料への反映がそもそも不要な変更であり、コード先行（反映が必要だが順序が後になった状態）とは別です。

## 正本候補が見つからない場合

**「正本候補なし」を一律に STOP へ寄せないでください。** 次の3つを区別してください。

| 状況 | 扱い |
|---|---|
| **正式資料で意味を定義する必要がない実装詳細である**（ローカル変数名、設計書が規定していない範囲の関数分割、同じ意味を保つ実装方式の変更、局所的な可読性改善など） | **ルートA**。正本を持たずに完結してよい。STOP にしない。正式資料を変更しない理由と、完結できる根拠を示す |
| **本来正式資料へ残すべき意味だが、適切な置き場が存在しない**（複数 feature で守るべき新しい共通方針、既存 `common_design/` の責務に当てはまらない横断ルール、新しい種類の正式な設計判断など） | 従来どおり**人間判断**。下記の制約に従う |
| **上記のどちらか判断できない** | **判断不能**。断定せず人間判断へ戻す |

置き場が存在しない場合（2つ目）の制約:

- 各 feature の設計書へ同じルールを無条件に重複記載しない
- 新しい文書種別や配置場所を勝手に作らない
- 「正本の配置について人間判断が必要」と報告する
- 選択肢を示す（例: 既存資料へ局所的に記載する案、新しい共通資料を設ける案、今回は正式化を見送る案）
- 人間が正本の配置を判断するまで、横断的な変更作業を自動的に開始しない

現在の `common_design/` は、ファイル設計（`31_file_design.md`）、データ設計（`32_data_design.md`）、DB設計（`33_db_design.md`）など、既存ルールで定義された用途を持っています。例外処理の書き方、命名、責務分担、実装パターンなどを、役割が合わない共通設計書へ押し込まないでください。

## 実施済みの変更を分析する場合の追加確認

実施状態が一部実施・実施済みの場合は、次も確認してください。

1. 実際の差分が、説明された変更意図と一致しているか
2. **範囲外の変更やついで修正が混入していないか**（混入していた場合は必ず指摘する）
3. 現在の正式資料と**矛盾する**変更が含まれていないか
4. テストの更新要否と、現時点で検証済みか
5. 正式資料へ反映すべき意味が、未反映のまま残っていないか
6. 実装詳細だと説明されているが、実は共通設計・共通方針として維持すべき内容ではないか
7. 変更前後で、既存のテストが確認していた条件が失われていないか

**変更実施者が人間かAIかによって、結論を変えないでください。** ただし、AIが実施した変更で、その task の許可範囲外が変更されていた場合は、範囲外変更として指摘してください。

## 上流から下流への反映順（ルートB、またはコード先行がある場合）

反映が必要な資産が複数ある場合は、原則として以下の順で進めるようにしてください。

1. 変更内容の正本となる正式資料
2. 正本を具体化する下流の設計・フロー
3. テスト計画・レビュー観点
4. 実装
5. テストコード
6. 実装後のレビューと整合性確認

ただし、変更不要な工程や資産は省略し、その理由を示してください。

**「上流優先」は、「すべての上流資料を変更する」という意味ではありません。**

- 外部動作が変わらない場合、`20_spec.md` を無理に変更しない
- command/app の責務や feature 分割が変わらない場合、`10_overview.md` を無理に変更しない
- 呼び出し関係が変わらない場合、`22_flow.md` を無理に変更しない
- テスト観点が変わらない場合、`23_test_plan.md` を無理に変更しない
- 変更不要と判断した上流資料についても、変更不要の理由を報告する
- **正本は仕様とは限りません。** 正本が設計であれば設計から、正本が呼び出しフローであればフローから始まります。「仕様 → 設計 → テスト計画」という順序は、正本が仕様である場合の一例です。

**この順序は、ルートAには適用しません。** ルートAでは正式資料を更新しません。

### 上流資料の基本的な候補（ルートB、C。コード先行がある場合も同様）

| 変更内容 | 正本の主な候補 |
|---|---|
| command/app の目的、Boundary、責務、feature 分割の変更 | `10_overview.md` |
| 利用者や外部システムから見える動作、入力、出力、制約、エラー仕様の変更 | `20_spec.md` |
| 複数 feature に共通するファイル、データ、DBなどの設計変更 | `common_design/` 配下の該当設計書 |
| 個別 feature の内部責務、関数構成、内部エラー処理などの変更 | `21_design.md` |
| 呼び出し順、依存関係、処理フローの変更 | `22_flow.md` |
| テスト観点、正常系、異常系、境界値の変更 | `23_test_plan.md` |
| レビュー観点や実装着手前の確認事項の変更 | `24_review_checklist.md` |
| 上記資料で定義された内容の具体化 | 実装ファイル、テストファイル |

この表は機械的な決定ルールとして扱わず、変更内容と現在の文書構成を確認して判断してください。**この表に当てはまらないからといって、直ちに STOP としないでください。** 実装詳細として完結する場合があります。

## 類似機能・横断的な変更の確認

類似する機能や実装が存在する場合は、変更対象だけを見て結論を出さないでください。

少なくとも以下を確認してください。

1. 類似機能では、どのような実装方式が採用されているか
2. 差異は外部仕様によるものか
3. 差異は内部設計上必要なものか
4. 単なる実装時期、担当者、生成AIの出力差によって生じた可能性があるか
5. どの実装を基準にする根拠があるか
6. 一か所だけ変更すると、新たな不統一が生じないか
7. 横断的に変更すべき対象がほかにないか
8. 統一によって、個別機能の仕様や拡張性を損なわないか
9. 共通化せず各 feature 内に閉じた方がよい可能性はないか

比較結果は、次の表で整理してください。

| 対象 | 現在の仕様 | 現在の実装方式 | 差異 | 差異の理由 | 統一要否 | 推奨対応 |
|---|---|---|---|---|---|---|

差異の理由を確認できない場合は、推測で断定せず「不明」「人間確認が必要」としてください。

**特定の実装を、根拠なく標準実装として選ばないでください。**

**実装方式の揺らぎが存在すること自体を、問題として扱わないでください。** 統一が必要だと判断する場合は、その根拠（正式資料との矛盾、保守上の具体的な支障など）を示してください。

- 共通化候補となる処理
- 現在の配置
- 共通化したい理由
- 共通化しない場合の問題
- 共通化した場合の影響範囲

## 出力形式

以下の形式でチャットに報告してください。

---

### 1. 総合判定

以下のいずれかを記載してください。

- `GO` — 次の作業を具体化できる
- `条件付きGO` — 文書更新や人間確認を行えば、次の作業を具体化できる
- `STOP` — 判断材料、比較範囲、変更目的などが不足し、次の作業を決められない

**判定値そのものの定義は、`docs/rules/core/20_approval_and_review.md` の `GO` / `条件付きGO` / `STOP` を正本とします。**
上記の説明は、この分析 task における各判定の解釈を補足するものであり、判定値を再定義するものではありません。

**ルートAと判定したこと自体を理由に、`STOP` としないでください。** ルートAで、正式資料と矛盾しないことを確認でき、コードとテストの整合と検証方針が示せる場合は `GO` になりえます。

**逆に、この判定は実装を自動承認するものではありません。** 実装を行う場合は、対応する task プロンプトと、そこで定められた承認ゲートに従ってください。条件付きGOの場合は条件を、STOPの場合は何を解決すれば進めるかを明記してください。

### 2. 確認したファイル

実際に確認したファイルを記載してください。Git差分を参照した場合は、参照した範囲（コマンドと対象）も記載してください。

### 3. 変更の要約

何を、なぜ変更したいのか（または変更したのか）を整理してください。**実施状態（未着手／一部実施／実施済み）と、コード先行の有無・理由**を明記してください。未指定項目があれば「未指定」と明記してください。

### 4. 現在の正式資料・設計・実装

現在の正式仕様、設計、実装を分けて記載してください。

### 5. 変更点の分割

1つの作業に複数の性質が混在する場合、変更点を分けて一覧にしてください。単一の場合は「1件」と記載してください。

| 変更点 | 内容 |
|---|---|

### 6. 判断材料チェックリスト

変更点ごとに、「判断材料チェックリスト」の表を記載してください。

### 7. 変更ルートと実施状態

変更点ごとに、**変更ルート**（A／B／C／判断不能）と根拠、**実施状態**（未着手／一部実施／実施済み、コード先行の有無）を、分けて記載してください。

| 変更点 | 変更ルート | ルートの根拠 | 実施状態 | コード先行 |
|---|---|---|---|---|

複数ルートが混在する場合は、それぞれについて次項以降を分けて記載してください。

### 8. ルート・実施状態ごとの整理

「ルートごとに整理すること」「実施状態ごとに整理すること」に従って記載してください。コード先行がある場合は、該当する変更点について両方を記載してください。

### 9. 類似機能・類似実装との比較

比較対象がある場合は、「類似機能・横断的な変更の確認」の表で整理してください。比較対象がない場合は「該当なし」と記載してください。

### 10. 影響する資産

「影響範囲の確認」の表で整理してください。ルートB・ルートC・コード先行のいずれかがある場合は更新順表も記載してください。

### 11. 実施済み変更の確認結果

実施状態が一部実施・実施済みの場合のみ、「実施済みの変更を分析する場合の追加確認」の7項目の結果を記載してください。未着手の場合は「該当なし」と記載してください。

**範囲外の変更やついで修正が混入していた場合は、必ずここに記載してください。**

### 12. リスクとトレードオフ

少なくとも以下を確認してください。

- 対象箇所だけ変更するリスク
- 横断的に変更するリスク
- 統一しないリスク
- 統一することで個別仕様を壊すリスク
- 共通化によって結合度が上がるリスク
- テストが実装詳細に依存するリスク
- 正式資料へ反映しないことのリスク（ルートAと判定した場合）
- 正式資料へ昇格させることのリスク（ルートCと判定した場合。設計書が実装詳細の写しにならないか）

### 13. 人間が判断すべき事項

**変更ルートの採否そのものを、必ずここに含めてください。** そのほか、変更するかどうか、どれを基準実装にするか、どこまで横断変更するか、正本をどこに置くかなど、人間判断が必要な内容を記載してください。

### 14. 推奨する次の作業

既存スターターキットのプロンプトやフローへ接続してください。単に利用するプロンプトを並べたり、「実装してください」と結論づけたりしないでください。

**ルートA の場合:**

- 正式資料の更新作業へは接続しない
- 実装とテストの変更作業（対象 feature の実装であれば `prompts/implement_feature.md`。**実装着手承認欄の確認は通常どおり必要です**）
- `prompts/review_feature_source.md`
- `python -m pytest`

**ルートB の場合（正本別）:**

- `10_overview.md` が正本の場合: `prompts/create_overview.md` で overview を更新 → 人間確認 → feature 資料（`20_spec.md` 以降）へ進む
- `20_spec.md` が正本の場合: `prompts/create_feature_spec.md` で仕様を更新 → 人間確認 → `prompts/create_function_design.md`、必要に応じて `prompts/create_function_call_flow.md`、`prompts/create_test_design.md` へ進む
- `21_design.md` が正本の場合: `prompts/create_function_design.md` で設計を更新 → 人間確認 → 必要に応じて `prompts/create_function_call_flow.md`、`prompts/create_test_design.md` → 実装へ進む
- `common_design/` が正本の場合: 対応する `prompts/create_file_design.md` / `create_data_design.md` / `create_db_design.md` で共通設計を更新 → 人間確認 → 各 feature の `21_design.md` へ反映する

**ルートC の場合:**

- 正式化する知見と反映先を人間が確認する
- 反映先に対応する作成系プロンプト（`create_*`）で、別作業として反映する
- 必要に応じて下流資料・実装・テストへ反映する

**コード先行がある場合（ルートB またはルートC とあわせて）:**

- 後追い反映順に従って、対応する作成系プロンプトで反映する
- 必要なテストを実施する
- 必要なレビューを行う（`prompts/review_feature.md` / `prompts/review_command.md`）
- 未了項目を残課題として明示する

**判断不能の場合:**

- 何が分かれば確定できるかを示し、人間判断を待つ

**その他:**

- バグ候補の場合: `docs/tutorials/040_bug_fix_flow.md` のフローへ進む（`prompts/create_bug_report.md` から開始）
- 共通化候補の場合: `docs/templates/30_common_proposal_template.md` を使った別作業で提案を整理し、人間判断を待つ
- 正本の配置に人間判断が必要な場合: 人間が判断するまで、横断実装へ進まない
- 現在の正式資料とコード全体の整合が気になる場合: `prompts/review_design_code_consistency.md` へ委譲する

- 理由

## 禁止事項

- ファイルを変更すること
- ソースコードを修正すること
- テストコードを修正すること
- 仕様書・設計書・テスト計画を修正すること
- `tasks.md` を更新すること
- 作業ツリーやリポジトリの状態を変える Git コマンドを実行すること
- バグと判断しただけでバグ修正を開始すること
- 正常動作しているものを無理にバグとして扱うこと
- コード変更内容をそのまま仕様として採用すること
- 実装方式の違いを根拠なく統一すること
- 実装方式の揺らぎが存在すること自体を、問題として扱うこと
- 一つの実装を根拠なく標準として選ぶこと
- 類似処理を直ちに `src/common/` へ移すこと
- 調査対象外のファイルを横断的に修正すること
- 人間の承認なしに次工程へ進むこと
- 正本を特定せず、複数の下流資料へ同じ変更内容を分散して記載すること
- 変更不要な上流資料を形式的に更新対象へ含めること
- 適切な配置場所がない共通方針を、役割の合わない `common_design/` へ記載すること
- 正本の配置について人間判断が必要なのに、AIが新しい文書やディレクトリを勝手に作ること
- **正式資料に未記載であることだけを理由に、不整合として扱うこと**
- **正式資料へ反映すべき意味を持つ変更について、反映を省略してよいと結論づけること**
- **判断材料が不足しているのに、変更ルートを確定すること**
- **現在の正式資料と矛盾する実装を、ルートAとして扱うこと**
- **コード先行であることを、後追い反映が不要な理由として扱うこと**
- **コードから見つかった内容を、今後も守るべき意味かを確認せずに正式資料へ昇格させること**
- **ルートAと判断したことを理由に、検証・レビュー・報告を省略すること**
- **変更ルートの判定を理由に、このプロンプトの作業範囲や保護対象の扱いを広げること**
- **「正本候補なし」を一律に STOP とすること**
- **コード先行を独立した変更ルートとして扱うこと。コード先行は実施状態であり、変更ルートA〜Cとは別の軸です**
- **標準化・共通化という変更内容だけを理由に、機械的にルートCへ分類すること**

このプロンプトは、変更の意味の見極め・変更ルートと実施状態の判定・影響範囲の整理・次の作業の提示だけを行います。
