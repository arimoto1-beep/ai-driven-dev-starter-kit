# コード変更案の影響範囲を整理してください

このプロンプトは、**コードを見ていて思いついた変更案**を入口にして、正式な変更作業へ進む前に影響範囲を整理するためのものです。

ソースコードを読んでいると、次のような変更を思いつくことがあります。

- 処理は正常だが、少し実装を直したい
- 同じような機能なのに、実装方式が微妙に異なっている
- 命名、責務分担、例外処理、戻り値の扱いを類似機能間でそろえたい
- 一部だけ古い実装方式が残っている
- 重複している処理を整理したい
- 保守しやすい構造へ変更したい
- 将来の変更に備えて内部構造を見直したい
- レビューで指摘されてはいないが、コードを読んでいて違和感がある

これらは、必ずしもバグではありません。仕様どおり正常に動いていても、設計改善・リファクタリング・類似機能間の整合性改善・標準化・共通化検討を行いたい場合があります。

一方で、「コードをどう変えたいか」はイメージできても、「これはバグなのか」「仕様変更が必要なのか」「設計書だけを変えればよいのか」「外部動作は変わるのか」「テスト計画を更新すべきか」「他の類似機能も一緒に確認すべきか」「共通化すべきか」「どの既存フローへ接続すべきか」の判断には高い思考負荷がかかります。

このプロンプトは、その判断を支援します。

**これは、変更案を実装するためのプロンプトではありません。** このプロンプトでは、いかなるファイルも変更しません。分析結果はチャットで報告し、どの変更を採用するか、どのフローへ進むかは人間が判断します。

## 作業手順

1. 利用者が指定した項目を整理し、未指定項目を洗い出してください
2. `10_overview.md` と対象 feature の正式資料（`20_spec.md`〜`24_review_checklist.md`）を読み直してください
3. 対象 feature の実装ファイルと単体テストファイルを確認してください
4. 類似機能・比較対象がある場合は、その仕様・設計・実装・テストも確認してください
5. 「現在の仕様・設計・実装」と「利用者が希望している変更」を分けて整理してください
6. 変更を分類し、変更目的を整理してください
7. 変更内容を定義すべき最上流かつ適切な正式資料を特定し、その資料を変更内容の正本とする根拠を整理してください
8. 変更不要と判断した上流資料と、その理由を整理してください
9. 適切な正本が現在の構成に存在しない場合は、人間判断事項として整理してください（勝手に新しい資料を作らないでください）
10. 影響する資産を洗い出してください
11. 正本から下流への更新順を整理してください
12. リスクとトレードオフを整理してください
13. チャットで分析結果を報告してください

## 変更案の整理方針

コードの変更案を、そのまま正しい仕様や設計として扱わないでください。

必ず、以下を分けて整理してください。

1. 現在の正式仕様
2. 現在の設計
3. 現在の実装
4. 利用者が希望している変更
5. 変更後に期待する外部動作
6. 変更後に期待する内部構造

特に、**「現在の実装が仕様どおりであること」と「変更する価値がないこと」を混同しないでください。** 正常に動いていても、設計改善や実装方式の統一が必要な場合があります。

一方で、**「他と違う」という理由だけで、無理に統一してはいけません。**

## 変更の分類

主分類として、少なくとも以下を扱ってください。

- 既存仕様どおりに動作していないバグ候補
- 既存仕様を変更する機能変更
- 既存 feature の責務内にある軽微な機能追加
- 外部動作を変えない内部設計の変更
- 外部動作を変えないリファクタリング
- 類似機能間の実装方式をそろえる整合性改善
- 複数機能にまたがる標準化
- 共通化候補
- ドキュメント・実装・テスト間の不整合
- コード上の好みまたは局所的な改善案
- 判断材料不足

主分類を無理に一つへ限定する必要はありません。複数の性質を持つ場合は、主分類と副分類、または変更目的のタグを分けて示してください。

変更目的として、次のような観点も整理してください。

- 不具合解消
- 外部動作の変更
- 可読性改善
- 保守性改善
- 重複削減
- 責務分担の改善
- 類似機能との統一
- プロジェクト標準への準拠
- 将来変更への備え
- 性能改善
- セキュリティ改善
- 運用性改善

## 変更の正本と上流からの更新

影響する資料を列挙するだけで終わらせないでください。変更内容を**どの資料で定義するか**を先に決めないと、より上流で一度だけ定義すべき内容が、各 feature の設計書や実装へ分散します。

### 正本の特定

変更案について、その内容を正式に定義すべき資料を特定してください。

**正本**とは、その変更内容を最初に定義し、下流資料や実装が参照・具体化する基準となる正式資料です。

複数の資料に同じ内容を重複して書く前に、どの資料を正本とするかを整理してください。

### 上流資料の基本的な候補

| 変更内容 | 正本の主な候補 |
|---|---|
| command/app の目的、Boundary、責務、feature 分割の変更 | `10_overview.md` |
| 利用者や外部システムから見える動作、入力、出力、制約、エラー仕様の変更 | `20_spec.md` |
| 複数 feature に共通するファイル、データ、DBなどの設計変更 | `common_design/` 配下の該当設計書 |
| 個別 feature の内部責務、関数構成、内部エラー処理などの変更 | `21_design.md` |
| 呼び出し順、依存関係、処理フローの変更 | `22_flow.md` |
| テスト観点、正常系、異常系、境界値の変更 | `23_test_plan.md` |
| レビュー観点や実装着手前の確認事項の変更 | `24_review_checklist.md` |
| 上記資料で定義された内容の具体化 | 実装ファイル、テストファイル |

この表は機械的な決定ルールとして扱わず、変更内容と現在の文書構成を確認して判断してください。

### 上流資料を無理に変更しない

**「上流優先」は、「すべての上流資料を変更する」という意味ではありません。** 変更内容を正式に定義する場所として、最も上流かつ**役割の合う**資料を選ぶという意味です。

- 外部動作が変わらない場合、`20_spec.md` を無理に変更しない
- command/app の責務や feature 分割が変わらない場合、`10_overview.md` を無理に変更しない
- 呼び出し関係が変わらない場合、`22_flow.md` を無理に変更しない
- テスト観点が変わらない場合、`23_test_plan.md` を無理に変更しない
- 変更不要と判断した上流資料についても、変更不要の理由を報告する

たとえば、外部動作を変えない個別 feature 内のリファクタリングであれば、`20_spec.md` を無理に変更せず、`21_design.md` を正本とする場合があります。一方で、利用者から見える動作が変わる場合は、実装や設計書より先に `20_spec.md` を更新する必要があります。

### 適切な正本が存在しない場合

複数 feature に共通する実装方針を統一したい場合でも、既存の `common_design/` に役割の合わない内容を無理に記載してはいけません。

現在の `common_design/` は、ファイル設計（`31_file_design.md`）、データ設計（`32_data_design.md`）、DB設計（`33_db_design.md`）など、既存ルールで定義された用途を持っています。例外処理の書き方、命名、責務分担、実装パターンなどを、役割が合わない共通設計書へ押し込まないでください。

変更内容を定義する適切な正式資料が現在の構成に存在しない場合は、次のように扱ってください。

- 各 feature の設計書へ同じルールを無条件に重複記載しない
- 新しい文書種別や配置場所を勝手に作らない
- 「正本候補なし」または「正本の配置について人間判断が必要」と報告する
- 選択肢を示す（例: 既存資料へ局所的に記載する案、新しい共通資料を設ける案、今回はコードと作業報告だけに限定する案）
- 人間が正本の配置を判断するまで、横断的な変更作業を自動的に開始しない

人間判断がなければ変更順を確定できない場合は、総合判定を `STOP` としてください。後続作業を限定的に進められる場合は、未確定事項と対象範囲を明示したうえで `条件付きGO` としてください。

### 上流から下流への反映順

変更対象が複数ある場合は、原則として以下の順で進めるようにしてください。

1. 変更内容の正本となる正式資料
2. 正本を具体化する下流の設計・フロー
3. テスト計画・レビュー観点
4. 実装
5. テストコード
6. 実装後のレビューと整合性確認

ただし、変更不要な工程や資産は省略し、その理由を示してください。

**コードとドキュメントを一括で変更するよう勧めないでください。** 正式資料の更新内容を人間が確認してから下流へ進む順番を提示してください。

## 類似機能・横断的な変更の確認

類似する機能や実装が存在する場合は、変更対象だけを見て結論を出さないでください。

少なくとも以下を確認してください。

1. 類似機能では、どのような実装方式が採用されているか
2. 差異は外部仕様によるものか
3. 差異は内部設計上必要なものか
4. 単なる実装時期、担当者、生成AIの出力差によって生じた可能性があるか
5. どの実装を基準にする根拠があるか
6. 一か所だけ変更すると、新たな不統一が生じないか
7. 横断的に変更すべき対象がほかにないか
8. 統一によって、個別機能の仕様や拡張性を損なわないか
9. 共通化せず各 feature 内に閉じた方がよい可能性はないか

比較結果は、次の表で整理してください。

| 対象 | 現在の仕様 | 現在の実装方式 | 差異 | 差異の理由 | 統一要否 | 推奨対応 |
|---|---|---|---|---|---|---|

差異の理由を確認できない場合は、推測で断定せず「不明」「人間確認が必要」としてください。

**特定の実装を、根拠なく標準実装として選ばないでください。**

## 共通化の扱い

似た処理が複数あっても、直ちに `src/common/` へ切り出してはいけません。

共通化候補の場合は、以下を整理してください。

- 共通化候補となる処理
- 現在の配置
- 共通化したい理由
- 共通化しない場合の問題
- 共通化した場合の影響範囲
- 個別 feature に残す代替案
- 現時点で共通化を検討すべきか

判断に迷う場合は、まず機能内に閉じた実装を優先してください。

共通化を進める価値がありそうな場合は、`docs/templates/30_common_proposal_template.md` を使って `docs/common/` 配下に提案をまとめる**別作業**を推奨してください。このプロンプトでは `docs/common/` も `src/common/` も変更しません。

### 更新順の整理

- 実装とテストコードは、正式資料の更新後に置く
- 同じ優先順位の資産が複数ある場合は、その旨を記載してよい
- 変更不要な資産は更新順表に入れず、上の影響範囲表で理由を示す

## 出力形式

以下の形式でチャットに報告してください。

---

### 1. 総合判定

以下のいずれかを記載してください。

- `GO` — 次の正式な変更作業を具体化できる
- `条件付きGO` — 文書更新や人間確認を行えば、次の変更作業を具体化できる
- `STOP` — 仕様判断、比較範囲、変更目的などが不足し、次の作業を決められない

**判定値そのものの定義は、`docs/rules/core/20_approval_and_review.md` の `GO` / `条件付きGO` / `STOP` を正本とします。**
上記の説明は、この分析 task における各判定の解釈を補足するものであり、判定値を再定義するものではありません。

この判定は、**実装を自動承認するものではありません。** 条件付きGOの場合は条件を、STOPの場合は何を解決すれば進めるかを明記してください。

### 2. 確認したファイル

実際に確認したファイルを記載してください。

### 3. 変更案の要約

利用者が何を、なぜ変更したいのかを整理してください。未指定項目があれば「未指定」と明記してください。

### 4. 現在の仕様・設計・実装

現在の正式仕様、設計、実装を分けて記載してください。

### 5. 変更の分類

主分類、副分類、変更目的と、その理由を記載してください。

### 6. 変更後に期待する状態

外部動作と内部構造を分けて記載してください。外部動作を変えない場合は、その旨を明示してください。

### 7. 類似機能・類似実装との比較

比較対象がある場合は、「類似機能・横断的な変更の確認」の表で整理してください。比較対象がない場合は「該当なし」と記載してください。

### 8. 影響する資産

「影響範囲の確認」の表で整理してください。

### 9. 変更の正本と更新順

「変更の正本と上流からの更新」に従って、少なくとも以下を記載してください。

- 変更内容の正本とする正式資料
- その資料を正本とする理由（なぜそれが最上流かつ役割の合う資料なのか）
- 変更不要と判断した上流資料と、その理由
- 上流から下流への更新順（「影響範囲の確認」の更新順表を使う）
- 適切な正本が存在しない場合の選択肢
- 正本の配置について人間判断が必要かどうか
- 正式資料を更新せずにコードだけ変更してよいか

### 10. リスクとトレードオフ

少なくとも以下を確認してください。

- 対象箇所だけ変更するリスク
- 横断的に変更するリスク
- 統一しないリスク
- 統一することで個別仕様を壊すリスク
- 共通化によって結合度が上がるリスク
- テストが実装詳細に依存するリスク

### 11. 人間が判断すべき事項

変更するかどうか、どれを基準実装にするか、どこまで横断変更するか、正本をどこに置くかなど、人間判断が必要な内容を記載してください。

### 12. 推奨する次の作業

既存スターターキットのプロンプトやフローへ接続してください。**正本から下流へ進む順番で示してください。** 単に利用するプロンプトを並べたり、「実装してください」と結論づけたりしないでください。

正本別の進め方:

- `10_overview.md` が正本の場合:
  - `prompts/create_overview.md` で overview を更新 → 人間確認 → feature 資料（`20_spec.md` 以降）へ進む
- `20_spec.md` が正本の場合:
  - `prompts/create_feature_spec.md` で仕様を更新 → 人間確認 → `prompts/create_function_design.md`、必要に応じて `prompts/create_function_call_flow.md`、`prompts/create_test_design.md` へ進む
- `21_design.md` が正本の場合:
  - `prompts/create_function_design.md` で設計を更新 → 人間確認 → 必要に応じて `prompts/create_function_call_flow.md`、`prompts/create_test_design.md` → 実装へ進む
- `common_design/` が正本の場合:
  - 対応する `prompts/create_file_design.md` / `create_data_design.md` / `create_db_design.md` で共通設計を更新 → 人間確認 → 各 feature の `21_design.md` へ反映する
- バグ候補の場合:
  - `docs/tutorials/040_bug_fix_flow.md` のフローへ進む（`prompts/create_bug_report.md` から開始）
- 共通化候補の場合:
  - `docs/templates/30_common_proposal_template.md` を使った別作業で提案を整理し、人間判断を待つ
- 正本候補が存在しない場合:
  - 人間が正本の配置を決めるまで、横断実装へ進まない

実装反映後は、以下を共通の締めとしてください。

- `prompts/review_feature_source.md`
- `python -m pytest`
- 必要に応じて `prompts/review_feature.md`
- 必要に応じて `prompts/review_command.md`

### 13. tasks.md 更新候補

このプロンプトでは `tasks.md` を直接変更しません。更新した方がよい内容がある場合は、以下を候補として記載してください。なければ「なし」と記載してください。

- 対象 tasks.md
- 更新候補
- 理由

## 禁止事項

- ファイルを変更すること
- ソースコードを修正すること
- テストコードを修正すること
- 仕様書・設計書・テスト計画を修正すること
- `tasks.md` を更新すること
- バグと判断しただけでバグ修正を開始すること
- 正常動作しているものを無理にバグとして扱うこと
- コード変更案をそのまま仕様として採用すること
- 実装方式の違いを根拠なく統一すること
- 一つの実装を根拠なく標準として選ぶこと
- 類似処理を直ちに `src/common/` へ移すこと
- 調査対象外のファイルを横断的に修正すること
- 人間の承認なしに次工程へ進むこと
- 正本を特定せず、複数の下流資料へ同じ変更内容を分散して記載すること
- 変更不要な上流資料を形式的に更新対象へ含めること
- 適切な配置場所がない共通方針を、役割の合わない `common_design/` へ記載すること
- 正式資料の更新前に実装変更を推奨すること
- 正本の配置について人間判断が必要なのに、AIが新しい文書やディレクトリを勝手に作ること

このプロンプトは、コード起点の変更案の分類・影響範囲の整理・正本と更新順の整理・次の作業の提示だけを行います。
