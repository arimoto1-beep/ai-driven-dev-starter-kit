# feature 実装直後のソースレビューを行ってください

このプロンプトは、`prompts/implement_feature.md` で作成した feature 実装ファイルと feature 単体テストファイルを対象に、**実装直後の中間チェック**を行うためのものです。

問題を見つけても、このプロンプトでファイルを修正しません。修正候補としてチャットで報告するだけです。

`25_review_result.md` は作成しません。正式なレビュー結果ファイルは、従来どおり `prompts/review_feature.md` で作成してください。

---

## review_feature.md との違い

| | review_feature_source.md（このプロンプト） | review_feature.md |
|---|---|---|
| 位置づけ | 実装直後の中間チェック | feature 単体の正式レビュー |
| 主な対象 | feature 実装ファイルと feature 単体テストファイル | 仕様、設計、実装、単体テスト、レビュー観点の整合 |
| 修正 | しない | しない（指摘のみ） |
| 出力先 | チャットで報告する | `25_review_result.md` に記録する |

## 未記載と矛盾を区別する

確認を始める前に、次の区別を必ず押さえてください。

| | 内容 | 扱い |
|---|---|---|
| **未記載** | 正式資料がその実装詳細を規定していない。実装側に具体的な処理が存在するが、正式資料が定義する意味には反していない | **それだけでは指摘しません** |
| **矛盾** | 正式資料が定義している意味と、実装の意味が食い違っている | **指摘します** |

**「設計書に書いてない」ことは、「設計書と矛盾している」ことではありません。**

生成されたコードには、同じ仕様・設計でも実装上の揺らぎ（関数の切り方、局所的な書き方、変数名、冗長さ、同じ意味を持つ複数の実装方法など）があります。**揺らぎが存在すること自体を指摘にしないでください。**

指摘する場合は、**どの正式資料の、どの記述が定義している意味と食い違うか**を示してください。示せないものは指摘とせず、「未記載だが問題ではない実装詳細」または「要仕様確認」として扱ってください。

ただし、次は「未記載だから問題なし」としてはいけません。正式資料が意味を定義している領域だからです。

- 仕様にない便利機能の追加
- 外部から見える動作の変更
- 責務・境界としての意味の変更
- `22_flow.md` が維持すべき意味として定めた呼び出し関係の変更
- 共通設計で定義された内容との食い違い

原則の正本は `docs/rules/core/10_workflow.md` の「未記載と矛盾を区別する」です。このプロンプトでは再定義しません。

## 確認観点

以下の観点で確認してください。

**仕様・設計との整合**

- 仕様にない便利機能を追加していないか（**未記載ではなく矛盾として扱う**）
- `20_spec.md` が定義する入力・出力・制約・エラー動作と、実装の動作が食い違っていないか
- `21_design.md` が定めた責務の外にある処理を、feature が担っていないか（**設計書に記載のない関数が存在すること自体は指摘しない。担っている責務が設計と食い違う場合に指摘する**）
- `22_flow.md` が維持すべき意味として定めた呼び出し順・依存関係と、実装が食い違っていないか（**内部的な関数分割や補助関数の有無は、それだけでは指摘しない**）
- エラー処理や境界値が、仕様・テスト計画が定義する意味とズレていないか

**責務分担**

- CLI引数解析や標準出力など、entrypoint の責務が feature に混ざっていないか
- feature 固有ロジックが entrypoint 側に逃げていないか
- `src/common/` に勝手に切り出していないか
- 標準ライブラリ以外を勝手に使っていないか

**テストの妥当性**

- `23_test_plan.md` の観点を単体テストが満たしているか
- `24_review_checklist.md` の観点に照らして大きな懸念がないか
- テストが、正式資料が定義していない実装詳細に依存しすぎていないか（**依存していること自体は直ちに指摘とせず、仕様どおりでも実装を変えるとテストが壊れる構造になっている場合に改善候補とする**）
- テストが実装の誤りを追認する形になっていないか

**範囲外変更**

- AIが指示範囲外のついで修正をしていないか
- 指定されていないファイルが変更されていないか

**逆反映候補**

- 実装に、単なる実装詳細ではなく**今後も守るべき仕様・設計・共通方針**として維持すべき内容が含まれていないか

これは矛盾ではありません。見つかった場合は「仕様・設計・テスト計画とのズレ」ではなく、**修正候補とは別枠**で報告してください。**コードにあるものを何でも昇格候補にしないでください。** 今後も守るべき意味を持つ根拠を示してください。採否は人間が判断します。

## 出力形式

以下の形式でチャットに報告してください。

---

### 1. 中間チェック判定

以下のいずれかを記載してください。

- `テスト実行に進めてよい` — 大きな問題なし
- `修正候補あり` — 軽微な懸念または要修正候補がある
- `要人間確認` — 仕様確認や判断が必要な点がある

### 2. 確認したファイル

参照したファイルの一覧を記載してください。

### 3. ソースレビュー結果

各観点の結果を以下の区分で記載してください。

- 問題なし
- 軽微な懸念
- 要修正候補
- 要仕様確認

### 4. 実装ファイルに関する指摘

実装ファイルへの具体的な指摘があれば記載してください。問題なしの場合もその旨を記載してください。

**各指摘には、どの正式資料の、どの記述が定義している意味と食い違うかを示してください。**

### 5. 単体テストファイルに関する指摘

テストファイルへの具体的な指摘があれば記載してください。問題なしの場合もその旨を記載してください。

### 6. 正式資料との矛盾

`20_spec.md`、`21_design.md`、`22_flow.md`、`23_test_plan.md` が定義している意味と、実装が食い違っている点があれば記載してください。なければ「なし」と記載してください。

### 7. 未記載だが問題ではない実装詳細

正式資料が規定していないが、正式資料の意味には反していない実装を記載してください。なければ「なし」と記載してください。

**これは指摘ではありません。** 確認済みであることを示すために記載します。**修正すべき事項として扱わないでください。**

### 8. 正式資料への逆反映候補

実装に含まれる、今後も守るべき意味を持つ内容があれば記載してください。なければ「なし」と記載してください。

- 候補:
- 今後も守るべき意味だと判断した理由:
- 反映先として適切な正式資料:

**採否は人間が判断します。このプロンプトでは反映しません。**

### 9. ついで修正・範囲外変更の有無

指示範囲外の変更があれば記載してください。問題なしの場合もその旨を記載してください。

### 10. 修正する場合の推奨対応

修正候補がある場合、どのように修正すべきかを記載してください。

**このプロンプトでは修正しません。** 修正は、人間が反映対象を判断した後、別作業としてAIに依頼してください。

### 11. 次に進む場合の候補

- 問題なしの場合: `python -m pytest` を実行する
- 修正候補がある場合: 人間が反映対象を判断し、別作業としてAIに修正依頼する
- 仕様確認が必要な場合: `20_spec.md` または `21_design.md` に戻る
- 逆反映候補がある場合: `prompts/analyze_code_change_impact.md` で変更ルートと反映先を整理する、または人間が直接判断する

## 禁止事項

- feature 実装ファイルの修正
- feature 単体テストファイルの修正
- docs の修正
- `tasks.md` の更新
- `25_review_result.md` の作成
- `src/common/` への切り出し
- `python -m pytest` の実行
- 自動修正
- **正式資料に未記載であることだけを理由に指摘すること**
- **実装方式の揺らぎ（関数の切り方、変数名、局所的な書き方など）そのものを指摘にすること**
- **根拠となる正式資料の記述を示さずに、矛盾として報告すること**
- 逆に、**仕様にない便利機能、外部動作の変更、責務上の意味の変更、維持すべき呼び出し関係の変更を「未記載だから問題なし」として見逃すこと**
- **逆反映候補を、AIの判断で正式資料へ反映すること**

このプロンプトは、ソースレビューと修正候補の報告だけを行います。
