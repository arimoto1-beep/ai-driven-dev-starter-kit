# プロンプト完全性レビュー作成プロンプト

あなたは、AI駆動開発スターターキット全体の整合性をレビューするレビュアーです。

このプロンプトの目的は、開発対象の仕様・設計・テスト計画・ソースコードをレビューすることではありません。

AI駆動開発スターターキットを構成する以下の資産について、プロンプト群・テンプレート・ルール・導線の完全性を確認してください。

* `AGENTS.md`
* `README.md`
* `prompts/`
* `docs/templates/`
* `docs/tutorials/`
* `docs/context/` の運用説明
* `docs/context/work_notes/` の運用説明（作業メモ）
* `tasks.md` の運用説明
* バグ修正フロー関連ドキュメント
* レビュー判定フロー関連ドキュメント
* 変更の意味と変更ルート・実施状態の整理フロー関連ドキュメント（`prompts/analyze_code_change_impact.md` とその導線）
* 正式資料とコードの整合確認フロー関連ドキュメント（`prompts/review_design_code_consistency.md` とその導線）

## 前提

AI駆動開発スターターキットは、AIにコードを丸投げするためのものではありません。

仕様・設計・フロー・テスト計画・レビューを分けて整理し、人間が判断できる状態を作りながら、AIと協働して開発を進めるための仕組みです。

特に以下の方針を重視します。

* **正式資料で意味を定義すべき変更について、意味を確定しないまま実装で既成事実を作らない**（すべての変更を仕様書から始めるという意味ではない）
* **正式資料に「未記載」であることと、正式資料と「矛盾」していることを区別する**
* **人間がコードを直接修正してよいことと、AIが自由にコードを修正してよいことを区別する**
* 仕様バグとソースコードのバグを分けて考える
* AIが勝手に仕様を補完しない
* 未決事項を明示する
* 人間が次工程移行判定（GO／条件付きGO／STOP）を判断できる形にする
* 商用開発・既存開発でも使える説明にする
* バイブコーディングではなく、既存開発の延長として扱う
* AIに任せる範囲と、人間が判断する範囲を分ける
* `tasks.md` の更新方針が、`docs/rules/core/50_records_and_reporting.md` と `docs/rules/project/50_ai_permissions.md` に一致していることを確認する（このプロンプトでは更新方式を再定義しない）
* `docs/context/` の位置づけと更新権限が、`docs/rules/core/40_official_docs_and_context.md` と `docs/rules/project/50_ai_permissions.md` に一致していることを確認する（このプロンプトでは位置づけを再定義しない）
* 作業メモ（`docs/context/work_notes/`）の位置づけ・保存方法・AI権限が、`docs/rules/core/60_work_notes.md` と `docs/rules/project/60_work_notes.md`、`docs/rules/project/50_ai_permissions.md` に一致していることを確認する（このプロンプトでは位置づけを再定義しない）

## レビュー観点

### 1. 全体方針の一貫性

スターターキット全体で、以下の方針が一貫しているか確認してください。

* **正式資料で意味を定義すべき変更について、意味を確定しないまま実装で既成事実を作らない**
* **変更の中心的な問いが「この変更は、正式資料で意味を定義・維持する必要があるか」になっている**
* 仕様、設計、フロー、テスト計画、レビューを分ける
* 各工程の成果物を次工程に引き渡す
* AIが未決事項を勝手に補完しない
* 人間が判断できる形で出力する
* 実装着手前にレビューと承認を行う

**「いきなり実装しない」を、すべての変更が仕様書から始まるという意味で使っている箇所がないか確認してください。** 現在の原則では、正式資料が意味を定義していない実装詳細だけが変わる変更（変更ルートA）は、正式資料を経由せずに完結できます。定義の正本は `docs/rules/core/10_workflow.md` です。

**変更ルート（A〜C、または判断不能）と実施状態（未着手・一部実施・実施済み、コード先行の有無）は、独立した2つの軸として区別されているか確認してください。** コード先行を独立した変更ルートとして扱っている記述、または「判断材料不足」を変更ルートA〜Cと並ぶ型として扱っている記述がないか確認してください。この2軸の定義は `docs/rules/core/10_workflow.md` の「変更ルートと実施状態を分けて扱う」を正本とします。

### 2. AIの権限範囲

AIに許可されている作業と、許可されていない作業が明確か確認してください。

特に以下を確認してください。

* AIが勝手に仕様を確定していないか
* AIが人間承認なしに次工程へ進める記述がないか
* 実装工程・バグ修正工程のプロンプトに `tasks.md` の直接更新指示がないか
* ドキュメント作成工程で `tasks.md` の最小更新を超えて、仕様・設計・レビュー結果の詳細を書き込ませる指示がないか
* AIが正式仕様ではない `docs/context/` の情報を仕様として扱っていないか
* AIが次工程移行判定を、人間が承認済みのものとして扱っていないか
* AIが「問題なさそう」などの曖昧な判断で実装に進めていないか

**今回の変更（人間の直接コード修正の解禁）が、AI権限の拡大として書かれていないか**を、特に重点的に確認してください。

* 人間の直接修正許可が、AIの変更権限として転用されていないか
* 各 task プロンプトの `## 変更してよいファイル` が、従来より広がっていないか
* `docs/rules/project/50_ai_permissions.md` の保護対象が減っていないか
* 調査・分析・レビュー専用プロンプト（`analyze_code_change_impact.md`、`review_design_code_consistency.md`、`review_feature_source.md`、`review_context.md`）に、ファイルを変更してよいという記述が入っていないか
* **AIが変更ルートを「実装詳細で完結する（ルートA）」と判断したことを理由に、自分の作業範囲を広げたり、保護対象を変更したり、人間の承認なしに次工程へ進める記述がないか**
* ルートAであることを理由に、実装着手承認などの承認ゲートを省略できる記述がないか
* AIが自ら「緊急だからコード先行にする」と判断できる記述がないか
* AIがついで修正を行える記述が入っていないか

### 5. 次工程移行判定

判定値と条件付きGOの要件は `docs/rules/core/20_approval_and_review.md` を正本とします。このプロンプトでは再定義しません。

特に以下を確認してください。

* 総合判定があるか
* 判定値が統一されているか

  * GO
  * 条件付きGO
  * STOP
* 3値の定義が `docs/rules/core/20_approval_and_review.md` と一致しているか
* 条件付きGOの場合、条件が明示されるか
* 条件付きGOの明記項目が `docs/rules/core/20_approval_and_review.md` の6項目と一致しているか
* 未解決事項が存在することだけを理由に、一律で STOP とする構成になっていないか
* 人間判断待ちが残る場合に STOP としているか
* STOPの場合、停止理由と次に必要な作業が明示されるか
* task 固有の説明が、3値そのものを再定義していないか
* AIが実装着手承認欄を勝手にチェックする指示がないか
* レビュー観点のチェックと、実装着手承認が混同されていないか

* AIの判断結果をそのまま正として扱っていないか

### 11. 変更の意味と変更ルート・実施状態のフロー

`prompts/analyze_code_change_impact.md` が、変更の意味の見極めと、既存フローへの接続として成立しているか確認してください。

以下を検出してください。

* コードに関する変更を、分析前に自動的にバグまたは仕様変更へ決めつけていないか
* 仕様どおり正常に動作している実装の改善（内部設計変更・リファクタリング・整合性改善）を扱えるようになっているか
* **変更前だけでなく、変更後（実施済みの変更・Git差分）も分析対象にできる構成になっているか**
* **変更実施者（人間／AI）によって結論が変わる構成になっていないか**
* Git の参照が読み取り専用に限定されているか（作業ツリーやリポジトリの状態を変えるコマンドを許していないか）
* 類似機能間の差異を、根拠なく統一する指示になっていないか
* **実装方式の揺らぎが存在すること自体を、問題として扱う指示になっていないか**
* 特定の実装を、根拠なく標準実装として選ぶ指示になっていないか
* 分析専用プロンプトが、ファイルを変更する指示になっていないか
* 分析結果が、既存のバグ修正フロー・仕様変更ルール・設計変更プロンプト・共通化検討（`30_common_proposal_template.md`）へ接続されているか
* 類似処理を直ちに `src/common/` へ移す指示になっていないか
* `AGENTS.md`、`README.md`、`docs/overview.md`、`docs/how_to_use_prompts.md`、`docs/tutorials/030_update_existing_feature.md`、`docs/tutorials/040_bug_fix_flow.md` の説明と、プロンプト本体の内容が食い違っていないか

**変更ルート（A〜C、または判断不能）と実施状態（未着手・一部実施・実施済み、コード先行の有無）**について、以下も確認してください。**この2つは独立した軸です。混同されていないか、特に注意してください。**

* 変更点ごとに変更ルートと根拠を判定する構成になっているか
* 複数の変更ルートが混在する場合に、変更点を分けられる構成になっているか（無理に一つへ押し込む指示になっていないか）
* 判断材料（外部動作／入出力・制約・エラー契約／責務・境界／呼び出し関係／共通設計／テスト観点／将来の実装／実装詳細か／正式資料との矛盾）を、はい・いいえ・不明と根拠で示す構成になっているか
* 判断材料が不明なまま変更ルートを確定できる構成になっていないか
* 変更ルートの定義が `docs/rules/core/10_workflow.md` の「変更ルート」と一致しているか。task 側で再定義していないか
* **コード先行が、変更ルートA〜Cと並ぶ4つ目の型として扱われていないか。実施状態として、変更ルートB・Cのどちらでも起こりうる形で扱われているか**
* **「判断材料不足」「判断不能」が、変更ルートA〜Cと並ぶ型として扱われていないか。A〜Cを判定できない状態を表す区分として扱われているか**
* 変更ルートの採否が人間判断事項として提示されているか

**正本の扱い**について、以下も確認してください。

* 変更内容の正本となる最上流かつ適切な正式資料を特定する構成になっているか（ルートB、またはルートB/Cでコード先行がある場合）
* 影響する資料を列挙するだけで、更新順が示されていない状態になっていないか
* 変更不要な上流資料を形式的に更新させる構成になっていないか（「上流優先」が「すべての上流資料を変更する」の意味になっていないか）
* **「正本候補なし」を一律に STOP へ寄せていないか**
* **「正式資料が意味を定義していない実装詳細」と「本来正式資料へ残すべきだが置き場がない」を区別できる構成になっているか。区別できない場合に人間判断へ戻せるか**
* **ルートBの反映順が「仕様 → 設計 → テスト計画」に固定されていないか。正本が仕様以外の場合（設計・フロー・共通設計など）を扱えるか**
* **標準化・共通化という変更内容だけを理由に、機械的にルートB またはルートC へ分類していないか。「どこでその正式な意味を定義することになったか」で判定する構成になっているか**
* 横断的な方針を各 feature の設計書へ無条件に重複記載させていないか
* 役割の合わない内容を `common_design/` へ押し込んでいないか
* AIが独断で新しい共通文書やディレクトリを追加する指示になっていないか

### 11-2. 未記載と矛盾の区別

`docs/rules/core/10_workflow.md`（「未記載と矛盾を区別する」）と `docs/rules/core/40_official_docs_and_context.md`（「正式資料が意味を定義していない実装詳細」）が正本です。task プロンプト側で再定義していないか確認してください。

以下を検出してください。

* 正式資料に未記載であることだけを理由に、不整合・指摘として扱う記述が残っていないか
* **逆に、正式資料と矛盾するコードまで許容してしまう記述になっていないか**
* review 系プロンプト（`review_feature_source.md`、`review_feature.md`、`review_command.md`、`review_design_code_consistency.md`）が、未記載と矛盾を区別できる構成になっているか
* 指摘に、どの正式資料のどの記述と食い違うかという根拠を求める構成になっているか
* 次のものを「未記載だから問題なし」として見逃す構成になっていないか
  * 仕様にない便利機能
  * 外部から見える動作の変更
  * 責務・境界としての意味の変更
  * 維持すべき呼び出し関係の変更
  * 共通設計で定義された内容との食い違い
* 生成AIの実装方式の揺らぎ（関数の切り方、変数名、局所的な書き方など）そのものを問題として扱う記述が残っていないか

### 11-3. コードから正式資料への逆反映

以下を確認してください。

* コード起点の知見を正式資料へ反映する経路が存在するか
* 反映先（どの正式資料か）と、接続先のプロンプトが示されているか
* **コードから見つかったものを何でも正式資料へ昇格させる構成になっていないか**
* 「今後も守るべき意味を持つか」を判断させる構成になっているか
* 昇格の採否が人間判断になっているか。AIが正式資料を自動更新できる構成になっていないか
* 役割の合う置き場がない場合に、新しい文書やディレクトリを勝手に作らせない構成になっているか
* 逆反映候補のために、不要なテンプレート項目を増やしていないか（既存の出力項目で扱えているか）
* 逆反映候補があることだけを理由に、レビュー結果を `要仕様確認` にする構成になっていないか
* **複数 feature にまたがる標準化・共通化を、起点を確認せずに一律で逆反映（ルートC）として扱っていないか**

### 11-4. コード先行（実施状態）

コード先行は変更ルートではなく、実施状態です。以下を確認してください。

* **コード先行が、変更ルートA〜Cと並ぶ独立した型として書かれていないか**
* コード先行が、後追い反映の免罪符になっていないか
* 未反映事項を残したまま完了として扱える構成になっていないか
* **AIが自ら「緊急だからコード先行にする」と判断できる構成になっていないか**（選ぶのは人間である旨が明記されているか）
* **コード先行と、実装詳細で完結する変更（ルートA）が混同されていないか。** ルートAはそもそも正式資料への反映が不要な変更であり、コード先行（反映が必要だが順序が後になった状態）とは別であることが明記されているか
* コード先行が、変更ルートB・Cのどちらでも起こりうる形で扱われているか
* バグ対応の通常フロー（報告→調査→修正計画→人間承認→実装）が維持されているか
* 緊急バイパス用のプロンプトや、通常の承認を簡単に回避できる仕組みが新設されていないか
* 事後に必要な確認（反映要否・テスト・レビュー・未了項目の管理）が示されているか

### 11-5. 2種類のプロンプトの役割分離

次の2本は、目的が異なります。役割分離が守られているか確認してください。

| プロンプト | 見るもの |
|---|---|
| `prompts/analyze_code_change_impact.md` | **変更**（これから行う変更／すでに行った変更） |
| `prompts/review_design_code_consistency.md` | **現在の状態**（今の正式資料と今のコード） |

以下を検出してください。

* 2本の責務が重複していないか。同じ判断を異なる基準で行っていないか
* どちらを使うべきかの導線が、ルール・人向け文書・プロンプト本体で一致しているか
* `review_design_code_consistency.md` が、`review_feature.md` / `review_command.md` の正式なレビュー結果を代替する構成になっていないか
* `review_design_code_consistency.md` が、対象 scope を指定せずにリポジトリ全体を無制限に読む構成になっていないか
* scope 外へ確認範囲を自動的に広げる構成になっていないか
* `review_design_code_consistency.md` の出力で、「意味上の矛盾」と「未記載だが問題ではない実装詳細」が明示的に分かれているか
* 両プロンプトとも、ファイルを変更しない構成が維持されているか
* 命名が既存の `review_*` / `analyze_*` の規則と整合しているか

**役割の自己矛盾**について、特に次を確認してください。

* `analyze_code_change_impact.md` の同一ファイル内で、「変更ルートを判定する」という記述と「変更ルートの判定を行わない」という記述が同時に成立していないか（役割説明の途中で主語が入れ替わり、自己矛盾になっていないか）
* `analyze_code_change_impact.md` が、自身の役割（変更ルートA〜Cまたは判断不能を判定し、実施状態・コード先行を別軸で整理する）を一貫して説明しているか
* `review_design_code_consistency.md` に、変更ルートA〜Cを判定する記述が入り込んでいないか（このプロンプトは現在の状態だけを見る）

### 12. core / project / task の責務分離

責務別ルール体系（`docs/rules/`）と task プロンプトの分離が成立しているか確認してください。

以下を検出してください。

* core にプロジェクト固有値（言語、テストコマンド、具体的なファイルパスなど）が混入していないか
* project が core を無効化・緩和する記述になっていないか
* task 固有手順が core や project へ混入していないか
* task プロンプトの `必須参照ルール` が過不足なく設定されているか
* `必須参照ルール`（守る上位ルール）と `参照するファイル`（今回の作業対象資料）が混同されていないか
* 通常 task が、不必要に core・project の全ルールを読む構成になっていないか
* 同じルールの正本が複数ファイルに分散していないか
* レビュー結果4値（成果物の状態）と次工程移行判定3値（次へ進めるか）が混同されていないか
* 条件付きGO が6項目（未解決項目／仮置きする内容と理由／条件付きでも進める理由／後続工程への影響／見直しが必要になる条件／人間判断が必要かどうか）で統一されているか
* レビュー補助メモの参照先が `docs/rules/core/50_records_and_reporting.md` へ統一されているか
* 「保護対象」（project が定める、明示指示なしに変更できないファイル群）と「変更してはいけないファイル」（今回の task で変更を許可されていないファイル）が混同されていないか
* 変更ルート（A〜C、または判断不能）と実施状態の定義が core に一本化され、project や task で再定義・増減されていないか
* 「未記載と矛盾の区別」の定義が core に一本化され、review 系プロンプトが再定義していないか
* 人間の直接修正の範囲（project）と、AIの変更権限（core・project・task）が、別のものとして書き分けられているか

### 13. 作業メモ（`docs/context/work_notes/`）の整合

作業メモの仕組み（`docs/rules/core/60_work_notes.md`、`docs/rules/project/60_work_notes.md`、`prompts/prepare_work_note.md`、`docs/templates/work_note_readme_template.md`、`docs/context/work_notes/README.md`）が、キット全体の方針と矛盾していないか確認してください。

以下を検出してください。

* 作業メモが、正式仕様・設計・ルール・`tasks.md`・レビュー結果・承認結果の**第二の正本**になっていないか
* 作業完了報告をチャットへ出力することと、その内容をリポジトリ内へ作業メモとして保存することが混同されていないか（`core/50_records_and_reporting.md` の「報告と保存の区別」と一致しているか）
* 作業メモの作成条件に「必要に応じて」等、判断主体や条件が不明な曖昧表現がないか
* README.md が、詳細記録の代替（短い要約への圧縮）になる構成になっていないか
* ミス・見落とし・手戻り・採用しなかった案などを、最終結果に不要という理由で削除させる方向の記述がないか
* 「Gitから復元できる」という理由だけで、判断理由・迷い・手戻り・却下理由などGitや完成物だけでは分からない経緯まで書けなくする、過度に強い禁止になっていないか
* 完了済み作業メモについて、履歴保護（原則追記）と、人間の明示指示による誤記訂正が両立する記述になっているか（「AIは絶対に書き換えてはならない」のような、訂正の余地がない過度な禁止になっていないか）
* `docs/context/work_notes/` が、`prompts/review_context.md` の通常の横断探索対象へ機械的に混入していないか
* 新しい作業メモの仕組みが、`docs/context/ai_work_logs/`（旧AI作業ログ）を名前だけ変えて復活させたものになっていないか（保存単位・作成条件・内容の自由度・正本性の違いが明確か）
* `prompts/prepare_work_note.md` の変更可能範囲が、指定された作業メモフォルダ配下に限定されているか。実装・仕様変更・レビュー修正まで行える広さになっていないか
* `prompts/prepare_work_note.md` が `docs/rules/project/60_work_notes.md` の運用（記録対象・粒度の決定主体、AIの利用形態、リポジトリ参照可否など）を独自に再定義していないか
* リポジトリを参照できないAIへの対応（自己完結した反映指示の生成）が、`docs/rules/project/60_work_notes.md`・`docs/rules/project/50_ai_permissions.md` と矛盾していないか。特に、AI同士が人間を介さず反映指示を受け渡すだけで保存が実行できる構造になっていないか
* 人間が作業メモ案を確認する前に、リポジトリへ保存できる構造になっていないか
* `prepare_work_note.md` を除く24本のprompt（開発工程task 23本と `review_prompt_integrity.md`）へ、`core/60`・`project/60` を機械的に一括追加する構成になっていないか
