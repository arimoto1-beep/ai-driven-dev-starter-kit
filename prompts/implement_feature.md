## 実装前確認（承認ゲート）

実装を開始する前に、まず `24_review_checklist.md` の「実装開始条件」の節を読み、**どちらの方式か**を判定してください。

| 記載 | 方式 | 確認する手順 |
|---|---|---|
| `方式: manual`、または「実装開始条件」の節がない | マニュアルモード | 下の「マニュアルモードの確認手順」 |
| `方式: auto` | オートモード | 下の「オートモードの確認手順」 |

**「実装開始条件」の節がない既存ファイルは、マニュアルモードとして扱います。** これは後方互換のための既定です。

### オートモードの確認手順

`方式: auto` の場合、**次の2つがともに成立していること**を確認してください。

1. `<対象機能フォルダ>/gates/` の**最新の CP1 Gate記録**に、人間による**下流進行承認**のチェック（`- [x]`）がある
2. `<対象機能フォルダ>/gates/` の**最新の G2 Gate記録**の front matter が `verdict: PASS` である

さらに、その G2 Gate記録に「**実装工程進行承認**」の節が「今回は対象外」以外の内容で存在する場合（G2 を Human Gate として運用している場合）は、その節のチェックもすべて入っていることを確認してください。

いずれかが欠ける場合は、実装を開始せず以下のメッセージで停止してください。

```
STOP — オートモードの実装開始条件が成立していません。

- CP1 下流進行承認: <あり / なし>
- G2 verdict: <PASS / それ以外 / 記録なし>
- G2 実装工程進行承認: <あり / なし / 対象外>

CP1 の承認は人間が行います。G2 の判定は prompts/review_stage.md が行います。
```

**CP1 の下流進行承認は「下流工程へ進めてよい」という判断であり、詳細設計・テスト設計を確認したうえでの実装承認ではありません。** 実装の可否は、上記2条件の成立によって決まります。

オートモードでは、`24_review_checklist.md` の「実装着手承認欄」は使用しません。**未チェックのまま残っていることは、STOP の理由になりません。**

**AIは、Gate記録の承認欄にも実装着手承認欄にも、自らチェックを入れてはいけません。**

条件が成立していることを確認した後、下記の「作業範囲」に進んでください。

### マニュアルモードの確認手順

1. 対象機能フォルダの `24_review_checklist.md` を読んでください
2. `24_review_checklist.md` に「実装着手承認欄」セクションが存在するか確認してください
3. 「実装着手承認欄」が存在しない場合は、実装を開始せず以下のメッセージで停止してください

```
STOP — 24_review_checklist.md に実装着手承認欄がありません。
prompts/create_review_checklist.md で承認欄付きの 24_review_checklist.md を作成または更新し、人間が確認してチェックを入れるまで、feature 実装には進めません。
```

AIが実装着手承認欄を勝手に追加して実装に進んではいけません。承認欄の作成・更新は `prompts/create_review_checklist.md` を使い、人間が確認してから再実行してください。

4. 承認欄のすべてのチェックボックスにチェック（`[x]`）が入っているか確認してください
5. 未チェック項目が1つでもある場合は、実装を開始せず以下のメッセージで停止してください

```
STOP — 実装着手承認欄に未チェック項目があります。人間が確認してチェックを入れるまで、feature 実装には進めません。

未チェック項目:
- <未チェック項目を列挙>
```

AIは実装着手承認欄にチェックを入れて実装に進んではいけません。チェックを入れるのは人間です。
実装着手承認欄がすべてチェック済みであることを確認した後に、以下の作業範囲に進んでください。

## 作業範囲

1. 仕様・設計・呼び出し定義・テスト設計・レビュー観点を確認してください
2. 実装前に、以下を簡潔に提示してください。
- 参照したファイル
- 変更予定ファイル
- 実装する内容
- テストで確認する内容
- 仕様・設計・テスト計画の不足や矛盾の有無
- 要検討項目・未解決項目・人間判断待ち項目の有無
不足・矛盾・要検討項目・人間判断待ち項目がある場合は、実装を開始せず確認事項として提示してください。
要検討項目が「記録済み」であっても、「解決済み」とは扱わないでください。

ここでいう「不足」とは、**実装に必要な意味が決まっていない**状態です。正式資料が実装詳細（関数の切り方、変数名、局所的な書き方など）まで規定していないことは、不足に当たりません。未記載と矛盾の区別は `docs/rules/core/10_workflow.md` に従ってください。
3. 関数呼び出し定義に従って実装してください
4. 実装をセルフレビューしてください
5. テスト設計に従って単体テストを作成してください
6. テストをレビューしてください
7. 可能であれば `python -m pytest` を実行してください

## 共通設計書の確認

`docs/<command_or_app_name>/common_design/` が存在する場合は、実装前に以下を確認してください。

- DB設計（`33_db_design.md`）が存在する場合、DBアクセスの実装がDB設計書の定義と整合しているか
- ファイル設計（`31_file_design.md`）が存在する場合、ファイル入出力の実装がファイル設計書の定義と整合しているか
- 共通データ設計（`32_data_design.md`）が存在する場合、データ項目の実装が共通データ設計書の定義と整合しているか

共通設計書に未定義の設計が必要だと判断した場合は、実装に勝手に追加せず、作業報告に「共通設計書への追加候補」として記載してください。

## 禁止事項

- 仕様にない便利機能を追加しないでください
- 外部ライブラリを追加しないでください
- 共通化候補があっても、人間レビュー前に `src/common/` へ切り出さないでください
- entrypoint.py や entrypoint テストを作成しないでください
- entrypoint が必要な場合は、`prompts/implement_entrypoint.md` を使ってください
- 結合試験が必要な場合は、`prompts/implement_integration_test.md` を使ってください
- 結合試験、外部API、CI/CD、デプロイ資産を作成しないでください
- 設計書と大きく異なる実装に勝手に変更しないでください
- 共通設計書（DB設計・ファイル設計・共通データ設計）と矛盾するDBアクセス、ファイル入出力、データ項目を実装に追加しないでください
